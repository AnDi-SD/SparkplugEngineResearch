# Захват сцены в USD

USD-захват сохраняет сцену для дальнейшего редактирования: геометрию,
экземпляры, материалы, текстуры, камеры и доступные данные скелета.
Успешная подача `DrawInstance` и получение скриншота сами по себе не
подтверждают работоспособность этого пути.

## Материалы Remix API

При подаче внешней геометрии `SceneManager::submitExternalDraw` связывает
поверхность с `MaterialData` из хранилища внешних материалов. В сопутствующий
`LegacyMaterialData` переносится идентификатор материала. Его поле текстуры
D3D9 при этом может оставаться пустым: материал API допускает постоянный
цвет без текстуры и отдельные текстурные каналы.

Следовательно, ненулевой хеш материала не гарантирует наличия
`getColorTexture().getImageView()`. Экспорт через безусловное обращение
`getImageView()->image()` приводит к ошибке доступа. Экспортёр должен
различать исходный материал D3D9 и внешний материал API, сохранять параметры
последнего и проверять наличие каждой текстуры перед чтением.

Для внешнего материала следует переносить значения, а не сохранять указатель
на запись API: запись может быть удалена после завершения подачи кадра,
тогда как запись USD выполняется асинхронно. Отсутствующая текстура является
допустимым состоянием. Текстура, которая задана, но ещё не загружена, требует
отдельной обработки; её пропуск нельзя считать полным захватом материала.

Исправление этого пути ещё проходит проверку. Захват игровых сцен с
`-AutoSurfaceRoles` пока не входит в подтверждённый рабочий сценарий.
[Патч экспортёра](../renderer-usd-fix/README.md) содержит изменения материалов
и Skin, правила сборки и границы уже проверенных возможностей.

## Скелет и веса

Размер палитры костей и число влияний на вершину — разные величины.
Экспортёр должен брать число влияний из фактической `RasterGeometry`
подсетки. Поле с таким же именем в `SkinningData` может описывать исходный
draw call: при создании экземпляра API геометрия подсетки присоединяется
позже. Нулевое значение нельзя использовать как предел цикла `count - 1`.

Remix API передаёт все веса явно. В исходном пути D3D9 последний вес
восстанавливается как единица минус сумма остальных. Эти способы хранения
нужно различать при захвате: восстановление последнего веса API изменяет
исходные данные. Экспорт также не должен самовольно нормализовать веса или
удалять отрицательные значения.

После чтения USD нужно проверить не только массивы весов, но и связь сетки
со скелетом, порядок суставов, bind pose и источник анимации. Итоговая
проверка вычисляет деформированные вершины через `UsdSkel` и сравнивает их
с независимым расчётом по исходной палитре. Статическая поза сама по себе
не подтверждает многокадровую анимацию.

Палитра матриц не содержит исходной иерархии суставов. Подчинение всех костей
первой создаёт дополнительное преобразование между их пространствами.
Сочетание вращения и неодинакового масштаба может внести shear, который
`UsdSkelAnimation` с компонентами translation/rotation/scale не сохраняет.
Для такой палитры кости следует записывать независимыми корнями, сохраняя
их исходный порядок и индексы вершин. Bind и rest transforms корней находятся
в одном пространстве; анимационная матрица равна `bind * skinningMatrix`
при используемых USD векторах-строках.

При многокадровой записи `xformOp` создают один раз для объекта, а затем
задают значения этой операции по времени. Повторный `AddTransformOp` с тем
же именем вызывает ошибку USD. Привязка материала также должна сопровождаться
применённой `MaterialBindingAPI` на примитиве, где записано отношение.

Эти случаи покрывает [CPU-проверка экспортёра](../renderer-usd-fix/offline-test/README.md).
Она проверяет запись и повторное чтение на собственных данных. Исходный shear
в самой матрице палитры и округление произвольного масштаба при хранении
в `half3` остаются отдельными ограничениями представления анимации.

Перенос анимации хранится в `float3`, вращение — в `quatf`. Поэтому точность
восстановленной палитры зависит и от bind pose. При переносе bind pose на `c`
экспортёр записывает `c * R + t`, а при чтении из этого значения вычитается
`c * R'`, где `R'` уже восстановлена из компонентов USD. Ошибка переноса
содержит округление записанного значения и произведение `c * (R' - R)`.
Далёкий от начала координат сустав может усиливать небольшую ошибку вращения.
Проверка должна отдельно учитывать типы записанных компонентов, восстановленную
палитру и конечные позиции вершин. Единый абсолютный допуск для всех этих
величин не описывает точность такого представления.

Представление знаковых весов WinxRemix содержит дополнительную нулевую кость.
Разложение матриц USD отвергает её и не записывает весь отсчёт анимации.
Для матрицы с полностью нулевой линейной частью существует точное представление:
нулевой масштаб, единичное вращение и исходный перенос. Экспортёр обрабатывает
этот случай явно и проверяет результат записи каждого отсчёта. Ошибка записи
должна завершать экспорт с ошибкой, иначе USD может молча использовать rest pose.

### Нормали после деформации

Совпадение деформированных позиций не гарантирует совпадения нормалей.
[Fixed.rfx](../../../docs/engine/animation/skin-deformation.md) умножает нормаль
на линейную часть каждой матрицы кости, суммирует влияния и нормализует результат.
Стандартный `UsdSkelSkinningQuery::ComputeSkinnedNormals` использует обратные
транспонированные матрицы. При масштабе эти операции могут дать разные направления.
Различие возможно и при равномерном масштабе каждой отдельной кости, если
масштабы нескольких влияющих костей неодинаковы.

Экспорт сохраняет исходные нормали. Он не компенсирует это различие изменением
данных: загрузчик Remix читает нормали и веса, а затем использует свой путь
деформации. Успешное чтение через USD не подтверждает освещение после повторного
импорта в renderer. Для такой проверки нужны нормали, не параллельные осям,
несколько влияний, масштаб и сравнение конечных направлений и изображения.

## Временные отсчёты геометрии

Индексы и атрибуты вершин могут иметь разные временные отсчёты. Отображение
сокращённых индексов должно сохранять идентичность вершин на всём интервале:
выбор отображения от следующего кадра подменяет текущие позиции и UV.
При постоянном наборе используемых вершин достаточно одного отображения;
при изменяющемся наборе экспортёр сохраняет полные буферы.
Топология использует удержание последнего значения, а числовые атрибуты
могут интерполироваться между отсчётами.

Если длины массивов между отсчётами различаются, USD удерживает предыдущий
массив. Сокращение обоих массивов до одинаковой длины изменило бы это поведение,
поэтому экспортёр сохраняет их исходные длины. Число граней строится из
фактического индексного буфера на каждом отсчёте, а не из числа индексов
при первом появлении сетки.

Каждый отсчёт цвета и прозрачности должен содержать значения только своего
массива. Накопление значений предыдущего отсчёта нарушает длину атрибута
`vertex` и его интерполяцию. Цвет с интерполяцией `constant` содержит одно
значение для всей сетки и не сокращается вместе с вершинами.
Стандартные индексы костей D3D9, напротив, создаются для каждой фактически
экспортируемой вершины и должны совпадать по длине с массивом весов.
[Проверка динамических буферов](../renderer-usd-fix/offline-test/README.md)
сравнивает атрибуты конечных треугольников после записи и чтения USD.

## Что проверять после захвата

Завершение операции требует окончания экспорта, завершения соответствующей
GPU-работы и повторного открытия сцены через USD. Раннее появление файла
сцены не означает, что связанные ресурсы уже записаны.

Завершение клиента и сервера проверяется по сигналу их удерживаемых
дескрипторов процессов через `WaitForSingleObject`. Код выхода может быть
доступен ещё во время завершения DLL; одного `Process.HasExited` недостаточно
для подтверждения очистки. Ожидание должно иметь предел, а принудительное
завершение собственного процесса — отражаться в результате проверки.

- Все внешние слои, материалы и текстуры должны существовать и разрешаться
  относительно сохранённой сцены.
- Нужно проверять состав видимых экземпляров и привязки материалов.
  Скрытые прототипы сеток не следует считать дополнительными видимыми объектами.
- Для геометрии проверяются позиции, индексы, нормали, UV и цвета вершин
  с учётом преобразования системы координат при экспорте.
- Для материалов проверяются сохранённые параметры и содержимое текстур,
  включая mip-уровни.
- Для скелета проверяются веса, индексы костей, связь с анимацией и результат
  деформации после чтения USD. Наличие массивов весов недостаточно.

Изолированный захват небольшой сетки проверяет конкретный путь экспортёра.
Полнота игровой сцены, многокадровая анимация и продолжительная работа
требуют отдельных проверок.

### Автоматический захват на заданном кадре

`DXVK_RTX_CAPTURE_ENABLE_ON_FRAME` задаёт номер кадра renderer. В текущем пути
запрос захвата проверяется на точное совпадение внутри подготовки сцены.
Если в этот момент подготовка пропущена, запрос не переносится на следующий
кадр. Успешные `Present` клиента не подтверждают, что подготовка сцены состоялась.

При включённом `rtx.shader.enableAsyncCompilation` незавершённая компиляция
Remix-шейдеров может пропускать подготовку сцены. Отдельный параметр
`rtx.initializer.asyncShaderPrewarming=false` отключает предварительный прогрев,
но не все фоновые задания регистрации шейдеров. Для отдельного ограниченного
теста можно подготовить профиль с `rtx.shader.enableAsyncCompilation=false`:
компиляция тогда может задерживать обработку кадра, поэтому контроль ресурсов
и внешнее ограничение времени сохраняют. Переменные `RTX_ENABLE_ASYNC_COMPILATION`
и `RTX_ASYNC_SHADER_PREWARMING` имеют приоритет над конфигурацией; тест должен
учитывать их фактические значения в дочернем процессе и восстанавливать окружение.
Такой профиль требует собственного успешного прогона. Отсутствие сообщения
`Begin USD export` отличают от ошибки уже начавшегося экспорта.

### Длительное ожидание и контроль ресурсов

Неотвечающее окно приложения не доказывает, что вычисления остановились.
Изолированная проверка может продолжать компиляцию, экспорт или ожидание GPU.
Физическую RAM, системный commit и память собственных процессов учитывают
раздельно: низкий остаток физической RAM сам по себе не равен исчерпанию commit.
Ресурсный профиль задают перед запуском, включая стартовый запас, потолок
собственных процессов и внешний предел времени. Контроллер работает независимо
от UI и сохраняет наблюдения, даже когда приложение не обрабатывает сообщения.

CPU-время и счётчики I/O показывают активность, но не подтверждают результат.
Отдельно отмечают новые этапы работы: начало и завершение USD-экспорта,
появление сцены, завершение GPU query и штатный выход. Повторное чтение того же
события или сообщение «продолжаю ждать» не обновляет время последнего результата.
Временная блокировка журнала для внешнего чтения требует отложить наблюдение,
а не прервать работающую операцию. После ожидания всё равно проверяют реальное
завершение собственных процессов и повторное чтение сохранённой сцены.

## Проект Toolkit и слой замены

Захват и проект Toolkit имеют разные роли. Workfile проекта содержит capture-слой
и replacement-слой; редактировать нужно replacement-слой. Исходный захват
сохраняют отдельно и проверяют, что создание проекта не изменило его ресурсы.

В Toolkit `ProjectWizardCore.setup_project_async` создаёт проект и связи `deps`
и `rtx-remix/mods/<project>`. Для прямого вызова API поля `project_file`,
`remix_directory` и `capture_file` передают как `pathlib.Path`: валидаторы этой
версии проверяют свойства пути до преобразования строк. JSON-файл конфигурации
остаётся строковым, преобразование выполняет адаптер перед вызовом. Результат —
пара `(success, error)`; непустая пара сама по себе не означает успех.
Работают только с новыми пустыми целевыми каталогами: мастер может заменять
существующие связи.

После создания workfile открывают через Toolkit, находят слои с типами
`workfile`, `capture` и `replacement`, выбирают `mod.usda` как edit target и
сохраняют через `LayerManagerCore`. Проверка читает сохранённые файлы, их
`lightspeed_layer_type`, связи workfile и фактический edit target.
Сообщение о невозможности создать checkpoint относится к отдельной операции
Nucleus после сохранения; успешную запись локального USD проверяют по файлу.

Создание, открытие и сохранение пустого проекта квалифицированы отдельно для
контролируемого rigid-захвата. Также подтверждены импорт DDS через настоящий MCP
Toolkit, замена существующего diffuse-входа материала с `force=false` и сохранение
mod. После завершения Toolkit независимый процесс USD SDK открыл проект и
прочитал записанную привязку. Два API-экземпляра используют этот общий материал;
контрольный native draw не имеет этой capture-привязки. Закрытие и повторное
открытие изменённого проекта через сам Toolkit, применение и удаление mod в том
же runtime остаются непроверенными этапами полного цикла.

### Команды импорта и сохранения

Подключение MCP подтверждают по discovery-записи запущенного экземпляра:
PID, endpoint и сообщение `SERVICE_READY service=mcp` должны согласовываться.
Фактический список инструментов и их схемы получают перед записью. Неподдержанные
поля запроса проверяют явно: генератор OpenAPI может отбросить лишний аргумент.

Последовательность для текстуры:

1. Подтвердить проект и выбрать replacement-слой как edit target.
2. Получить material prim и экземпляры через `get_model_instances`. Число всех
   экземпляров сцены не равно числу объектов с изменяемым материалом.
3. Проверить существующий вход через `get_texture_material_inputs`. Объявленный
   Asset-вход без значения отличается от отсутствующего входа.
4. Вызвать `ingest_material_asset`, проверить непустые `completed_schemas` и
   `validation_passed=true` для каждого результата. Материальный importer принимает
   `input_files=[[source_path,"DIFFUSE"]]`; исходник и output directory различаются.
5. Взять реальный выход `ConvertToDDS` из data flow `ingestion_output` и сопоставить
   его с `get_available_ingested_assets`. Имя результата заранее не конструируют.
6. Вызвать `override_textures` с `force=false`, затем `save_layer` и `get_textures`.

`executor=0` выполняет импорт в текущем процессе Toolkit. Ограничение conversion
workers снижает параллелизм; ресурсные проверки продолжают действовать.
Успешно импортированный файл сопровождается metadata: `validation_passed` и
`base_hash`, равным MD5 содержимого файла. Суффикс `.rtex.dds` сам по себе
не подтверждает успешную валидацию. Повторное использование такого ресурса требует
сохранения его точных bytes и metadata; выдавать самостоятельно созданный metadata
за результат валидатора нельзя.

`close_project(force=false)` отвергает pending edits. Перед закрытием проверяют
изменённые слои и сохраняют известные собственные workfile/replacement-слои.
Неожиданное изменение capture, внешнего или session-слоя требует отдельного
разбора. Ручное сбрасывание pending-флага и принудительное отбрасывание изменений
не подтверждают сохранение.

Сохранение replacement-слоя может запускать отложенное создание `capture_baker`.
Toolkit добавляет этот вспомогательный слой в mod, а в workfile записывает его
заглушение. Сам baker защищён собственными `flux_layer_widget_exclusions`:
запрещены add child, edit target, lock, move, mute, remove и rename. Эта защита
отличается от `omni_layer.locked` в workfile и от `Sdf.Layer.permissionToSave`.
В проверенном пути workfile блокирует исходный capture; отдельная запись
блокировки baker в workfile не требуется. Заглушённый слой может отсутствовать в
`GetLayerStack` и `GetUsedLayers`; его проверяют также через `GetMutedLayers`
и фактические `subLayerPaths`. Перед закрытием должны быть сохранены как
изменённые собственные слои, так и состояние контекста. Штатный Kit API
`UsdContext.save_layers_async` отличается от MCP `save_layer`: первый участвует
в сохранении состояния контекста, второй сохраняет отдельный Sdf-слой.
Готовность к закрытию проверяют по pending-флагу и чистоте всех слоёв независимо.

Имя capture stage определяет расширение файлов материалов, сеток и света.
Файл `.usd` может содержать бинарный USDC: его сигнатура — `PXR-USDC`.
При этом `Sdf.Layer.GetFileFormat().formatId` может возвращать `usd`, поскольку
этот формат выбирает способ хранения по содержимому. Роль слоя проверяют через
`Sdf.Layer` и типизированные `customLayerData`; сигнатуру и идентификатор формата
учитывают отдельно. Это относится и к файлам, перечисленным в отчёте Toolkit
о сохранённых слоях.

Renderer поддерживает `.usd`, `.usda` и `.usdc`, но проверенная версия события
Toolkit `copy_ref_to_override` конструирует ссылки baker с расширением `.usd`.
Для этого пути используют захват `.usd`. Переименование существующих файлов
не исправляет их внутренние ссылки. Проверка baker сопоставляет ссылку с
фактически записанной ссылкой исходного capture, включая целевой `primPath`.
Успешное чтение текстуры из открытого проекта не обнаруживает автоматически
оборванную ссылку внутри заглушённого слоя. Если mod содержит baker как sublayer,
этот слой и его зависимости входят в пакет mod.

`UsdUtils.ComputeAllDependencies` собирает USD-слои и записанные в них пути
ресурсов; импортируемые модули внутри MDL он не разбирает. Вместе с USD-набором
сохраняют файлы MDL захвата с исходными относительными путями, а также DDS и
его проверочные metadata. Такой набор сам по себе не доказывает наличие всех
библиотек MDL или успешную компиляцию материала. Для переноса используют явный
список файлов: ссылки `deps` и `rtx-remix/mods` проекта могут образовать цикл
каталогов. После копирования отдельно проверяют разрешение зависимостей из
нового расположения.

Переносимый mod сохраняет относительные ссылки на baker, материалы, текстуры и
ресурсы capture. Для runtime достаточно файлов, доступных из его entry layer;
workfile остаётся проектом редактирования. Обычные каталоги внутри mod заменяют
проектные junction без изменения содержимого USD. Все capture-ресурсы сохраняют
в том относительном расположении, на которое ссылается baker.

Каталог новых захватов runtime должен быть свободен от входных файлов mod.
Совпадение имени выходного capture с уже скопированным входом может испортить
ресурс и преждевременно удовлетворить проверку появления захвата. Перед запуском
проверяют непересечение путей, после завершения — неизменность входных файлов.

Повторное открытие в том же процессе может использовать кеш `Sdf.Layer`.
Для проверки диска применяют read-only `Sdf.Layer.OpenAsAnonymous` либо отдельный
процесс USD SDK. Проверяют тип и значение записанного Asset-входа, разрешение
относительной ссылки и неизменность DDS. Чтение через SDK и повторное открытие
через команды Toolkit получают отдельный зачёт.

### Discovery на локализованной Windows

MCP discovery запускает `whoami.exe` и `icacls.exe`. В проверенной Windows их
локализованный вывод использует OEM-кодировку; UTF-8 strict вызывает ошибку
декодирования. Изолированный overlay расширения задаёт `encoding="oem"` на этой
границе `subprocess.run`, сохраняя проверку кода выхода, timeout и ограничение ACL.
Выбор overlay через Kit `devPaths` подтверждают фактически загруженным extension
path, файлом модуля и его хешем. Наличие каталога overlay без такой проверки
не устанавливает, какой код исполнялся.
