# Текущий Skin draw и shader-контракт

`-SkinDrawAudit` проверяет полный текущий кандидат перед исходным indexed draw.
Геометрия берётся из [общего источника пакетов Skin](skin-packets.md), независимо
от записи файлов и частоты диагностических выборок. Наблюдение сохраняет
исходный draw и само не вызывает Remix API.

## Подготовка программ

Сборка исходника использует общую восстановленную
[подготовку PC shader](../../../Sparkplug/Code/SparkplugPC/spPCShaderSource.h).
Собственный helper не содержит второй копии правил shader manager.
Для подготовки каталога нужны MSVC x64, Python x64, оригинальный локальный
`Fixed.rfx` и D3DX9 SDK24 соответствующей архитектуры.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools/WinxRemix/Build-ShaderSource.ps1 -Name shader-source-check
python tools/WinxRemix/Prepare-SkinShaders.py --source-helper local-data/rtx-remix/shader-source-build/shader-source-check/shader_source.exe --fixed local-data/pc-pristine/Shaders/Fixed.rfx --output local-data/rtx-remix/skin-shader-contracts/skin-contract-check
```

Генератор принимает установленную реализацию Fixed и создаёт 160 вариантов:
B1–B4, ColorMode4, UV0 без texture transform, 0–3 источника света,
без specular. Поддержаны все упорядоченные сочетания directional, point и
spot; порядок входит в ключ программы. `--directional-only` создаёт прежний
каталог из 16 вариантов. Ограничение относится к программе, не к модели или уровню.
Дополнительный `--uv-transforms` удваивает выбранное семейство и включает
программы с матрицей UV0. Для смешанного света это каталог из 320 вариантов.
Другой исходный shader требует отдельного установления семантики.
Игровой исходник и скомпилированные программы остаются в `local-data/`.

Каталог WSF1: little-endian uint32 magic `0x31465357`, версия 1, число записей,
32 байта SHA256 исходной реализации; далее для каждой записи два слова
shader key, uint32 длина bytecode и сами байты. Каталог ограничен 1 МиБ,
512 записями, каждая программа — 16 КиБ. Дубли ключей и хвост не допускаются.
Это доверенный локально подготовленный вход, а не цифровая подпись.

При draw сравниваются native selection, фактически связанный COM shader,
его байты, инструкции VS1.1 и все отражённые параметры CTAB: имена,
регистры, типы, размеры и массивы. Различия creator/comment padding не
меняют семантику. Изменение инструкции или описания константы отвергается.

Ожидаемый набор констант зависит от типов света. `view_matrix` занимает три
регистра для directional и четыре при наличии point/spot; без света он
отсутствует. Массив каждого вида доходит до последнего использующего его
слота, включая промежуточные слоты другого типа. Point требует позиции и
attenuation, spot — позиции, направления и границ конуса. Неиспользуемые
массивы должны отсутствовать. Этот контракт определяет исходную программу;
отправка RT-света остаётся отдельной политикой адаптера и не воспроизводит
покадровое вершинное освещение Fixed.

Для программы с UV-преобразованием CTAB должен содержать `UVTransform`:
column-major float3x3, массив из восьми элементов с тремя используемыми
регистрами. Без соответствующего бита в ключе этот параметр должен отсутствовать.

## Проверка состояния

Проверяются VB/IB/declaration и диапазон draw, текущая палитра в shader
константах, native matrix caches, camera apply, завершённый world update,
MatDiffuse, Color4 material policy, состояния sampler/stages и поколение
текстуры. Первая поддержанная ветвь требует единичную native world matrix;
палитра уже задаёт мировую геометрию. Неизвестная ветвь нормали не угадывается.
Матрица UV0 читается из native-кэша и сверяется с xyz каждого загруженного
регистра. Неиспользуемый w регистра не участвует в сравнении; актуальность
native-матрицы проверяется снова перед отправкой.
Наблюдаемый `D3DTTFF_COUNT2` допускается вместе с доказанной программой:
UV уже вычислил vertex shader, повторного FFP-преобразования адаптер не делает.
Проективная выборка отклоняется. Эти состояния относятся к разным этапам
[конвейера D3D9](https://learn.microsoft.com/en-us/windows/win32/direct3d9/d3dtexturetransformflags).

Общий guard и перехваты setter отслеживают изменения состояния, включая
все шесть типов VS/PS-констант и StateBlock.Apply. Ошибочный setter тоже
инвалидирует чтение. Getter может временно вызвать нефинальный Device.Release;
такой вызов блокирует повторное чтение на время выполнения, но сам не
меняет состояние рендера. Вложенный setter и финальный Release инвалидируют
его по-прежнему. COM references освобождаются до заключительной проверки.

`cameraSubmitted` отдельно подтверждает принятие текущей камеры клиентским
API. `directLightsSubmitted` требует успешной отправки всей текущей группы
прямых источников, сохранения native registry/payload, API-владельцев и
политики исключения дублирующего legacy light. Ambient/environment сюда
не входят. Смешение отправок разных сцен в одном кадре не квалифицируется.
Эти поля не доказывают завершение GPU-команды.

## Запуск и проверки

К существующим параметрам `Start-Probe.ps1` и `Run-WinxRemix.ps1` добавляются `-SkinDrawAudit`
и `-SkinShaderContracts <путь к contracts.wsf>`. Launcher копирует каталог
в новый run и записывает его SHA256. Для системного D3D9 доступны
`-DebugMenu -Backend system`; API-поля в этом режиме остаются ложными.
Журнал `skin-draw-source.jsonl` ограничен 16 МиБ. Число вершин в повторных
выборках не является числом уникальных вершин сцены.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools/WinxRemix/Test-SkinShaderContract.ps1 -Name shader-contract-check -Platform x86 -Catalog local-data/rtx-remix/skin-shader-contracts/skin-contract-check/contracts.wsf
powershell -NoProfile -ExecutionPolicy Bypass -File tools/WinxRemix/Test-SystemSkinCapture.ps1 -Name skin-device-check
```

Собственные CPU/COM fixtures проверяют отдельные отказы, повторный вход и
владение; игровой запуск подтверждает связь с фактическими исходными draw.
Совместимость [постоянной геометрии с весами Fixed](../renderer-skinning-fix/README.md)
и визуальная проверка игрового live submit проверяются отдельно.

## Постоянная геометрия и изменяемая палитра

[Адаптер signed skinning](../winx_skin_gpu_submit.h) передаёт исходные позиции,
нормали, UV, явно подготовленные цвета и постоянные массивы весов/индексов.
Палитра передаётся отдельным расширением instance. Её изменение между позами
не пересоздаёт mesh. Текущая квалификация по-прежнему вычисляет CPU-эталон
деформации и цвета при каждом draw; это не путь без затрат на CPU-skinning.
На GPU передаются исходные позиции и отдельная палитра.
При включённом UV-преобразовании общий [расчёт Fixed](../../../Sparkplug/Analysis/PC/spFixedShaderSkinning.h)
готовит текстурные координаты. Для квалифицированной 2D-текстуры без проекции
используется xy результата, без деления на z. Изменение UV входит в ключ
неизменяемого mesh и может создавать новые ресурсы; одна смена позы этого не делает.
Разные экземпляры персонажей требуют разных устойчивых
идентификаторов владельца; одинаковый адрес после уничтожения объекта нельзя
считать прежним экземпляром.

Общий владелец Surface учитывает память весов и индексов, хранит необходимый
размер палитры по созданной геометрии и уничтожает mesh до его material.
Перед единственным вызовом DrawInstance повторно проверяется актуальность
состояния вызывающей стороны. Ошибка после начала API-вызова не разрешает
повторить исходный draw: неизвестно, успела ли команда попасть в очередь.

`Test-SkinPacketSubmit.ps1` проверяет обе формы геометрии, смену поз без
пересоздания mesh, разделение владельцев, отказ при короткой палитре,
повторный вход и освобождение при частично успешном Create/Draw.
Это проверка API-контракта с записывающими callbacks.

## Идентичность экземпляра и экспериментальная отправка

[Реестр экземпляров](../winx_native_instance_lifetime.h) связывает сцену,
RenderNode owner, Skin, mesh и поколение устройства с собственным номером.
Идентичность не зависит от номера кадра, позы или названия модели. Реестр
ограничен 8192 записями; заполнение означает отказ, без переиспользования номера.
Текущая связь объектов проверяется источником пакета отдельно при каждом draw.

Уничтожение сцены, RenderNode и Skin удаляет соответствующие записи до входа
в исходное тело деструктора. Уничтожение на другом потоке запрещает новые
borrow на время операции и сбрасывает прежнюю историю. Reset и финальный
Device.Release удаляют записи устройства. Потеря проверяемого перехвата
деструктора инвалидирует накопленные номера. Этот механизм не владеет игровыми
объектами и не продлевает их жизнь.

`-SkinSubmit` включает экспериментальный путь для RTX с расширениями
[моста](../skinning-bridge/README.md) и [рендерера](../renderer-skinning-fix/README.md).
Обычная поставка Remix не подтверждает поддержку этого пути. Launcher включает
Skin audit, native camera, native lights и общие material channels; каталог
shader-контрактов обязателен. Material channels сохраняют уже существующие
цветовые составляющие обычных поверхностей при совместной RT-отрисовке.
Перед подготовкой ресурсов требуются подтверждённые камера, прямые источники
света и идентичность экземпляра. После освобождения временных texture references
состояние проверяется снова. Подготовка использует общий материал Surface.

При отказе до API-вызова выполняется исходный draw. После начала вызова он
подавляется; ошибка API или нарушение актуальности отключает следующие Skin
отправки до перезапуска. В журнале разделены `candidate`, `instanceQualified`,
`apiCalled` и `apiSucceeded`. Это разные этапы; принятие API не доказывает
готовность изображения или корректность истории движения. Полная проверка
игровой RTX-анимации этого пути ещё не завершена.

Первые 32 отказа дополнительно сохраняются между обычными диагностическими
выборками: `reason` описывает отказ квалификации, `detail` уточняет этап.
Покадровые счётчики учитывают и те операции, которые не попали в подробный лог.
Для `reason=5` (`Program`) значения `detail=1..701` обозначают ошибку чтения
снимка D3D9; `1000` — чтение vertex shader, `1001` — его отсутствие или смену,
`1002` — установленный pixel shader, `1003` — отсутствие актуальных сведений
о привязанной программе, `1004` — несовпадение с каталогом, `1005` — различие
числа влияний. Поля подготовленной геометрии при отказе до завершения чтения
не описывают входную модель.
При отказе после чтения D3D-состояния `observedKey` отдельно сохраняет
наблюдавшийся shader key, а `stage0` — пары enum/value текстурного этапа.
Это диагностические значения, не свидетельство допуска программы.

Запись `timing` содержит длительности фаз в микросекундах и число входов.
Измерение использует `QueryPerformanceCounter`. `read` и `submit` включают
свои внутренние этапы; `current` учитывает повторные проверки актуальности,
в том числе внутри `instance`. Эти вложенные длительности нельзя складывать
в общий итог. Отдельно видны чтение пакета и состояния, shader-контракт,
константы, CPU-подготовка цвета, GPU-payload и ресурсы mesh/material.
Внутри `current` отдельно измеряются `currentPacket` (актуальность исходного
пакета) и `currentLights` (соответствие отправленному набору прямого света).

Для визуальной проверки нужны также обычные адаптации текстур, интерфейса,
неба и старых теней из [RTX-профиля](guide.md). Сам `-SkinSubmit` включает
зависимости источника Skin и API, но не заменяет остальные настройки профиля.
Минимальный запуск через `Start-Probe` с одними диагностическими флагами
не подтверждает качество обычного игрового изображения.

Отдельный [стенд истории движения](skinning-fixture.md#история-движения)
сравнивает GPU-палитру с независимым rigid API объектом. Его область проверки
ограничена искусственными переносами и не заменяет проверку игровых анимаций.
