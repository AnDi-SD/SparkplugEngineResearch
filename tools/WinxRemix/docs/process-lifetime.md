# Завершение собственных процессов

Launcher сохраняет `Process` и открытый дескриптор запущенного клиента и каждого
обнаруженного сервера из своего отдельного runtime. Путь и время создания
проверяются при установлении владельца; одно совпадение PID недостаточно.

Код выхода Windows может появиться до окончания `DLL_PROCESS_DETACH`. В этом
состоянии `.NET Process.HasExited` уже возвращает `true`, хотя процесс ещё
выполняется. Поэтому код выхода и строка об очистке в журнале сами по себе
не подтверждают освобождение процесса.

[ProcessLifetime.ps1](../ProcessLifetime.ps1) проверяет сигнал удерживаемого
дескриптора через `WaitForSingleObject`. `Get-OwnedProcessExitCode` по умолчанию
отклоняет чтение до сигнала. Режим `-AllowRunning` предназначен только для
диагностики ожидающего выхода. `Stop-OwnedProcess` при необходимости вызывает
`TerminateProcess` на том же дескрипторе и также дожидается сигнала.
Дескриптор принадлежит вызывающему launcher; после проверки он освобождает
сохранённый `Process` через `Dispose`.

Процесс также может закончиться между проверкой и `TerminateProcess`.
Если вызов завершения не удался, обработчик повторно проверяет сигнал того же
дескриптора. Подтверждённый выход закрывает операцию; если сигнала нет, исходная
ошибка Windows сохраняется. Это исключает ложный отказ очистки при таком
порядке выполнения потоков.

Стенды Skin и emission дают клиенту до пятнадцати секунд после появления кода
выхода, затем принудительно заканчивают затянувшуюся очистку. Такое завершение
считается ошибкой проверки, даже если процесс успел сообщить код 0. Сервер
проверяется отдельно. Общие ограничения времени и памяти продолжают действовать.

## Проверка без игры и GPU

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools/WinxRemix/Test-ProcessLifetime.ps1 -Name fresh-process-check
```

[Стенд](../test_process_detach.cpp) собирает собственные EXE и DLL. При выходе
DLL сообщает вход в очистку и ждёт отдельное событие. Родитель проверяет,
что код выхода уже появился, а сигнал процесса ещё отсутствует. В первом
случае родитель разрешает нормальную очистку; во втором проверяет принудительное
завершение через общий обработчик. Оба случая должны закончиться настоящим
сигналом процесса; посторонние процессы стенд не останавливает.

Ещё два случая воспроизводят гонку завершения для старого и исправленного
решения. В копию C#-метода вставляется одна точка управления расписанием:
после проверки работающего процесса разрешается завершиться собственной DLL,
затем вызывается настоящий `TerminateProcess`. Старое решение сообщает ошибку
5, хотя процесс уже вышел; исправленное подтверждает его сигнал. Остальные
операции метода и вызовы Windows сохраняются. Сгенерированные исходники и их
хеши входят в результат стенда.

Нужны Windows и MSVC x64. Исходники, бинарные хеши и результаты сохраняются в
новом `local-data/rtx-remix/bridge-shutdown-tests/<Name>`; использованное имя
отклоняется. Проверка подтверждает ожидание процесса, но не отсутствие утечек
внутри renderer или корректность всех путей завершения игры.
