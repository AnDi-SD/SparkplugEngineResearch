# SmoImporter

Версия рабочего дерева: **0.6.1**; последний опубликованный релиз — **0.6.0**.

В текущем рабочем дереве MeshData записывают общие восстановленные C++
MeshData/DXMeshData serializers и CPU buffers. Замена mesh resource, создание
skinned chunks и skeleton carrier используют один `SmoMeshDataWriter` через
native DLL. Собственная C# wire serialization удалена; donor conversion,
FAT repack и другие typed graph writers ещё требуют отдельной переработки.
Создание MeshBV в collision appender также передано общему C++ writer. Подбор
зарегистрированного шаблона, CollisionInfo/registration edits и FAT repack
пока остаются host-операциями и отдельными задачами переноса.

SMO preview/geometry reader получает общую сцену Exporter и разворачивает все
фактические reference slots, включая повторный Model. Матрица берётся из его
собственного размещения. ImportedScene пока не хранит несколько material passes
или layers: такой донор явно отклоняется с MATERIAL_IMPORT_SHAPE. Нативная
SMO-to-SMO замена переносит render forest напрямую и не использует этот DTO.

В 0.6.1 новые импортированные текстуры используют подтверждённый встроенный PC
BGRA-контейнер, включая точные NPOT-размеры. Шаблон определяется структурой,
а не байтами размера заголовка. Статическая замена записывает inline-текстуру
при первой ссылке; отдельная проверка не допускает ссылку до её определения.
Исходные файлы сохраняются, результат устанавливается после проверок.

Чистая замена персонажа использует подтверждённую явную native-ветвь как
шаблон. Неявные материалы удаляемых старых meshes и rigid-детали цели больше
не блокируют выбор шаблона. Shared spFog разрешается по реальной ссылке.
Проверены Bloom_body, bloom_jeans, Tecna, Icy и Flora: полная загрузка PC-кодом,
точные palettes/inverse binds, сохранность skeleton/collision и штатные SAN
в Viewer. Если подходящего шаблона нет, операция отклоняется до замены output.
SMO-донорный путь с переносом исходной ветви проверяется отдельно.

Clean skinned writer удаляет старые ветви одной перестройкой и избегает лишних
копий временного SMO/текстуры. На двух целях с четырёхмешевым OBJ-донором
проверенная запись ускорилась на 7–9%, суммарные выделения памяти уменьшились
на 25–27%; пик памяти процесса остался около 200 МиБ. Это отдельный замер
записи, не ускорение всего GUI или автоматического создания весов.

Создание весов теперь использует один проход: clean writer создаёт дополнительные
16-слотовые palettes, поэтому прежний предварительный подбор числа влияний не
требуется. Финальная проверка сохранена. На Дафне и Bloom reboot подготовка
ускорилась примерно вдвое при точном совпадении весов и SMO; суммарные выделения
уменьшились на 53–54%. Время отрисовки и отдельного анализа GUI в этот замер не входит.

SmoImporter заменяет модель в существующем PC SMO данными из SMO, OBJ, GLB или
FBX и создаёт новый проверенный SMO. Для персонажей сохраняется подтверждённый
игровой skeleton/service state; для объектов без скелета используется отдельный
нативный статический путь.

## Единственный актуальный конвейер

1. Открыть целевой SMO персонажа.
2. Открыть SMO, OBJ, GLB или FBX донора.
3. Выбрать способ подготовки скелета либо статическую замену без костей.
4. Настроить геометрию, позу и разделяющие плоскости, если выбран режим создания
   весов.
5. Проверить итоговый preview и создать новый SMO.

SMO-донор обрабатывается отдельным нативным путём. Reader декодирует его в
`ImportedScene` только для предварительного просмотра; сохранение не преобразует
донор и не использует общий writer для FBX/GLB/OBJ. Из целевого файла целиком
удаляется старая render-ветвь, а на её место переносится полная render-ветвь
донора со всеми `spSkin`, `MeshData`, material-объектами, UV, палитрами и
`TextureData`.

Идентификаторы объектов и внутренние ссылки перенумеровываются, чтобы не
столкнуться с сохраняемыми service/skeleton-объектами целевого контейнера. Байты
каждого `MeshData` и `TextureData` остаются идентичны донору. Поэтому нативные
неявные связи материала, которые игра понимает без отдельной material-ссылки,
не требуется угадывать или восстанавливать.

Ссылки внутри bone palettes `spSkin` также переводятся на новые object IDs.
Равенство наборов костей не требуется. Кость донора, которой нет в target,
схлопывается в ближайшего логического предка с именем из target-скелета; её
inline-ветвь физически удаляется, а palette-slot получает inverse bind общего
предка. Число слотов и индексы весов в `MeshData` не меняются. Если общий предок
определён позже первого использующего его слота, его исходная inline-сериализация
переносится в первый такой слот, поэтому native loader не получает forward
reference. Отсутствующие у донора deform-кости target не блокируют перенос.

Target-only листья анимационного графа, отсутствующие у донора (`hand_*`,
`foot_*`, camera/target/hair helpers и их аналоги), сохраняются на точных
одноимённых родителях. Если отсутствующий target-узел является целым неизвестным
поддеревом, операция блокируется вместо создания файла, который загрузится лишь
частично или упадёт при применении SAN.

Сохранение выполняется во временный файл, проходит строгий parse/decode и только
после этого атомарно устанавливается по выбранному пути. Существующий output
получает резервную копию `.bak`. Исходный SMO и файл донора не изменяются.

## Режимы портирования

- **Подготовленная модель** — donor уже использует подтверждённые игровые кости и
  пригодные skin weights.
- **Адаптировать существующий скелет** — donor weights переводятся только через
  доказанное соответствие костей. Неизвестная weighted-кость блокирует импорт.
- **Создать веса** — специализированный режим только для человеческих персонажей.
  Donor rig отбрасывается, все meshes анализируются как одна геометрическая сцена,
  а веса создаются на игровом скелете.
- **Статическая модель (без костей)** — только для target без `spSkin` и донора,
  у которого все meshes не имеют skin weights. Это standalone-профиль общего
  `SmoLevelModelGraphReplacer`, используемого также полной заменой моделей Level
  Creator. Ядро сохраняет нативный `spRenderNode → spModel → material/mesh`-граф
  цели и не создаёт `spSkin`, palettes или фиктивные веса. Размер, поворот и
  положение меняются полями либо тем же viewport gizmo, который используется при
  создании весов.

Writer выбирает одну безопасную нативную unskinned model/material-ветвь target как
структурный шаблон, удаляет остальные старые mesh-ветви и расширяет шаблон до
фактического числа частей донора. Поэтому прежнее количество mesh-ветвей target не
ограничивает OBJ/GLB/FBX-донор. Текстуры standalone-результата сериализуются
каноническим PC BGRA-путём и также не зависят от формата старого texture-шаблона.
Для общей текстуры донора ядро создаёт один `TextureData` и перенаправляет на него
все material consumers; разные изображения получают независимые texture resources.

Режим создания весов не является универсальным риггером животных, транспорта или
произвольных существ. Для них понадобится отдельный алгоритм.

## Плоскости и жёсткие детали

В человеческом режиме используются четыре независимых ограничения:

- плечевые стены начинаются от `L_Bicep` и `R_Bicep`, идут вниз и защищают
  руки от весов корпуса и ног;
- плоскость **Head** задаёт высоту и наклон жёсткой головы и защищает головные
  детали;
- плоскость **Back** отделяет цельные компоненты для ручной привязки к спине;
- нижняя центральная стена запрещает обмен весами между левой и правой ногой.

Геометрия не режется плоскостями. Классификация выполняется по цельным связным
компонентам и уникальным пространственным точкам. Head имеет приоритет защиты.
Back передаёт в ручную обработку только незащищённую цельную деталь, для которой
строго больше половины точек находится за плоскостью. Остальная геометрия тела
остаётся единым деформируемым набором.

Плоскость Head — единственный актуальный редактор головы. Старого объёмного
эллипсоида головы нет. Объёмные редакторы используются только для кистей.

## Текстуры и материалы

Embedded-текстуры донора и добавленные пользователем изображения образуют единый
каталог. Связь material → texture хранится индексом ресурса, а не угадывается по
номеру target slot.

Каждая используемая texture group сериализуется отдельным `TextureData` и
получает собственные material/`spSkin` consumers в skinned-пути либо отдельную
model/material-ветвь в статическом пути. Текстуры не собираются в общий атлас.
UV донора сохраняются. Прозрачность проверяется по реально используемым texels и
связным компонентам.

Поддерживаются PNG, JPEG, BMP и TGA. Нормали, roughness, metallic и служебные
карты не назначаются как base color автоматически.

## Проверка

Итоговый preview строится из той же подготовленной сцены, которая передаётся
writer-у. Автоматический запуск игры при сохранении отсутствует. Ручная проверка
доступна в разделе диагностики после создания файла.

Основные диагностические файлы:

- `SmoImporter.log` — журнал текущего запуска;
- adjacent save log — результат строгой проверки и этапов записи;
- `.bak` — предыдущая версия output, если она существовала.

## Сборка и запуск

Рабочее дерево использует общий Core и `SmoViewer.Editing`. Для сборки нужны
Windows x64, полный workspace и Visual Studio C++/CMake: автоматически собирается
`SparkplugViewerNative.dll`, необходимая рядом с приложением.

```powershell
dotnet build tools/SmoImporter/SmoImporter.Gui/SmoImporter.Gui.csproj
dotnet run --project tools/SmoImporter/SmoImporter.Gui/SmoImporter.Gui.csproj
```

Актуальные быстрые регрессии:

```powershell
dotnet run --project tools/SmoImporter/SmoImporter.FormatTests -- --glb-normal-repair-regression
dotnet run --project tools/SmoImporter/SmoImporter.FormatTests -- --glb-resource-safety-regression
dotnet run --project tools/SmoImporter/SmoImporter.FormatTests -- --alpha-component-regression
dotnet run --project tools/SmoImporter/SmoImporter.FormatTests -- --rigid-level-preparation-regression
dotnet run --project tools/SmoImporter/SmoImporter.FormatTests -- --static-model-replacement-regression <static-target.smo>
dotnet run --project tools/SmoImporter/SmoImporter.FormatTests -- --native-smo-visual-replacement <target.smo> <donor.smo>
dotnet run --project tools/SmoImporter/SmoImporter.FormatTests -- --porting-mode-pair <native|prepared|adapt|generate|static> <target.smo> <donor>
```

`--porting-mode-pair` запускает соответствующий production writer во временной
папке, повторно читает результат, проверяет тип visual graph и неизменность обоих
входов. Тяжёлые corpus-прогоны следует выполнять последовательно: FBX-конвертация
и большие многоматериальные GLB не предназначены для параллельного запуска.

Полный контракт человеческого риггинга описан в
[`BONE_BINDING_DESIGN.md`](BONE_BINDING_DESIGN.md).
