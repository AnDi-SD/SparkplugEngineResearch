# SmoImporter

Текущая версия: **0.4.0**.

Пользовательский архив предназначен для Windows x64. Запускайте
`SmoImporter.Gui.exe` из корня распакованного пакета: загрузчик проверит наличие
Microsoft .NET 8 Desktop Runtime и, только после подтверждения, предложит скачать
официальный установщик Microsoft. Само приложение находится в `app`, документация —
в `docs`. Отдельный `SmoNativeValidator.exe` не поставляется: его ядро встроено в
Importer и используется только для автоматической проверки созданного SMO.

Importer всегда пишет новый SMO и не разрешает сохранять результат поверх target
или donor. GUI загружает исходный SMO как серый фон, OBJ/GLB/FBX как оранжевую модель
замены и позволяет настроить uniform scale, XYZ rotation и translation.

В `0.4.0` стандартизирован импорт текстур. Вместо отдельных элементов для
embedded-текстуры, одиночного внешнего изображения и папки `matN` GUI использует
единый список доступных ресурсов. Встроенные изображения модели появляются в нём
автоматически, а внешние PNG/JPEG/BMP/TGA можно добавлять сразу группой, целой
папкой и удалять из списка.
Панель **Текстуры для импорта** находится сразу после выбора модели-донора, поэтому
изображения и material mapping можно подготовить до размещения, генерации весов и
автоматической нарезки.
Связь material → texture переводится с потенциально неоднозначного имени на
стабильный индекс исходного изображения. Несколько независимых texture groups уже
передаются раздельно в rigid и skinned writers; до ручной проверки в игре этот путь
считается экспериментальным.

Для внешних OBJ/FBX/GLB диагностическая галочка **Оставить текстуры исходного SMO**
импортирует геометрию, но запрещает writer-ам изменять или добавлять `TextureData`. Для skinned-модели все
примитивы используют основной visual group исходного SMO. Многоматериальная rigid-
модель в этом режиме проходит через одиночный body-slot и поэтому должна помещаться
в лимит 65 535 уникальных вершин. Текстуры донора остаются в списке, но временно не
используются; после снятия галочки все сопоставления восстанавливаются.

## Три режима портирования внешней модели

Для OBJ/GLB/FBX в `0.4.0` введён явный выбор способа подготовки геометрии.
Автовыбор только рекомендует режим по фактически прочитанным skin weights; пользователь
может сменить его. После отказа строгого режима 1 Auto отдельно запускает safety-анализ
режима 2; если тот не может однозначно сопоставить все активные donor weights,
рекомендация безопасно переключается на режим 3 и donor rig не используется.
Повреждённый rig не считается моделью без костей молча: если GLB
или FBX не удаётся прочитать как skinned-сцену, Importer повторно загружает только
геометрию и текстуры, показывает исходную ошибку и рекомендует режим 3. Это
**geometry-only fallback**, а не доверие некорректным костям или весам.

Для режима 3 первым этапом теперь является отдельное размещение donor geometry до
расчёта weights и rigid attachments. **Автоподгонка по росту и центру** заполняет
абсолютные uniform scale и XYZ translation как стартовую оценку; эти значения можно
исправить вручную. Они задают итоговый transform, а не дополнительную поправку поверх
скрытого auto fit. Начальная оценка использует полные bounds модели, поэтому крылья,
далеко вынесенные аксессуары и другие выбросы могут потребовать ручной коррекции.
Rotation на этом этапе пока запрещён и отклоняется Core.

Изменённые, но ещё не применённые scale/translation считаются pending: до нажатия
**Применить** нельзя построить plan или сохранить модель. Успешное применение заново
считает weights/attachments и сбрасывает подтверждение текущего результата. Alignment
входит в `FittingPreviewScene`/`PreparedScene` ровно один раз; preview не накладывает
его поверх подготовленной сцены, а writer получает уже подготовленную geometry с
identity transform.

1. **Подготовленная модель.** Все внешние meshes уже имеют пригодные weights, а
   активные joints строго сопоставляются с костями игры. Предпросмотр использует тот
   же путь, что writer, и сразу показывает геометрию в target bind pose. Исправлена
   граница систем координат: наружное right-handed пространство остаётся наружным,
   отражение обратно в SMO и смена winding выполняются только при сериализации.
   Несколько donor skins сводятся по точным именам; одинаковое имя с различными
   inverse-bind matrices считается конфликтом и блокирует импорт.
   `RetargetToGameBindPose` один раз применяет
   `donor inverse-bind × target bind-world`; `PreservePreparedGeometry` оставляет
   уже подготовленные positions/UV/weights неизменными и требует identity transform.
2. **Адаптировать существующий скелет.** Имена и rest pose донора не переносятся,
   но его исходные weights используются. Активные joints разрешаются только точным
   именем, безопасной нормализацией имени или явно заданным humanoid-алиасом;
   неизвестная weighted-кость не угадывается по близости. Геометрия пересчитывается
   из donor bind pose в bind pose игры, совпавшие target influences складываются,
   затем остаются четыре нормализованных веса. Результат получает точные target
   bone names и target inverse-bind matrices и показывается до сохранения.
   Опциональная ручная подгонка переводит этот режим в weights-only вариант:
   donor inverse binds больше не задают геометрию, пользовательский uniform donor
   alignment помещает модель вокруг временной позы target, а числовые local bone
   rotations уточняют эту позу перед обратным bake.
3. **Создать веса с нуля.** Экспериментальный pipeline передаёт Core полностью
   unskinned сцену. Перед weights и attachments к ней применяется окончательный
   абсолютный uniform scale + translation; без явного значения Core может получить
   его консервативной автоподгонкой к target bind geometry. Автоподгонка позы работает
   только с уже применёнными uniform scale/translation: pending alignment сначала
   нужно применить, а при плохом совпадении ориентиров GUI показывает предупреждение
   вместо доверия сомнительному результату. Core детерминированно строит связные
   компоненты и по одной геометрии выбирает либо цельное тело, либо пару «ноги/низ» +
   «торс/руки». Имена meshes и материалов для выбора не используются, поэтому крылья
   исключаются не по специальному имени.

   Выбранный `TargetRigBodySelection` содержит точную принадлежность исходных вершин
   и привязан к target, donor topology и применённому alignment. Тот же selection
   передаётся в `GeneratedSkinningPreparer`: всем выбранным поверхностям выдаются
   side-aware L/R веса по капсулам безопасных deform-костей, максимум четыре
   нормализованных влияния. Каждый оставшийся компонент сохраняется целиком, получает
   rigid-привязку к одной ближайшей безопасной кости и возвращается в `Attachments`.
   Ни один рисуемый связный компонент автоматически не удаляется.

   FBX/glTF может содержать служебные vertex slots, не входящие ни в один
   невырожденный треугольник, а также грани нулевой площади. Общая
   нормализация топологии не включает их в body selection и attachments:
   нулевые грани исключаются из подготовленного triangle stream, а исходные
   массивы и индексы вершин остаются стабильными, а нерисуемые slots получают
   детерминированный безопасный placeholder weight. Это одинаковое правило для
   всех моделей; имена meshes, materials и файлов в нём не участвуют.
   Выход индекса за границы, неполная тройка индексов или non-finite positions/площадь
   по-прежнему считаются повреждённой геометрией и блокируют подготовку.

   Выбор body-поверхностей отделён от оптимизации позы: Core может построить
   `TargetRigBodySelection` через `SelectBody` без запуска **Автоподгонки**. Поэтому
   ручную или нейтральную позу режима **Человек** можно сразу применить после
   размещения donor; Auto остаётся необязательной стартовой подсказкой.

   Для центральной smooth-поверхности расстояние до капсул дополнено конечными
   анатомическими полями, откалиброванными по исходным target weights. Вдоль цепочки
   позвоночника строятся эллиптические объёмы, сдвинутые вперёд на свою полуось:
   их задняя стенка касается линии позвоночника, а центр не лежит на ней. Для `Head`
   отдельно строится такой же сдвинутый вперёд эллипсоид. Это удерживает грудь и
   голову на центральных костях, когда длинные капсулы рук или ног геометрически
   оказываются ближе. Поле имеет конечное плавное затухание; за его пределами остаётся
   прежний capsule score, а нижняя граница корпуса не заходит в ноги. Поэтому веса
   рук и ног вне этих центральных объёмов не меняются.

   Результат всегда требует явного подтверждения. Донор обязан уже быть upright,
   Y-up, не зеркальным и смотреть в ту же сторону, что target: по одной поверхности
   надёжно определить front/back невозможно, поэтому режим не вращает и не отражает
   модель. Неоднозначная topology, неполный target decode или сомнительный fit
   блокируют подготовку вместо догадки. GUI показывает alignment, предупреждения и
   полный список rigid attachments. При ручной подгонке режима 3 разрешены только
   local bone rotations; root rotation/translation отключены, поскольку абсолютный
   donor alignment остаётся в canonical target space. `RequiresConfirmation` всегда
   равен `true`. Перед подтверждением GUI обязан хотя бы один раз показать точный
   канонический `PreparedScene` текущей ревизии. Для этого есть отдельная кнопка
   **Показать итог и разрешить подтверждение**: пользователю не нужно искать скрытую
   зависимость от галочки fitting pose. После просмотра `PreparedScene` и явного
   подтверждения разблокируются plan/save; новая правка позы снова отменяет просмотр
   и подтверждение.

   Перед **Автоматической нарезкой** доступна отдельная кнопка **Показать окончательный
   результат с текстурами**. Она запускает тот же geometry-preparation path, что writer,
   и показывает полный подготовленный mesh с фактическим atlas, переписанными UV и
   импортируемыми изображениями; вспомогательные серый target, skeleton overlay и
   изоляция деталей на время этого просмотра скрываются. При включённом режиме
   **Оставить текстуры исходного SMO** такой donor-texture preview недоступен, а для
   проверки остаётся прежняя явная кнопка одноцветного канонического
   `PreparedScene`; пока текущая ревизия не засчитана просмотренной, она доступна
   даже если canonical scene уже находится в viewport. Для legacy rigid `matN`
   окончательный текстурированный preview также намеренно отключён: сырой preview
   не воспроизводит его packer/writer и потому не выдаётся за точный результат.

   Для `local-data/Лейла/Model.obj` и эквивалентного FBX при применённом масштабе
   автоподбор детерминированно выбирает две body-поверхности из 43. Обе получают
   smooth weights, а остальные 41 компонент, включая восемь частей крыльев, остаются
   rigid attachments. Production writer собирает material groups в один RGBA-atlas
   основного texture group, переназначает UV с wrapped gutters и переносит donor RGBA,
   но не сводит разные режимы смешивания в один consumer. PNG Alpha сам по себе не
   определяет режим материала: у Layla прозрачные texels `mat3`/глаз и `mat4`/рта
   содержат полезный RGB и являются непрозрачными лицевыми накладками. Для них в списке
   текстур нужно явно выбрать **Непрозрачная накладка**; `mat5`, `mat6` и `mat7`
   остаются в режиме **Авто**. Тогда 2 714 opaque triangles остаются на существующих
   opaque `spSkin/material`-ветвях target, 124 triangles глаз/рта получают две
   независимые opaque overlay-ветви, а только 70 действительно прозрачных triangles
   записываются в три alpha-ветви со ссылкой на тот же atlas. Каждый исходный
   renderable начинает собственную material-bearing `spSkin`-ветвь; разные глаза,
   рот, украшения, крылья и подвеска не объединяются только потому, что помещаются
   в одну bone palette. Новые ветви используют текущие
   сгенерированные веса и target
   palettes, поэтому разделение материала не возвращает старую Head-only привязку.
   Для фиксированных 16-костных palettes режим 3 сначала пробует четыре влияния,
   а при доказанной нехватке ёмкости адаптивно ограничивает их до трёх или двух
   и повторяет точное
   разбиение. На Layla выбран предел в три влияния. Strict writer, Viewer и native
   loader проверяют структуру, ссылки и загрузку результата, но не подтверждают его
   визуальный blend в игре.

Если для режима 3 выбран skinned или частично skinned GLB/FBX, GUI повторно читает
весь исходный файл как geometry-only вместо выборочного удаления meshes. Внешние
texture overrides сохраняются. Папка `matN` — только rigid workflow: в режиме 3
автоматически найденный bundle полностью игнорируется, его frames не показываются,
а кнопка выбора папки отключена. Текстуры для режима 3 добавляются пакетно через
**Добавить файлы…** и должны однозначно сопоставляться с material references полной
исходной сцены.

Все три режима используют существующий target skeleton/object graph. Donor nodes,
control graph и animation logic не сериализуются; длины костей и связи target не
изменяются. Uniform placement режима 3 меняет только donor geometry; target bind и
inverse-bind matrices остаются игровыми. Подготовленная геометрия передаётся
существующему writer-у как уже находящаяся в target bind pose и не трансформируется
повторно.

Редактор позы имеет два переключаемых режима и по умолчанию открывается в режиме
**Суставы**. В нём deform-сустав выбирается из списка или щелчком непосредственно в
preview, а три ползунка задают его абсолютные local Euler angles X/Y/Z в диапазоне
от −180° до +180°. Выбранный сустав подсвечивается красным. Режим **Человек**
предлагает **Автоподгонку** и симметричные controls: подъём и направление рук,
анатомически направленный сгиб локтей, разведение и сгиб ног, наклон корпуса и
движение шеи вперёд/назад. Руки и ноги рассчитываются как симметричные
двухсегментные цепочки с неизменными длинами. При движении шеи `Head` получает
bind-local counterrotation, сохраняющую его мировое направление вперёд; отдельная
ручная поправка головы поверх этого не теряется.

Оба режима редактируют один общий `TargetRigFittingPose`: переключение не сбрасывает
позу, значения режима **Человек** видны в **Суставах**, а rebase high-level controls
сохраняет уже внесённые ручные коррекции. Изменение ползунков создаёт live draft и
сразу обновляет preview. До **Применить** эта поза считается pending и блокирует
plan/save; применение фиксирует snapshot, пересчитывает подготовку и сбрасывает
прежнее подтверждение. `FittingPreviewScene` показывает временную позу, а
`PreparedScene` возвращает geometry per-vertex в canonical target bind перед writer.
Target hierarchy, длины parent-child связей, исходный bind и inverse-bind matrices
не меняются. В режиме 2 дополнительно доступны ручной donor alignment и weights-only
подготовка; в режиме 3 root transform запрещён. **Применить** работает и до первого
запуска **Автоподгонки**: selection для подготовки разрешается отдельно, поэтому
ручной workflow не зависит от optimizer-а.

В режиме 3 внутри **Человек → Жёсткие детали** можно переопределить автоматическую
rigid-привязку отделённых частей — например, закрепить крылья за верхней частью спины,
а отдельные локоны за головой. GUI показывает точные связные компоненты в списке и
позволяет выбрать их щелчком по треугольнику в preview; `Ctrl` добавляет или убирает
компонент из выделения, `Shift` выбирает диапазон в списке. Выбранные компоненты
подсвечиваются в viewport. **К спине** задаёт строгое one-hot влияние `Spine_03`,
**К голове** — строгое one-hot влияние `Head`, а **Вернуть автоматическое назначение**
снимает ручную привязку.

Галочка **Скрыть основное тело модели-донора** оставляет в authoring preview только
отделённые rigid-компоненты, чтобы их было проще выбирать. Это исключительно режим
отображения: он не меняет body selection, weights, attachments или вход writer-а;
окончательный текстурированный preview снова показывает модель целиком.

Назначения сохраняются при изменении позы, scale/translation, переключении режимов
редактора/портирования и текстур, пока target и геометрия donor остаются теми же.
Перед каждым применением Core сверяет точные fingerprints target/donor, число
компонентов и принадлежность каждой вершины; устаревшее или неоднозначное назначение
блокируется. Закреплять можно только отделённые компоненты из `Attachments`: часть,
сваренная с общей smooth-поверхностью, нельзя целиком выделить и превратить в rigid
деталь этим инструментом. Уже созданные SMO не меняются задним числом — после новой
генерации весов или назначения деталей результат нужно создать заново.

Скелет рисуется поверх геометрии в screen space, поэтому остаётся видимым и пригодным
для выбора даже внутри непрозрачной модели. В режиме **Суставы** щелчок выбирает
сустав, но не является viewport gizmo: напрямую тянуть или вращать кости мышью пока
нельзя. Euler angles также имеют обычную неоднозначность и gimbal lock; у одной и той
же ориентации может быть несколько эквивалентных троек значений ползунков.
Donor по-прежнему должен быть upright, Y-up и смотреть в ту же сторону, что target.
Сохранение target skeleton/анимационного graph не доказывает качество деформации во
всех клипах, поэтому анимации и поведение модели необходимо проверить вручную в игре.

В `0.2.0` появился отдельный режим **SMO → SMO**, а в `0.3.0` его writer переведён
на append-only visual packing. Если модель-донор уже является SMO, GUI отключает
подгонку, rigid bone, ручную текстуру и повторную нарезку. Importer проверяет
платформу и совместимость общих костей, сохраняет исходный
service/skeleton graph target: его каталог, IDs, collision volumes, movement
trackers, `SubMaster`, IK/control nodes, attachments, character markers и ещё не
расшифрованные связи. Старые target meshes остаются структурными anchors, но получают
невидимые degenerate triangles. Полные donor visual branches — `spSkin`, materials,
textures, UV controllers и meshes — добавляются отдельно с новыми уникальными IDs.
Donor nodes и служебный graph не копируются: reference-only palettes указывают на
target nodes по именам костей и сохраняют donor inverse-bind matrices. После этого
пересчитываются каталог, enclosing sizes и offsets контейнера.

Такой append-only путь не пытается сжимать donor atlases в существующие target slots
и не заменяет неизвестный runtime graph целиком. Контрольный перенос Faragonda в
`bloom_jeans.smo` сохранил все 121 target objects, добавил 21 visual object,
7 meshes и 3 исходные donor textures. Один byte-identical общий visual helper
переиспользуется, поэтому итоговый каталог содержит 142 objects. Результат прошёл strict parser, быстрый
native smoke test и контекстную загрузку в настоящем Bloom slot на Gardenia02.

Упаковщик также поддерживает visual forest из нескольких render roots. Контрольные
StellaX ↔ `bloom_jeans.smo` сохраняют отдельную голову, rigid-крылья, все 38 ссылок
анимированной texture sequence и общий атлас `stella_x`. Оба направления прошли
strict и быстрый native smoke test; StellaX → Bloom дополнительно проверен в
настоящем Bloom slot.

Для rigid GLB, OBJ и FBX без скелета добавлен отдельный **multi-texture → SMO** путь. Он
связывает mesh/material с PNG по именам `matN.png` либо `_matN.png` и кадрам
`matN.1.png`, `matN.2.png` и т. д., создаёт отдельные `spSkin`, material,
texture и mesh branches для каждой material group. Production writer принимает здесь
только полностью непрозрачные привязанные frames (`A = 255`) и сохраняет их BGRA
пиксель-в-пиксель. Любой `A < 255` fail-loud блокируется в анализе и повторно прямо
перед созданием файла: для generated one-bone `spSkin` пока не подтверждён полный
alpha material/sort-state contract. Уже кратные степени двойки текстуры переносятся
пиксель-в-пиксель; остальные
увеличиваются по каждой оси до ближайшей следующей степени двойки, никогда не
уменьшаются и ограничены размером 2048. Геометрия жёстко привязывается к palette
slot 8, который target обязан разрешать как `Head`; это номер слота конкретной
палитры, а не глобальный ID кости.

GUI автоматически проверяет PNG рядом с моделью, но также позволяет выбрать отдельную
папку с текстурами. OBJ разбирается по `mtllib`/`usemtl`/`map_Kd`; если MTL отсутствует,
достаточно material-имён `matN` и выбранной папки. FBX конвертируется через Blender,
после чего geometry primitives связываются по material/image metadata. Meshes и PNG,
которые не относятся ни к одной активной `matN`-группе, явно показываются как пропущенные.

Регрессия на обновлённых `local-data/Лейла/Model.obj` и `Model.fbx` проверяет 7 material
meshes, 11 textures и две texture sequences для групп `mat3`/`mat4` в двух вариантах.
Копия кадров с `A = 255` проходит полный opaque writer/strict round-trip и сохраняет
target material state; копия с `A < 255` обязана быть отклонена анализом и прямым
writer без создания файла. Более ранние strict/native проверки alpha-варианта
подтверждали сериализацию и загрузку ресурса, но, как показал игровой тест, не
подтверждали корректный render contract.

После каждого успешного сохранения GUI автоматически запускает короткую нативную
проверку в изолированном оконном окружении. Пользователю остаётся только путь к
`WinxClub.exe`; итог показывается одной карточкой «подходит / не подходит / не
определено» без журнала и дополнительных настроек. Зелёный результат подтверждает
FFPS header/version, ненулевой `ResourceLoad` и окно наблюдения, но не заменяет
визуальную проверку анимаций и поведения модели в игровом уровне.

Различающийся набор костей показывается в раскрываемом дереве GUI. Совпавшие
bone names используются для перепривязки служебных ссылок. Дополнительные weighted
кости донора показываются в дереве как игнорируемые; их weights сворачиваются в
ближайшие совместимые target bones, поэтому их отдельная локальная анимация теряется.

Иерархия сравнивается по ближайшему weighted-предку. Различающиеся невзвешенные
control/helper nodes не блокируют совместимую deform-цепочку, но показываются
отдельной веткой с полными target/donor paths. Для `Spirit.smo` так распознаются
шесть цепочек через `C-LegRoot*`, `C-ArmRoot*` и `C-SpineRoot*`; её
`L/R_strip_1…3` сворачиваются в соответствующие `L/R_UpperArm`.

В режиме SMO → SMO donor vertex records и topology переносятся без перекодирования.
Field-wise конвертация в target layout (`0x093E → 0x097E`, включая вычисление
normals) остаётся частью отдельного пути внешнего skinned GLB → SMO.

В `0.2.0` также появился экспериментальный путь **skinned GLB → SMO** для уже
подготовленной внешней модели. Он читает `JOINTS_0`, `WEIGHTS_0`, inverse bind
matrices, материалы и embedded base-color, показывает дерево соответствий костей
и сохраняет весь object graph целевого SMO. Вершины автоматически переводятся из
bind pose GLB в bind pose target, а triangles переразбиваются по существующим
16-костным palettes. Неизвестные имена костей не угадываются: без подтверждённого
соответствия запись блокируется.

Bind-pose перенос теперь имеет два явных режима. GUI по умолчанию использует
`RetargetToGameBindPose`: вершины и normals ровно один раз переводятся формулой
`donor inverse-bind × target bind-world`, после чего в SMO записываются только
игровые bone IDs и игровые inverse-bind matrices. Donor node hierarchy, rest-pose,
control nodes и animation logic никогда не сериализуются. Диагностический
`PreservePreparedGeometry` не меняет positions/UV/weights и допустим только с
identity transform; он предназначен для моделей, уже подготовленных точно в
игровой bind pose. GUI блокирует AutoFit и произвольный transform для skinned-моделей.

Если несколько material primitives используют один image, они остаются одной
body-atlas группой. Texture writer меняет RGB только сопоставленного texture object;
непарные eyes/effects проверяются побайтово. Контрольная подготовленная Текна
(`local-data/Текна/untitled.glb`) использует 17 точно совпавших active joints и
382 triangles. В результате сохранены обычный `Tecna.smo` skeleton/animation graph
и глазной `tecna_e`, а новый body atlas применён только к `tecna`. Файл прошёл
strict parser, быстрый native smoke и две загрузки в настоящем Cloud01_02 без
ошибок serializer и crash; все игровые проверки выполнялись оконно.
Вложенные однокостные render-ветки (например, `bloom_eyes` под `Head`) считаются
жёсткими runtime-контрактами и больше не перепрофилируются под произвольный
material primitive. В generated-skinning path opaque и alpha primitives могут
использовать один RGBA-atlas, но получают разные material consumers и render-ветви.
Обычный single-texture путь skinned writer по-прежнему меняет только RGB и сохраняет
Alpha target SMO. Multi-material generated-skinning путь собирает один RGBA-atlas,
переписать UV в его ячейки и перенести donor Alpha; непрозрачные и прозрачные
triangles при этом не смешиваются в одном material consumer. Для
`0x32E3`/`0x43E3` настоящий BGRA payload начинается с
`+0x3D`, а не со служебного marker `00` на `+0x3C`. Atlas ограничен размером
существующей target-текстуры (для Bloom — 256×256), поэтому исходные изображения
могут уменьшаться; большие tiled UV за пределами проверяемого gutter блокируются.

## Контракт Alpha/Blend

`FinalBlendOp` — отдельная операция/enum, а не набор битовых флагов. Поэтому значение
`4` нельзя интерпретировать как «включён Alpha» только потому, что в нём установлен
бит `0x4`: в исследованном игровом материале это семейство glow/effect, и обычный
skinned atlas не должен получать `FinalBlendOp = 4`.

Production-контракт обычной skinned texture-alpha поверхности перенесён из
нативного comparator `Minautor.smo`. Для каждого самостоятельного source renderable
создаётся отдельная material-bearing цепочка `spSkin → material → mesh` с состоянием
`FinalBlendOp = 2`,
`MaterialRenderStates = [0, 0, 1, 0, 1, 1, 3, 0, 4, 0, 6]`,
`LayerTextureStates = [0, 3, 3, 0, 0, 4278190080, 2, 0, 0]`,
`AlphaSortEnable = 1`, `Priority = 1` и vertex diffuse `0xFF000000`. Только
palette/ushort-продолжение того же renderable может нести mesh без собственного
material consumer. Само произвольное значение `FinalBlendOp = 2` не означает Alpha:
классификация требует точного связанного consumer state и фактически прозрачных
texels, покрытых UV его triangles. Встречающиеся у `IceWorm`/`Yeti` ветви с
`FinalBlendOp = 6` относятся к другому подтверждённому семейству и не являются
универсальным шаблоном для всех персонажей.

Тиара `bloom_princess.smo` остаётся полезным структурным примером маленькой локальной
alpha-ветви, но её старое состояние с `MaterialRenderStates[5] = 0` и
`AlphaSortEnable = 0` не является production-шаблоном для больших skinned-крыльев.
В игре такие крылья с этим состоянием могут перекрываться более далёкими alpha-
поверхностями листвы и уровня. Поэтому importer не копирует Princess tuple на
крылья и другие крупные прозрачные поверхности.

PNG Alpha не является достаточным признаком прозрачного материала. В частности,
`mat3`/глаза и `mat4`/рот Layla хранят полезный цвет даже в texels с исходным `A = 0`:
это непрозрачные лицевые накладки, а не настоящие alpha-поверхности. Явный режим
GUI **Непрозрачная накладка** переводит `A` всей выбранной source texture group в
`255` до premultiplied resize atlas, поэтому скрытый RGB не теряется, и создаёт
отдельный post-body run с каноническим состоянием глаз `bloom_jeans.smo`:
`FinalBlendOp = 0`,
`MaterialRenderStates = [0, 0, 1, 0, 1, 1, 3, 0, 4, 0, 6]`,
`LayerTextureStates = [0, 3, 3, 0, 0, 4278190080, 2, 0, 0]`,
`AlphaSortEnable = 0`, `Priority = 1`, vertex diffuse `0xFFFFFFFF`. Белый diffuse
совпадает с generated retained body, который writer создаёт для OBJ без vertex
colors, и не вводит отдельную углозависимую модуляцию лица. Нормали при этом не
сплющиваются, не заменяются и не перенаправляются: сохраняется обычный importer path
нормалей. Профиль привязан
к точной donor scene и применяется одинаково в Analyze, окончательном preview и writer;
неполная texture group или устаревший профиль отклоняются, а режим **Авто** сохраняет
прежний классификатор.

Production-путь Layla теперь разделяет общий RGBA-atlas на три семейства: 2 714
opaque body triangles остаются на исходных opaque branches target; `mat3`/глаза (72)
и `mat4`/рот (52) получают два независимых opaque-overlay
`spSkin/material/mesh` runs; 70 действительно прозрачных triangles получают три
alpha-runs с production-состоянием `Minautor.smo`: `mat5`/украшения (34),
`mat7`/крылья (34),
`mat6`/подвеска (2). Для этого случая выберите **Непрозрачная накладка** у `mat3` и
`mat4`, а `mat5`, `mat6`, `mat7` оставьте в **Авто**. Только palette/ushort-
продолжения того же исходного renderable могут быть material-less; объединять разные
renderables в один native draw/sort unit нельзя. Ранний importer полезно сохранял
material groups раздельно, но его Head-only weights и `FinalBlendOp = 4` были
неверны; текущий split сохраняет новые веса, target inverse-bind matrices и
16-костные palettes. Прозрачная подвеска `mat6` остаётся отдельным двухтреугольным
alpha overlay. За ней продолжает рисоваться opaque body branch, поэтому прозрачное
окно не должно открывать внутреннюю геометрию из-за превращения всего тела в Alpha.

Rigid multi-material packer сам создаёт one-bone `spSkin`, поэтому прежняя попытка
патчить его в `FinalBlendOp = 6`/`RS[8] = 2` не считается подтверждённым контрактом.
Привязанные alpha frames теперь блокируются до записи; opaque groups сохраняют
исходный material tuple target без изменений.

Exact tuple/pixel round-trip, strict writer verification и native loader подтверждают
сериализацию и загрузку. Они не подтверждают native blend, lighting, depth/sort или
визуальный паритет. WPF Viewer и Blender могут корректно показать atlas/UV/Alpha даже
у неверного alpha-run; кроме того, поворот камеры вокруг модели при фиксированном
world-light способен скрыть углозависимую ошибку материала. Итоговые порядок, цвет и
окклюзия независимых material-bearing ветвей требуют нового пользовательского теста
созданного SMO непосредственно в игре.

Skinned FBX использует тот же pipeline через Blender: Importer находит
`blender.exe` через ручной путь, `BLENDER_PATH`, `PATH`, реестр и стандартные
каталоги, преобразует во временный GLB только meshes с Armature modifier и сами
armatures, затем удаляет временный каталог. Это исключает случайные helper meshes
без skinning и не создаёт отдельный FBX writer с другими правилами костей.

```powershell
dotnet run --project tools/SmoImporter/SmoImporter.FormatTests -- `
  --skinned-glb target.smo donor.glb output.smo

dotnet run --project tools/SmoImporter/SmoImporter.FormatTests -- `
  --skinned-fbx target.smo donor.fbx output.smo
```

```powershell
dotnet run --project tools/SmoImporter/SmoImporter.FormatTests -- `
  --smo-to-smo target.smo donor.smo output.smo

dotnet run --project tools/SmoImporter/SmoImporter.FormatTests -- `
  --rigid-multitexture target.smo donor.obj output.smo
```

Для внешней OBJ/GLB-сцены с нулём или одной разрешённой texture group GUI сохраняет
старый single-atlas fallback. При двух и более группах автоматически используется
multi-material writer; специальная папка `matN` остаётся способом добавить также
последовательности кадров. Single-atlas путь
объединяет meshes и детерминированно разрезает triangle stream по настраиваемым
`MaxVertices`/`MaxTriangles`: каждый chunk получает локальную таблицу индексов,
а вершины на границах дублируются. Интерфейс сравнивает число chunks с количеством
существующих `spMeshData` slots исходного SMO.

Этот legacy **unskinned** OBJ/GLB whole-model режим:

- объединяет meshes OBJ/GLB в один rigid body-slot с новой topology;
- оставляет остальные существующие render slots валидными через degenerate triangle `(0,0,0)`;
- записывает всем вершинам rigid weight `(1,0,0,0)` на выбранный подтверждённый palette slot;
- принимает embedded GLB base-color либо внешний PNG/JPEG;
- безопасно заменяет только RGB существующего BGRA atlas, сохраняя исходный Alpha, marker, headers, offsets и длину SMO;
- никогда не перезаписывает исходный SMO.

Ограничение на изменение разрешения относится именно к legacy single-atlas
режиму: он не перестраивает texture object и меняет только RGB существующего
атласа. Новый multi-material packer выше создаёт собственные opaque BGRA branches,
fail-loud отклоняет alpha frames и может только увеличивать non-POT входы до следующей
степени двойки.
Произвольный repack существующих textures алгоритмом `SMOTextureTool` по-прежнему
не используется: старый путь создавал структурно читаемые файлы, вызывавшие вылет
оригинальной игры.

```powershell
dotnet run --project tools/SmoImporter/SmoImporter.FormatTests -- path/to/model.smo
```
