# Дорожная карта SmoImporter

Эта карта отделяет уже работающий импорт от направлений, которые ещё требуют
исследования. Главная цель — не максимальное число режимов, а воспроизводимый
цикл `preview → writer → native scene-ready → визуальная проверка в игре` без
повреждения исходных файлов.

## Базовая линия 0.6

Выпуск 0.6 фиксирует четыре пользовательских режима:

- нативный перенос визуального графа SMO → SMO;
- импорт уже подготовленной skinned-модели;
- адаптацию существующих donor weights;
- создание человеческих весов и отдельную статическую замену без костей.

Для режима создания весов базовой считается одна общая fitting-поза, защитные
плоскости плеч и Head, объёмы кистей, полный список компонентов с ручными
исключениями Head/Back и точный канонический preview перед подтверждением.
Автоматического извлечения Back в пользовательском пути нет.

## Этап 1 — стабилизация и воспроизводимость

Приоритет: высокий.

- сохранять и восстанавливать alignment, позу, настройки защиты и ручные
  назначения как переносимый preset с fingerprints входов;
- поддерживать последовательную тестовую матрицу разных SMO и доноров по всем
  режимам с лимитами времени и памяти;
- добавлять минимальные регрессии на каждую подтверждённую ошибку UI, writer-а
  или native loader-а;
- сделать диагностический пакет одного запуска: лог, параметры, fingerprints,
  writer summary и native-validation report без игровых данных;
- не считать loader acceptance визуальной проверкой: для персонажей отдельно
  проверять позу, анимацию, Head/Back-исключения и материалы непосредственно в
  игре.

## Этап 2 — качество человеческих весов

Приоритет: высокий после стабилизации 0.6.

- расширить корпус разных пропорций, одежды, волос, крыльев и раздельных
  mesh-компонентов без правил по именам моделей;
- улучшить автоматическую позу с объяснимым отчётом о найденных плечах, тазе,
  кистях, коленях и шее;
- добавить сравнение fitting preview и canonical `PreparedScene`, чтобы
  обнаруживать расхождения до writer-а;
- развить ручную привязку компонентов без разрезания геометрии и без возврата
  устаревшего автоматического Back;
- проверять несколько штатных SAN-анимаций после scene-ready, а не только
  статическую загрузку персонажа.

## Этап 3 — произвольные скелеты

Приоритет: средний; отдельный проектный этап.

- спроектировать явное сопоставление костей для животных, транспорта и других
  нечеловеческих ригов;
- отделить универсальный bone mapper от анатомических эвристик режима
  **Человек**;
- добавить ручное назначение root/deform/service-костей и проверку bind pose;
- не включать этот путь в production, пока неизвестная weighted-кость или
  неоднозначная hierarchy не блокируются fail-closed.

## Этап 4 — материалы и визуальная точность

Приоритет: средний.

- подтвердить в игре Alpha/blend/depth-sort для волос, лица и полупрозрачных
  накладок;
- исследовать material controllers, culling и остальные runtime-состояния,
  которые не доказываются строгим parse/decode;
- добавить эталонные игровые снимки только как локальный opt-in тест без
  публикации игровых ресурсов;
- расширять texture layouts только после round-trip и native-проверки каждого
  нового представления.

## Этап 5 — удобство и пакетные операции

Приоритет: низкий до завершения этапов 1–2.

- пошаговый экран проекта с возобновлением прерванной работы;
- очередь последовательных импортов с отдельным memory/time budget на задачу;
- отчёт о различиях между входом, preview и записанным SMO;
- пакетный режим разрешать только поверх тех же production writers и проверок,
  что используются единичным GUI-импортом.

## Ворота следующего релиза

Новый пользовательский релиз допустим, когда одновременно выполнены:

1. Debug и Release собираются без ошибок.
2. Быстрые regressions и production writer-пары проходят последовательно.
3. Входные файлы остаются неизменными, output проходит повторный strict decode.
4. Для изменённых персонажных путей есть contextual native `scene-ready`.
5. Несколько разных моделей проверены в игре визуально и в движении.
6. README, changelog и release notes описывают только фактически доступный UI.

SmoLVLcreator развивается отдельно. Его исходники могут использовать общие
проверенные Core-компоненты, но новый релиз редактора уровней не должен следовать
за релизом Importer автоматически: он требует собственной матрицы сохранения,
коллизий и игровых уровней.
