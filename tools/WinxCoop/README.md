# WinxCoop

Экспериментальный кооперативный мод для оригинальной PC-версии Winx Club.
Цель первого прототипа: два компьютера в одной локальной сети, на каждом
своя управляемая Блум и видимая удалённая Блум в том же уровне.

Здесь находятся сетевая библиотека, системный TCP transport для Windows,
лаунчер лобби, экспериментальный x86 адаптер и диагностические программы.
Объединение лаунчера с игровой симуляцией ещё не завершено; сетевой
кооператив пока не принят. Текущие границы — в [руководстве прототипа](docs/prototype-runtime.md).

## Сетевая библиотека и проверки

`src/Networking` содержит собственные `SessionCore`, `TcpPacketFramer`
и `WindowsTcpTransport`.
Они используют общий восстановленный Packet/MemoryStream codec. Coordinator
обеспечивает подключение, ожидание серверного разрешения, обмен, heartbeat
и завершение; Framer сохраняет неполные TCP packets. Оригинальные Worker,
StateCtrl и неизвестный DGE bootstrap в этом пути не используются.
Причины замены и границы описаны в [контракте сессии](../../docs/engine/architecture/network-session.md).

На Windows с Visual Studio C++ Build Tools, Windows SDK и CMake:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools/WinxCoop/Build-NetworkChecks.ps1
```

Команда собирает `WinxCoopNetworkProbe.exe` и проверяет два координатора на
byte streams, framing, игровой протокол, а также затронутые Manager/Flow suites общего движка.
Игра и игровые ресурсы для этих проверок не требуются. Реальные sockets
проверяются отдельным [межпроцессным сценарием](docs/transport.md).

Для проверки игровой песочницы есть отдельный [диагностический helper XP](docs/xp-game-probe.md).
Он проверяет системный D3D9, запускает исходный игровой EXE и восстанавливает
временный `MediaPath` в реестре гостя. Работу транспорта и пригодность VM для
графики нужно принимать отдельно.

Диагностика создания второй модели описана в [руководстве ActorProbe](docs/actor-probe.md).

## Первый прототип

- Отдельная программа создаёт лобби, ищет лобби в LAN и подключается по
  введённому адресу и порту. В сеансе ровно два участника.
- Каждый игрок управляет своей Блум обычным игровым вводом. Удалённая Блум
  отображает движение и необходимые состояния анимации другого участника.
- Сервер запускает прохождение и выбирает уровень. Подключившийся клиент
  ждёт команды сервера, затем присоединяется к его текущему уровню.
- После загрузки оба играют. Переход в следующий уровень может активировать
  только сервер; персонаж клиента не запускает этот триггер. Сервер задаёт
  переход обеим сторонам, на время загрузки включается ожидание.
- При выходе участника удалённый персонаж корректно удаляется. Повторное
  подключение не оставляет дубликаты.

Общая синхронизация боя, врагов, инвентаря, квестов и сохранений выходит за
пределы первого прототипа. Приёмочная сцена должна позволять проверять
передвижение без зависимости от этих систем.

## Оригинальная игра и сетевой стек

Целевая схема сохраняет исходные EXE и ресурсы игры. Отдельной программе
понадобится небольшой адаптер внутри игрового процесса: создание удалённого
персонажа, применение его состояния и контроль смены сцены требуют доступа
к игровому циклу. Экспериментальный адаптер загружается только в собственный
дочерний процесс проверенной версии игры; для опытов нужны отдельная копия
игры и отдельное состояние сохранений.

Основа исследования — существующий [сетевой стек Sparkplug](../../docs/engine/architecture/network-family.md)
и библиотека `SparkNetwork`, а также общие исходники `Winx/`.
Сокеты `spDXNetwork` используют WinSock TCP/UDP. Наличие восстановленных
операций ещё не подтверждает LAN-игру: Peer/Server и защищённые операции
менеджера восстанавливаются и проверяются отдельно. Подключение менеджера
зависит от службы, названной в диагностике DGE. Её конфигурация и игровой путь
использования сети остаются предметом исследования.

Найденные связи PC-цепочки, пакеты, состояния, владение и неизвестные
зависимости сведены в [контракт сессии](../../docs/engine/architecture/network-session.md).
Выбранный самостоятельный путь не зависит от неустановленных настроек DGE
или игровых получателей уведомлений. Системный adapter использует Winsock
напрямую; обмен тестовыми пакетами ещё не создаёт игрового персонажа.
Перед игровым прототипом нужно изучить его создание и жизненный цикл.

Подробнее: [контракты и устройство прототипа](docs/design.md),
[общие правила разработки](../../CONTRIBUTING.md).
