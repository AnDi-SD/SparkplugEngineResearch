# Устройство первого прототипа WinxCoop

Документ разделяет принятую конструкцию P и следующую реализацию общего игрока.
Описание кода и проектные требования не заменяют проверку двух настоящих игр.

P проверен на физическом ПК и Windows 7 VM в фиксированной Alfea 28:
серверный запуск, две управляемые локальные Блум с удалённым отображением,
переподключение и завершение с подтверждённой очисткой.
Условия запуска описаны в [руководстве прототипа](prototype-runtime.md).

## Управление сервером

Сервер — ведущий ПК с оригинальной игрой. Он запускает прохождение, задаёт
текущий уровень и управляет жизненным циклом сеанса. Клиент подключается,
ожидает команды сервера и загружает назначенный уровень. Подключение к уже
запущенному сервером уровню входит в минимальный сценарий. Когда обе стороны
готовы, каждый игрок управляет своей Блум.

| Решение | Этап P | Следующая реализация |
| --- | --- | --- |
| Запуск игры | Сервер запускает свою копию; клиент ждёт назначения готовой сцены | Сохраняется управление сервером |
| Текущее поколение и Ready/Resume | Сервер назначает только Alfea 28 / entry 0 после фактической готовности | Сервер назначает новое поколение при переходе |
| Ввод и физика своей Блум | Штатно выполняются на соответствующем ПК; ввод по сети не пересылается | Клиентский ввод исполняет отдельное серверное тело через проверенный штатный контроллер |
| Принятое состояние удалённого персонажа | Сервер принимает или отклоняет наблюдения клиента, публикует принятые позы | Потребует согласования с жизненным циклом новой сцены |
| Выход на следующий уровень | Переход не реализован; native-поколение фиксированной сцены завершается | Только персонаж сервера; клиентский триггер подавляется до побочных эффектов |

В P клиент сообщает готовность и наблюдаемую позу своей штатной Блум, но не
назначает уровень и не публикует принятое состояние. Его подтверждённая поза
не записывается поверх собственного локального персонажа. Серверная физика
персонажа клиента, предсказание и коррекция локального движения не используются.
Синхронизация общего мира, квестов и сохранений не заявляется.

Подавление клиентского триггера, согласованный переход и ожидание обеих сторон
относятся к следующей реализации и требуют отдельного игрового hook. Native `spNetworkServer`
остаётся частью исходного сетевого стека; серверное управление WinxCoop
реализуется собственным протоколом поверх общего Packet codec.

## Общий игрок с двумя телами

Целевое устройство сохраняет один логический профиль, HP, магию, инвентарь,
прогресс и сохранение. На сервере действуют два отдельных тела с собственными
командами и анимациями. Попадание по любому телу изменяет общий ресурс;
подобранный предмет и награда применяются один раз штатным игровым путём.
Сервер считает врагов, урон, взаимодействия и сюжет, разрешает переходы и
публикует результат. Клиент передаёт действия и поддерживает своё отображение,
камеру и анимации без повторного применения игровых последствий.

Сначала проверяются отдельный native Character/MoveCtrl и реальные источники
обновления клиента, затем штатные операции damage/pickup и связь с профилем.
После этого ввод и состояние мира включаются в сетевой протокол, а переходы,
смерть, checkpoint и сохранения согласовываются по ведущему. Один предмет,
враг и уровень образуют начальный проверочный сценарий. Область реализации
может расширяться сразу, если обнаружен пригодный штатный механизм с меньшей
стоимостью внедрения, включая более полный кооператив.

Это направление разработки, а не уже принятые возможности P. Если понадобится
сохранить локальное движение P как временное упрощение, такое решение должно
быть явно отражено в контракте и проверке. Пропуск transform traversal или
передача одной позы не доказывают серверную симуляцию мира.

## Состав

| Часть | Ответственность |
| --- | --- |
| Внешняя программа | LAN-лобби, ручной адрес, два места; на сервере запуск прохождения, на клиенте подключение и ожидание команд |
| Адаптер игрового процесса, x86 | Проверка версии игры, выполнение команд на игровом потоке, наблюдение локального персонажа, жизненный цикл удалённого персонажа и сцены |
| Сетевой сеанс | SessionCore/TcpPacketFramer поверх общего Packet codec и WindowsTcpTransport поверх Winsock; V3 связывает соединение, назначение фиксированной сцены, готовность, наблюдения и решения сервера |
| Общие Sparkplug/Winx | Восстановленные операции; единственное место общей игровой логики |

Внешняя программа и игровой адаптер обмениваются ограниченными сообщениями
через локальный IPC. Указатели игры не передаются по IPC или сети. Работа
сетевого потока заканчивается очередью команд; изменение сцены и персонажей
выполняется на установленной безопасной фазе игрового потока.

Оригинальные EXE и ресурсы сохраняются. Рабочую версию адаптера допускают
только для явно распознанного образа: архитектура, контрольная сумма и
проверенные сигнатуры функций. Сохранения, конфигурация и журналы опытов
принадлежат отдельному тестовому экземпляру.

Текущий UI — Win32, TCP-порт по умолчанию 27025, LAN discovery — UDP 27026.
GameProcessClient и GameHost используют IPC3, имеющий одного владельца команд;
native-операции исполняются на проверенной границе оригинального игрового потока.

## Использование существующей сети

Изучаемая цепочка:

```text
Winx и уведомления движка
  -> spNetworkManager + spNetworkStateCtrl
  -> spNetworkServer / spNetworkPeer / spNetworkMatchmaking
  -> spNetworkPacket + spSocketStream
  -> spNetwork / spDXNetwork
  -> WinSock, потоки, блокировки и время
```

Это карта областей исследования; конкретные направления вызовов, владение и
потоки должны быть установлены для каждой операции. Диагностические названия
DGE и Matchmaking не доказывают наличие готового однорангового LAN-лобби.

В `SparkNetwork` восстанавливаются собственные операции network, DX network,
packet, socket stream, manager, state controller, matchmaking, debug, peer
и server. Для каждой операции отдельно устанавливаются входы, владение и
ошибки. Host-интерфейсы описывают внешние зависимости и требуют системного
провайдера. Подробнее — [семейство сети](../../../docs/engine/architecture/network-family.md),
[менеджер](../../../docs/reference/classes/sp-network-manager.md),
[сокеты](../../../docs/reference/classes/sp-dx-network.md).

Для самостоятельной сессии выбран общий восстановленный Packet/MemoryStream
codec с собственным coordinator и framer. Известный native Manager зависит
от неустановленного DGE bootstrap, а Worker теряет TCP fragments. Выбранный
путь исключает эти зависимости и сохраняет оригинальные классы как эталон.
Точный handshake, владение, ошибки и границы совместимости —
[в контракте сессии](../../../docs/engine/architecture/network-session.md).
Системный transport adapter реализован по установленному byte-stream контракту;
его API и проверка описаны в [руководстве транспорта](transport.md).

Исходный пакет имеет 17-байтный little-endian заголовок и uint16-размер payload.
При этом native packet выделяет только 256 байт под payload, а его Read и
Write не проверяют эту границу. До установления ограничений callers нельзя считать
весь диапазон uint16 допустимым; совместимый прототип ограничивает payload
проверенной вместимостью и не передаёт произвольный размер в original Read.
TCP требует установленных правил сборки фрагментов, короткой отправки и
закрытия. Граница `spSocketStream` сама по себе не обеспечивает полную
доставку: её WriteData допускает короткую отправку как успех.
Исходный Server Worker также не хранит незавершённые пакеты между проходами
приёма; его поведение описано в [карточке Server](../../../docs/reference/classes/sp-network-server.md).
В WinxCoop это делает собственный TcpPacketFramer с сохранением фрагментов и
различением неполных данных, EOF и ошибки. Системный adapter должен отдельно
сохранить положительный receive prefix и остаток short write.
Игровые сообщения V3 используют канал данных type `2` и различают наблюдаемое
состояние и принятое сервером состояние. Данные
передаются собственной owned очередью; неизвестный native потребитель `0x1F`
для этого пути не требуется.

## Две Блум

На каждом компьютере остаётся один обычный локальный игрок и один удалённый
персонаж. Нельзя просто клонировать весь объект игрока: нужно установить
владение input controller, камеры, Bloom state machine, физики, registry и
animation bindings. Регистрация класса и успешная factory этого не доказывают.

Адаптер создаёт пассивную удалённую модель в сцене, применяет положение и
анимацию через установленные игровые операции и удаляет её с подтверждением.
Она не получает локальный ввод, камеру или собственный физический контроллер,
не становится текущим игроком и не выполняет его сюжетные триггеры.
Её отображение отделено от штатного локального персонажа.

Сетевой образ V3 содержит:

- идентификаторы сеанса, участника и персонажа;
- поколение уровня (`levelEpoch`) и порядковый номер состояния;
- позиция, ориентация и только необходимые состояния движения/анимации;
- счётчики наблюдения и публикации, а также точное подтверждение решения по
  наблюдению; эти значения не являются общим физическим временем.

Сервер является источником принятого состояния поз для репликации. Клиент
передаёт `ObservedState`, после чего сервер принимает либо отклоняет точный
элемент FIFO. Проверяются connection/session/epoch/entity, последовательность,
конечность чисел, ортонормальность и числовой предел native-сцены. Эти проверки
не доказывают корректность физики, столкновений или отсутствие читов.
Получатель применяет состояния только к персонажам текущего поколения сцены.
Числа проверяются на допустимость; старые и повторные состояния отбрасываются.
Исходная частота для измерений — 20 обновлений в секунду, с дальнейшим подбором
по реальной задержке и плавности. Это начальная настройка, не измеренный результат.
Анимация использует существующие игровые bindings, без отдельного sampler.

## Лобби и подключение

Лобби рассчитано на ведущего и одного гостя. LAN-поиск возвращает название,
адрес подключения и занятость. Ручной `IPv4:port` доступен независимо от
результата обнаружения. Обнаруженное
лобби ещё не означает успешное подключение к игровому сеансу.

Перед стартом обе стороны согласуют совместимую версию игры/адаптера,
а сервер назначает идентификатор уровня и способ входа в него. Пока сервер
не запустил уровень, клиент ожидает назначение в лаунчере. Если сервер уже
играет, новому клиенту передаются текущие level/entry/epoch и необходимые
данные входа; разрешение играть выдаёт сервер после проверки готовности.
Для P фиксируется одна начальная ситуация:
level descriptor, entry и нужное состояние сценария/вариантов ресурсов.
Одинаковых EXE и level ID недостаточно для доказательства совместимости сцен.
TCP-порт настраивается, UDP discovery использует 27026;
второе лобби на той же машине не должно незаметно делить чужой endpoint.
Обмен не передаёт ресурсы игры. Поведение при несовместимости, полном лобби,
недоступном адресе и потере участника должно быть видно в программе.

## Переход уровня и ожидание

Это часть следующей реализации; в текущем P данные действия не реализованы.
Только сервер должен инициировать переход. Клиентский персонаж не должен
активировать выход, а полученные от клиента команды смены уровня не должны
исполняться. Требуемая последовательность:

1. Безопасный игровой hook разрешает выход только серверному игроку и замечает
   его до разрушения сцены. Клиентский выход останавливается до локальной загрузки.
2. Сервер назначает следующее поколение и сообщает обеим сторонам точный
   уровень и способ входа. Повторные/устаревшие команды не запускают ещё
   одну загрузку; клиент не может назначить новое поколение.
3. Обе стороны прекращают передачу состояния старой сцены, удаляют её
   удалённого персонажа и входят в ожидание. Сетевой pump продолжает работать.
   До Resume локальный ввод/симуляция ограничены так, чтобы игрок не двигался
   и не запускал новые выходы. Безопасный механизм такого ожидания ещё нужно
   установить; одной остановки snapshot для этого недостаточно.
4. Каждая сторона выполняет штатную загрузку и сообщает готовность только
   после появления сцены, локального персонажа и пригодной точки входа.
5. После двух подтверждений ведущий разрешает игру. Удалённые персонажи
   создаются заново; принимаются состояния только нового поколения.

Timeout, отказ загрузки или отключение оставляют сеанс в понятном состоянии
ожидания/разрыва. При потере ведущего прототип завершает сеанс без миграции
хоста. Возврат к одиночной игре допускается только после проверки корректного
удаления адаптером своих объектов. Сюжетные переменные и сохранения не
объединяются; способ штатной загрузки одинакового назначения нужно доказать.

Если безопасный перехват выхода до unload не найден, поведение ожидания
нельзя считать реализованным. Нельзя переносить указатель персонажа через
загрузку или принимать состояние старой сцены в новую.

## Последовательность проверки

| Ступень | Что должна доказать |
| --- | --- |
| Native-исследование | Полный найденный PC network call graph, конфигурация, DGE, peer/server, callbacks, потоки, ownership, ошибки и потребители Winx |
| Настоящие сокеты без игры | Два процесса: создание сессии, подключение, двусторонние данные, framing, close, timeout и обрыв |
| Один игровой процесс | Наблюдение локального игрока; отдельный удалённый персонаж, input/camera isolation, движение, анимация и удаление |
| Два игровых процесса | Независимые сохранения и ввод; обе Блум видны на каждой стороне; изоляция single-instance ограничений |
| Изолированные ОС | Проверенные графика, ввод, адресация и доступность портов; ручное соединение, затем LAN discovery |
| Два ПК либо физический ПК + VM | P: движение, отображение и disconnect/reconnect; следующая реализация: общий мир/ресурсы, переход сервера, запрет клиентского выхода и согласованное ожидание |

Ограниченный instruction harness полезен для операций оригинального кода.
Он не заменяет две работающие игры с ОС и графикой. Готовность VM или иной
песочницы подтверждается отдельным запуском обычной игры.

Приёмка P: 10 минут совместного передвижения в Alfea 28, подключение к уже
готовому серверу, отдельные локальные игроки, корректный обрыв и повторное
подключение без лишней Блум. Нужны журналы обеих сторон и визуальное
подтверждение на обоих ПК. Приёмка следующей реализации добавляет переход сервера, попытку клиента
активировать выход без смены уровня и побочных эффектов, согласованное ожидание
при задержке загрузки и блокировку повторных выходов до Resume.
Сборка и обмен тестовыми пакетами сами по себе не являются приёмкой мода.
