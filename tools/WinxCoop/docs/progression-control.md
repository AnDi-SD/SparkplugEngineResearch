# Управление переходом между сценами

Отдельный протокол и детерминированная машина состояний E6
согласуют решение сервера, завершение старой сцены и допуск нового ввода.
Native-адаптеры предоставляют ограниченные операции контроля сохранений,
известного перехода и срока жизни владельцев. В двух настоящих игровых
процессах проверены повторный вход Alfea28, серверная запись и загрузка
сохранения, пауза Diary61 и сюжетный Game Over Gardenia3 с восстановлением
из серверного checkpoint Alfea28. После смены сцены создаются новые
Input5/WCS1 каналы; Resume следует за фактическим native ACK клиента.
Диагностический владелец перезапускает обе игры при смене поколения.
Это конечный объём на одном физическом ПК через loopback TCP;
после повторного входа и восстановления вручную проверены модели, движение,
прыжок и камера. Полное совместное прохождение требует отдельной приёмки.
Межмашинный путь требует удалённого владельца Guest и проверки совместимости
runtime с выбранной гостевой ОС; эта интеграция относится к E7.
Лаунчер P продолжает использовать V3/IPC3; новый путь ещё не встроен в него.

Протокол использует существующие SessionCore, Packet/MemoryStream и TCP
transport. Он дополняет [диагностическую доставку ввода IPC5](shared-resources-probe.md) и
[WCS1 состояния мира](world-state.md). Смена поколения сцены требует нового
комплекта их объектов и каналов.

## Решение и барьер

Только Host начинает операцию. Решение содержит монотонный operation ID,
прежние и следующие levelEpoch/generation, причину, назначенные level/entry
и digest дескриптора локации. Оба счётчика поколения увеличиваются на1;
переполнение отклоняется. Предусмотрены причины смены локации, повторной
загрузки, respawn, checkpoint и cutscene. Их наличие в сообщении задаёт
координацию; соответствующие игровые операции требуют отдельного native допуска.

| Сообщение | Отправитель | Условие и результат |
| --- | --- | --- |
| Prepare | Host | Начинает одну неизменяемую операцию; новый игровой ввод удерживается барьером |
| Retired | Guest | Подтверждает полное завершение старого native scope; Host также предоставляет собственное локальное подтверждение |
| Load | Host | Допускается после обоих Retired и настоящего нового входа Host; содержит новую identity каналов и digest seed/witness |
| Loaded | Guest | Требует согласованного нового native entry, полного применённого снимка и свежей нейтральной границы ввода |
| Resume | Host | Следует за точным Loaded; завершает барьер для нового поколения |
| Abort | Любая сторона | Завершает соответствующую операцию с явной причиной ошибки |

Host может завершать свой исходный переход, пока Guest освобождает прежнюю
сцену. Выдача нового игрового ввода ожидает барьера. Ожидание peer не добавляет
неограниченную остановку внутри исходного Exit или native cleanup batch.

Retired требует всех девяти подтверждений: original Exit вернулся; input и
world каналы retired; native bindings завершены; заимствованные узлы и patches
восстановлены; собственных native объектов и pending вызовов/применений нет;
ресурсы освобождены на последующем World. Начало Exit и завершение вызванного
перед ним cleanup batch учитываются отдельно от возврата исходного Exit.

Получатель Load выдаёт разрешение на native загрузку ровно один раз.
Guest entry должен совпасть с назначенными сценой, дескриптором, каналами и
digest seed/witness. Local entry ordinal каждой игры может различаться;
значение Host в seed сохраняет собственную семантику. Loaded дополнительно
связывается с ненулевыми revision/native tick полного применённого снимка.
Tick служит порядком native наблюдений, без сравнения часов разных ПК.

На Host очередь Resume сохраняет input=false до принятия полного сообщения
транспортом и CommitOutbound. Guest ожидает получения соответствующего Resume.
Владельцу адаптера принадлежит фактическое применение этого допуска к игре.

## Данные и срок жизни протокола

Версия протокола1, сообщение фиксированного размера244 байта. Прежний предел
Packet payload256 байт сохраняется; padded C++ structs по сети не копируются.

| Поля | Байт |
| --- | --- |
| Версия, kind, connection session/scenario/token | 32 |
| Operation, прежнее/новое поколение, причина, level/entry и digest дескриптора | 68 |
| Новые common session/input token/world token и четыре mapping nonce | 56 |
| Digest seed и witness | 64 |
| Applied revision и native tick | 16 |
| Маска retirement и terminal reason | 8 |

Prepare и Retired не передают будущий payload загрузки. Load содержит digest,
а сами seed/witness предоставляет владелец нового scene scope. Значения
каналов и nonce непрозрачны для игры; указателей native объектов в сообщении
нет. Неиспользуемые поля каждого kind должны быть нулевыми. Неизвестные kind,
размер, версия, неполный retirement или нулевой native ACK отклоняются.

Для нового поколения создаются новые Input5/WCS1 session, tokens и mapping
nonce. Проверяются отличия от текущего поколения и взаимная уникальность
четырёх новых nonce. Platform owner дополнительно проверяет существование,
PID/creation и срок жизни настоящих mappings и процессов.

Точный повтор команды идемпотентен: он не запускает повторную загрузку и не
увеличивает очередь. Замена содержания того же активного operation ID закрывает
сеанс. Устаревшие команды завершённых операций не предоставляют полномочий
новому поколению. Очередь ограничена четырьмя сообщениями; Peek не потребляет
запись, Commit вызывается после принятия полного application frame транспортом.

Владелец передаёт монотонное время до каждого приёма сообщения, native receipt
и commit. Общий deadline перехода задаётся в пределах100–600000мс; повтор
сообщения его не продлевает. Откат часов, истечение срока и disconnect
терминальны. Возврат позднего ACK не открывает закрытую попытку. Freshness
ввода IPC5 и actor leases сохраняют свои отдельные правила.

Начальное Running передаётся явно как trusted bootstrap. Native receipts
также являются утверждениями вызывающего владельца: core проверяет полноту,
идентичность и порядок, но сам не читает игру. Fixture, TCP-доставка и совпадение
digest не заменяют наблюдение настоящих native вызовов и их последствий.

## Native scopes и текущий допуск

Текущий внешний диагностический владелец использует явный перезапуск обоих
игровых процессов. Сначала Host выполняет исходный переход, завершает старый
scope и наблюдает настоящий вход назначения: LoadLevel, placement и первый
World. Seed и witness копируются из этого входа. После завершения прежних
процессов новые Host и Guest получают новые IPC session, токены и nonce.
Оба проходят native вход; полный снимок применяется клиентом до Loaded/Resume.
Таким образом, завершение старой игры и готовность новой подтверждаются
разными наблюдениями. Бесшовного перехода этот путь не предоставляет.

Перед переходом Guest входит в отдельную подготовленную фазу Waiting.
Она удерживает mappings и native-политику подавления симуляции, но прекращает
обычное чтение прежних снимков. Последующий Retire подтверждает фактическую
очистку. Только ожидаемое закрытие уже подготовленного peer допускается на
этой границе; ошибки identity, последовательности и lease не превращаются
в успешное завершение. Оставшиеся в TCP фрагменты прежнего снимка обрабатываются
по ограниченному правилу [WCS1](world-state.md).

Process owner может сохранять процесс игры и общие observation sites, меняя
scene scope после его завершения. Для этого реализован отдельный entry router:
семь original sites устанавливаются один раз, а новые immutable seed/witness
принадлежат новым scope. Process entry ordinal ограничен; новый scope не
переустанавливает старые hooks и не сбрасывает порядковый номер. Незавершённый
original Load/Placement нельзя скрыть через retirement.

Отдельная граница NativeResourcesRetired требует actual Exit-return witness и
освобождения на позднем World. Она допускает уже существующую следующую сцену
и повторное использование адресов allocator. Старые E5 проверки Menu30s и
двух MainMenu Worlds сохраняют прежние критерии; они относятся к завершению
конечного диагностического режима. Новая граница ресурсов не подставляет
фиктивные menu-счётчики и сама не подтверждает вход следующего уровня.

В ограниченных игровых проверках подтверждены process-local выбор MediaPath,
серверное выполнение штатного save writer и подавление этого writer на Guest.
Process-local путь использует настоящий успешный системный запрос и меняет
только временный результат внутри принадлежащего игре процесса; значение
реестра не переписывается. Сохранения проверяются на изолированных игровых
копиях. Suppression writer не означает подавления всей предшествующей работы
с профилем, settings writers или других способов записи.

Известный native ChangeLevel имеет отдельную политику: Host сохраняет
исходную проверку основного персонажа, Guest пропускает действие до его
побочных эффектов. Допуск ограничен установленным типом команды и сценовым
владельцем. Он не распространяется автоматически на все trigger families.
Наблюдение запроса Flow учитывает ещё не исполненное решение о переходе.

В Alfea28 проверен полный цикл двух игр: штатный захват состояния и запись
Saved00 на Host, загрузка неизменного файла исходным LoadSave, настоящий
возврат Exit и новый LoadLevel/placement/первый World. Перезапущенный Host
сначала выполняет исходную загрузку сохранения и только затем создаёт второе
тело. Его local entry ordinal равен2, у нового Guest —1; серверный ordinal
в seed/witness сохраняется. Новый полный снимок и native ACK подтверждают
профиль и HP обоих тел перед Resume.

Сохранение целиком передаётся исходному loader. Выбранные Profile411/Seed448
не заменяют полный SavedState или checkpoint. Проверенный файл имеет layout143,
349 байт и пустое имя; побайтовая сохранность проверяется отдельно от смыслов
его полей. В этом случае HP/max HP равны6/6. Исходная загрузка восстанавливает
текущее HP из сохранённого максимума; произвольное ненулевое сохранённое HP
не квалифицировано. Карта формата — в [описании WXS](../../../docs/formats/wxs-save.md).

Сюжетный сценарий Gardenia3 начинает серверную симуляцию после настоящего
полного native ACK клиента: на время первого подключения используются штатные
Pause/Start игрового таймера. Затем проверены общее смертельное поражение двух
тел, исходные Playing Exit и Game Over, возврат зарегистрированной командой
в главное меню и восстановление принятого серверного checkpoint Alfea28.
После этого обе игры перезапускаются и проходят новый барьер ACK/Resume.
Этот сценарий проверяет игрока, профиль и исход поражения; представление
Ghoulie, его атак и наград на клиенте в него не входит.
Game Over показывается на Host; Guest ожидает серверного восстановления.

Пауза Diary61 проверена в обеих играх через исходные push/pop и парные
Entry/Exit с сохранением сцены, seed/witness и WCS epoch. После возврата
требуются новые реальные InputRET, нейтральное подтверждение ввода и полный
неприостановленный снимок с native ACK. Эта проверка не распространяет допуск
на все дневниковые страницы, гардероб и произвольные cinematic-состояния.
В проверочном запуске дневник виден с чёрным фоном: этот косметический дефект
остаётся открытым, его причина не установлена.

Потеря фокуса Guest сохраняет исходное отключение ввода. В конечном
Alfea-профиле представление продолжает анимацию, но свежие клиентские команды
не публикуются. Переход, требующий нового нейтрального native ACK, может ждать
возврата фокуса и завершиться по deadline. Подтверждение старой команды или
локальная запись нейтральных полей не заменяют этот ACK.

Клиентский канал пока не передаёт приседание и движение в приседе.
Медленная ходьба отдельным клиентским режимом не проверена; Moving semantic
не различает её с бегом. Эти ограничения не отключают штатные возможности
основного персонажа Host.

Отсутствующее Retired клиента завершает попытку по deadline с input=false
и без завершённого перехода. Игровая очистка и закрытие принадлежащих попытке
процессов проверяются также при этом исходе. Полное прохождение всех локаций,
естественные переходы всех trigger families и все варианты checkpoint пока
не квалифицированы.
Границы выбранных профилей и входных решений описаны в
[карте состояния уровня](level-entry-state.md).
