# Экспериментальный игровой прототип

Текущий код связывает лаунчер, GameplayProtocol V3 и native IPC3. Каждый ПК
сохраняет штатный ввод и локальную физику своей Блум. Сервер запускает сеанс,
назначает готовую сцену и принимает либо отклоняет наблюдения клиента.
Удалённая модель отображает принятое состояние другого игрока.

Этап P проверен в ограниченной конфигурации: физический ПК и Windows 7 VM,
Alfea 28 / объявленный entry 0, отдельные локальные игроки и удалённые модели
со штатными волосами и цветом. Проверены движение, повороты, прыжки,
переподключение к продолжающейся серверной игре, непрерывный сеанс свыше
десяти минут и завершение с подтверждённым удалением моделей. Программы и
журналы находились на локальных дисках соответствующих ОС.

## Сборка

Сетевые и игровые контрактные проверки:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools/WinxCoop/Build-NetworkChecks.ps1 -Configuration Release
```

Для сборки экспериментальных программ под оригинальную x86 игру:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools/WinxCoop/Build-NetworkChecks.ps1 -Architecture x86 -Configuration Release -IncludePrototype
```

Результат по умолчанию — `artifacts/WinxCoop/network-checks/<architecture>/<configuration>`.
`-BuildDirectory` задаёт другой каталог. Используется один compiler worker;
`-BuildWorkers` меняют с учётом доступной памяти. Нужны MSVC x86/x64,
Windows SDK, CMake и Ninja из Visual Studio Build Tools. Проверки не требуют
игровых ресурсов. Для игровых опытов нужна подготовленная отдельная копия игры.

## Файлы и настройки

На каждом ПК нужна собственная [подготовленная копия игры](preparation.md),
с отдельным Saved. Для приёмки «физический ПК + VM» копия в VM также должна
быть независимой. EXE и игровые ресурсы не входят в комплект WinxCoop.

Программы и `caseRoot` размещайте на локальном диске соответствующей ОС.
Для VM используйте диск гостя, например `C:\WinxCoop\Cases`, и копируйте
готовые отчёты через общую папку после завершения. GameHost синхронно пишет
журнал в своём цикле обработки отладочных событий; задержка записи может
задержать продолжение игрового потока.

Рядом с лаунчером разместите программы из одного актуального x86 набора:

```text
WinxCoopLauncher.exe
WinxCoop.NativeAdapter.dll
WinxCoopGameHost.exe
XpGameProbe.exe
WinxCoopLauncher.ini
PreparedGame\       (или другой gameRoot)
Cases\              (создаётся при необходимости)
```

Имена и пути можно изменить в соседнем `WinxCoopLauncher.ini`:

```ini
[Paths]
gameRoot=PreparedGame
media=PreparedGame\Media
adapter=WinxCoop.NativeAdapter.dll
helper=WinxCoopGameHost.exe
outer=XpGameProbe.exe
caseRoot=Cases
[Prototype]
seconds=900
```

Это значения по умолчанию. Относительные пути разрешаются от каталога
лаунчера; после разрешения нужны короткие абсолютные ASCII-пути. Профиль
читает `gameRoot\WinxClub.exe` и `gameRoot\winx.ini`; последний должен уже
содержать единственный sectionless `startLevel=28`. Сам лаунчер INI не меняет.

CLI переопределяет параметры INI:

| Аргумент | Значение |
| --- | --- |
| `--game-root PATH` | Отдельный каталог игры |
| `--media PATH` | Каталог Media |
| `--adapter PATH` | DLL адаптера |
| `--helper PATH` | WinxCoopGameHost.exe |
| `--outer PATH` | XpGameProbe.exe |
| `--case-root PATH` | Каталог новых игровых случаев и отчётов |
| `--seconds N` | 5–3600 секунд; по умолчанию 900 |
| `--port N` | TCP-порт, по умолчанию 27025 |
| `--report NEW_PATH` | Явный новый путь отчёта лаунчера |

`--game-root` также выбирает `PATH\Media`, если `--media` не указан явно.
Например, из каталога программ:

```powershell
.\WinxCoopLauncher.exe --game-root D:\WinxCoop\PreparedGame --seconds 900
```

Роль и адрес гостя выбираются в окне; CLI `--host`/`--join` отсутствуют.
Пути и профиль читаются при запуске. Чтобы заменить DLL или изменить пути,
завершите лаунчер с подтверждённой очисткой и запустите его заново.

Лимит включает загрузку и ожидание гостя. Внутренний предел helper равен
`max(30, seconds)`; лаунчер начинает штатную очистку через
`min(seconds, helperLimit-15)` секунд, отсчитываемых перед запуском фасада.
Поэтому при значении 900 удаление модели и остановка игры начинаются примерно
через 885 секунд. Лаунчер ждёт подтверждение native-удаления, выхода процесса и
восстановления `MediaPath`; резервный watchdog остаётся отдельной границей.
Фасад передаёт outer-helper предел `(helperLimit+35)*1000` мс:
для 900 секунд это `935000`. Нужен свежий XpGameProbe с пределом `3700000` мс;
старый бинарник с пределом `900000` не подходит даже для значений по умолчанию.
Диагностический AdapterProbe по-прежнему имеет отдельный предел 5–600 секунд.

## Два настоящих экземпляра

`WinxCoopLauncher.exe` создаёт лобби на TCP-порту 27025, ищет серверы через
UDP-порт 27026 и подключается по адресу IPv4:порт. Двойной щелчок по найденной
записи выбирает сервер и подключается. После выхода можно подключиться снова.
Допускается один гость. Discovery показывает доступность лобби; окончательное
решение о приёме принимает TCP transport. Оба ПК должны иметь одинаковые EXE,
DLL адаптера и совместимый подготовленный Media. Профиль рассчитывает полный
SHA256 EXE/DLL и детерминированный отпечаток Media, исключая Saved и журналы.
EXE/DLL удерживаются открытыми для чтения до завершения лаунчера.

1. На обоих ПК запустите лаунчер и дождитесь успешной проверки профиля.
2. На сервере нажмите «Создать лобби», затем «Начать игру». Гость для этого
   не нужен. Дождитесь фактической готовности Alfea 28.
3. На клиенте нажмите «Найти в LAN» и дважды щёлкните по серверу либо введите
   IPv4 сервера с портом и нажмите «Подключиться». Для VM нужен адрес физического
   ПК в общей сети; `127.0.0.1` в VM указывает на саму VM.
4. До назначения сервером готового уровня клиентская игра не запускается.
   После Welcome запускается обычный EXE клиента. Когда обе стороны сообщат
   готовность уровня, сервер разрешает обмен состояниями через Resume.
5. Проверьте обычное управление и удалённую Блум в обеих играх. Для выхода
   клиента используйте «Покинуть лобби»; серверная игра может остаться открытой.
   Повторное подключение ожидает удаления прежней модели с ACK.
6. Для ручного завершения закройте лаунчер. При достижении мягкого лимита
   лаунчер также начинает очистку: ждёт удаления модели, выхода игрового
   процесса и отчёта о восстановлении MediaPath. Окно остаётся открытым до
   подтверждения этих операций; результат сохраняется в отчётах.

В фиксированном профиле штатный старт сцены задаётся sectionless
`startLevel=28`. Фасад запускает EXE и наблюдает фактическую готовность;
отдельной команды навигации по титульному экрану/меню здесь нет. Если уровень
не стал готовым, один запуск процесса ещё не завершил барьер загрузки.

После успешной проверки профиля отчёт лаунчера создаётся автоматически как
`Cases\launcher-PID-TIME.json`; `--report` задаёт другой новый путь. Отдельные
`Cases\P-PID-GENERATION` содержат отчёты GameHost и outer. В отчётах есть счётчики
кадров, наблюдений, серверных решений, native ACK, задержек и фактической очистки.
Завершение процесса с кодом 0 само по себе не доказывает готовность уровня.

## Игровой протокол

`GameplayProtocol` V3 использует общий Packet codec и канал application messages.
Он связывает соединение с session/epoch, проверяет совместимость EXE, адаптера
и заданной сцены, ожидает готовность обеих сторон и разрешение сервера.
Клиент не назначает уровень и не публикует принятое состояние напрямую.

Клиент передаёт `ObservedState` своей штатной локальной Блум: позицию, базис,
оценённую по локальному времени скорость и состояние анимации. Хост решает
каждый элемент FIFO и только затем публикует принятое состояние. При паузе
хоста наблюдение отклоняется как busy; это не завершает живую сцену. Проверка
чисел и предела abs(позиция/скорость) ≤ 1e6 служит защите native-команд,
а не проверке столкновений или античиту.

Принятое состояние клиента отображается сервером; принятое состояние сервера —
клиентом. Подтверждение собственной Блум клиента используется только как ACK,
не заменяя её локальную позу. Legacy V2 `SubmitInput` в V3 неактивен; пересылки
ввода или симуляции чужой физики на хосте в P нет.

Начальная частота выборки — около 20 Гц. Native-адаптер сглаживает только
удалённую модель за 75 мс, сохраняя локально проверенный масштаб. Это параметры
реализации, а не измеренный результат плавности. Уже отправленные наблюдения
не заменяются; при backpressure откладывается следующая выборка. Native-команда
неизменна до точного ACK; объединяются только ещё не опубликованные визуальные
состояния. Смена сетевого соединения не переиспользует старую сетевую generation.

По сети и IPC передаётся ориентация штатного корня персонажа. При отображении
адаптер добавляет исходный поворот модели вокруг Y на пол-оборота: для матриц
со строковыми векторами `displayR = diag(-1, 1, -1) * characterR`. Этот поворот
заменяет исключённый из копии `model_root_master` и применяется ко всему
wrapper с телом, скелетом и волосами. Позиция, масштаб и локальный персонаж
от этой поправки не меняются.

## Адаптер и диагностика

`WinxCoop.NativeAdapter.dll` с IPC3 предназначен только для проверенной оригинальной
x86 версии. Он подключается к главному игровому потоку и обменивается с внешней
программой версионированными данными без native pointers и handles. Проверяются
полный EXE, исходные/live инструкции, сцена и типизированные игровые связи.

`WinxCoopAdapterProbe.exe` запускает собственный экземпляр игры, загружает DLL,
проверяет восстановление контекста и ограничивает длительность опыта. Он не
подключается к уже работающей произвольной игре. Требуются абсолютные пути:
`--game GAME_EXE --adapter ADAPTER_DLL --report NEW_JSON --seconds 60`.
Это диагностический путь; сохранение регистров не заменяет проверку модели,
управления, выгрузки уровня и двух настоящих игровых экземпляров.

Собственный GameHost использует тот же engine владения дочерним процессом;
registry-подготовка остаётся у [XP helper](xp-game-probe.md), managed опыты —
у [ActorProbe](actor-probe.md). Native-поколение одной игры отделено от сетевых
session/epoch, поэтому сервер может обслужить нового гостя без перезапуска игры.

Отпечаток scenario означает объявленный контракт Alfea28/entry0, а не равенство
Saved, квестов и мира. Переходы, запрет клиентских выходных триггеров и общий
режим ожидания загрузки относятся к L по [проектному контракту](design.md).
В P выход из квалифицированной сцены завершает её native-поколение; смена уровня
обоим игрокам текущим кодом не обещается.
