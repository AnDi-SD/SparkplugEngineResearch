# Экспериментальный игровой прототип

Лаунчер, игровой протокол и x86 адаптер пока проверяются отдельно. Лобби
не запускает прохождение: кнопка «Начать игру» отключена до подключения
проверенного игрового backend. Наличие двух сетевых соединений не означает
совместную игру.

## Сборка

Сетевые и игровые контрактные проверки:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools/WinxCoop/Build-NetworkChecks.ps1 -Configuration Release
```

Для сборки экспериментальных программ под оригинальную x86 игру:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools/WinxCoop/Build-NetworkChecks.ps1 -Architecture x86 -Configuration Release -IncludePrototype
```

Результат по умолчанию — `artifacts/WinxCoop/network-checks/<architecture>/<configuration>`.
`-BuildDirectory` задаёт другой каталог. Используется один compiler worker;
`-BuildWorkers` меняют с учётом доступной памяти. Нужны MSVC x86/x64,
Windows SDK, CMake и Ninja из Visual Studio Build Tools. Проверки не требуют
игровых ресурсов. Для игровых опытов нужна подготовленная отдельная копия игры.

## Лобби

`WinxCoopLauncher.exe` создаёт лобби на TCP-порту 27025, ищет серверы через
UDP-порт 27026 и подключается по адресу IPv4:порт. Двойной щелчок по найденной
записи выбирает сервер и подключается. После выхода можно подключиться снова.
Допускается один гость. Discovery показывает доступность лобби; окончательное
решение о приёме принимает TCP transport.

Необязательные аргументы: `--port PORT`, `--report NEW_PATH`. Отчёт создаётся
только по новому пути и записывает состояние и освобождение сокетов при выходе.
Окно сообщает отдельно о соединении и готовности игрового адаптера.

## Игровой протокол

`GameplayProtocol` использует общий Packet codec и канал application messages.
Он связывает соединение с session/epoch, проверяет совместимость EXE, адаптера
и заданной сцены, ожидает готовность обеих сторон и разрешение сервера.
Клиент не назначает уровень и не публикует принимаемую сервером позу.

Команда ввода описывает штатные magnitude, relative direction, reference heading
и jump-held. Последовательная очередь сохраняет переходы нажатия и отпускания.
Пропуск наблюдения ввода, события или переполнение очереди завершает этот
экземпляр протокола ошибкой. Отправитель сохраняет начало очереди, пока
transport не примет сообщение. Последовательность принятых событий сама по
себе не подтверждает их применение физикой: это обязанность native backend.

## Адаптер и диагностика

`WinxCoop.NativeAdapter.dll` предназначен только для проверенной оригинальной
x86 версии. Он подключается к главному игровому потоку и обменивается с внешней
программой версионированными данными без native pointers и handles. Проверяются
полный EXE, исходные/live инструкции, сцена и типизированные игровые связи.

`WinxCoopAdapterProbe.exe` запускает собственный экземпляр игры, загружает DLL,
проверяет восстановление контекста и ограничивает длительность опыта. Он не
подключается к уже работающей произвольной игре. Требуются абсолютные пути:
`--game GAME_EXE --adapter ADAPTER_DLL --report NEW_JSON --seconds 60`.
Это диагностический путь; сохранение регистров не заменяет проверку модели,
управления, выгрузки уровня и двух настоящих игровых экземпляров.

Подготовка MediaPath и графическая проверка описаны у [XP helper](xp-game-probe.md),
отдельные managed опыты — у [ActorProbe](actor-probe.md). Серверный выбор уровня,
подавление клиентских выходных триггеров и переход обеих сторон остаются
отдельной работой по [проектному контракту](design.md).
