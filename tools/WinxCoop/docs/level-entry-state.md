# Вход в локацию и общее состояние игрока

Статическая карта оригинального PC EXE SHA256
`3F022480BF55045DA4BF692E4BC8862ED38FC024E8A964A558FBDFDF646DFC4F`.
Адреса и поля относятся к этому образу. Она дополняет
[формат сохранений](../../../docs/formats/wxs-save.md) и
[диагностику общих ресурсов](shared-resources-probe.md).
Новые пути здесь установлены по оригинальным инструкциям и ресурсам;
их сетевое применение и игровой цикл повторного посещения ещё не приняты.

## Сохранение, вход и готовое состояние

Обычный загрузчик `4E7580` сначала сбрасывает Profile через `4E42B0`, читает
SavedState и запрашивает отложенный переход `595450(savedLevel,1)`. Затем
восстанавливает профиль. Сам запрос перехода не означает, что загрузка уровня
уже завершилась. Как описано в формате WXS, сохранённый максимум HP применяется
и как максимум, и как текущее здоровье.

Playing Entry `5F9AF0` вызывает LoadLevel `5F9580`. После получения ресурса и
инициализации объектов в его хвосте проходят отдельные операции:

| Порядок / вызов | Результат |
| --- | --- |
| `5F9919 → 5F7E30` | Переустановка разрешений и части флагов в контексте локации |
| `5F993B → 4EEF30` | Выбор и создание группы персонажей через `wxCharacterPlacementManager` |
| `5F99A2 → 552540` | Настройка `wxSideQuestManager` для уровня |
| `5F99AA → 5F8030` | Дополнительные условия и сообщения уровня/прогресса |
| `5F99F4..5F9A58` | Выбор сохранённой либо обычной начальной позиции основной Блум |

Позже сюжетные и tutorial-сообщения могут снова менять способности. Например,
цепочка `4EB6A0 → message27DB → Profile Notify4E4560 → 4E3970` для cinematic ID1
включает `Profile+510` и устанавливает первую ступень силы `+6E4=1`.
Сюжетный прогресс, разрешение атак, освоенный второй режим и ранг силы —
раздельные величины.

## Первое и повторное появление

Канонический `wxCharacterPlacementManager` находится через `765AEC`, его
ClassID — `6C56254E`. Он ищет в дереве сцены `Characters`, затем одну из
авторских групп `First` / `Others`. Решение зависит от текущего сюжетного
`Profile+514`, а в одном семействе — также от сохранённого байта `+53C`.
Универсальный счётчик посещений этим не установлен.

| Native level IDs | Условие выбора |
| --- | --- |
| `1..3` | `514==1` выбирает First, иначе Others |
| `9..13` | `514<4` выбирает First, иначе Others |
| `17..21` | `514<9` выбирает First; далее выбор зависит также от `53C` |
| `27..35`, включая Alfea28 | Другая ветка выбирает сюжетные группы Gardenia, First_Date, BMS, Ct1, Date2, RedFountain, Sparks или Ct2 по `514` |

Потребитель `4EEAF0 → 4EE5B0` обрабатывает `General` и `Part_%02d`, разрешает
шаблоны, создаёт и регистрирует экземпляры, копирует размещение/ориентацию и
задаёт начальное состояние узлов. Меняется группа персонажей внутри сцены.
Это не доказательство выбора другого файла всего уровня.

Начальная позиция основной Блум выбирается отдельно. Успешная загрузка сейва
ставит одноразовый `Profile+6E0=1`; LoadLevel использует сохранённую позицию
`+584`, затем очищает флаг. При нуле используется обычный путь `5F68E0`.
Конечный профиль с уже очищенным флагом не описывает использованный путь входа.

Не доказано, что конкретный первый вход сам меняет `514/53C` до загрузки
клиента. Расхождение групп при разных входных значениях этих полей возможно
по показанным веткам; обязательное такое расхождение каждого первого входа
не заявляется. Для сетевого контракта нужны фактическое решение сервера и
состояние после завершения штатного входа.

## Разрешения Блум

`5F7E30` вычисляет `Profile+510` через native запрос и затем применяет условия
локации. Для IDs `27..35` и `41..46` оно явно устанавливается в ноль; Alfea28
входит в эту проверенную ветку. Вход также меняет отдельные биты из массива
50 флагов `Profile+518..549`. Этот массив нельзя автоматически называть картой
50 посещённых уровней.

Штатный ввод `4E2C92` проверяет `510`. При нуле очищаются attack20/21,
с отдельным исключением device mode9, и поле1F. Это не глобальное отключение
ходьбы и прыжка. Battle отдельно временно очищает `Profile+512` и восстанавливает
его при выходе. Текущие режим устройства, состояние тела и ресурс маны также
влияют на действия.

Первый Sparx со снежками полностью не прослежен. Установлены исключение mode9,
сброс `Profile+6F8` при загрузке, выдача10 снежков и штатный расход; producer,
который именно при первом входе назначает этот контекст, остаётся открытым.
Называть любое mode9 снежным режимом пока нельзя.

## Две валюты и покупки

| Состояние | Канонический источник |
| --- | --- |
| Обычные Fairy Stars | `Profile+6F0`, native award `58C270`, Star table `702160` |
| Собранные магазинные Gems | Маска `Profile+3B8..3E7` и шесть счётчиков `+3E8..3ED` |
| Потраченные Gems | `Profile+3F0` |
| Доступный баланс Fashion | Native `4E3580` суммирует шесть unsigned байтов; Fashion вычитает потраченное |

Магазинная валюта соответствует описанию розовых коллекционных наград:
её отдельный native тип — `wxCollectibleGem`, ClassID `27F540A1`, table
`6FCF20`, ресурс `SFX/CollectibleGem.spt` и отдельный HUD `HudGems`.
Цвет заново не проверялся визуально. Callback `544F20 → 4E7470 → 4E4FA0`
обновляет собранные Gems. Это отдельный тип от FairyStar.

Подтверждение покупки `5EA1AF → 5E8600` увеличивает сумму потраченного и
через `553B80` ставит флаг владения предметом. Начальный `5E9010` лишь
открывает окно подтверждения. Поэтому для общего состояния нужны маска,
счётчики, сумма расходов и владение; одного отображённого баланса недостаточно.

Шесть именованных покупок одежды имеют IDs `0x89..0x8E` и постоянные флаги
`wxSideQuestManager+B5..BA`. Native price-ветка принимает также `0x8F`, но этот
ID назван BMSFairy1; нельзя объявлять весь её диапазон шестью костюмами.
Флаги доступности Fashion и выбранный пункт меню — другие состояния.
Конечное поле выбранного asset и смена модели второго тела ещё не установлены.
Они могут быть отложены отдельно от общего владения покупками.

## Предметы и квесты

`765AE0` — один `wxSideQuestManager`, ClassID `4C843EA5`, table `6FDEDC`.
Он объединяет несколько представлений состояния:

| Область | Назначение |
| --- | --- |
| `2C..BF`,148 байтов | Постоянно полученные/купленные предметы |
| `C0..DC` | Отдельные вторичные флаги доступности/удержания |
| `DD..EF` | 19 флагов начала/доступности заданий |
| `F0..102` | 19 флагов завершения |
| `14C..155` | Сохраняемые байты, включающие доступность Fashion; смысл каждого producer не закрыт |

В оригинальной таблице селекторов найдены OutfitScissors `0`,
OutfitIvorySnowflake `3`, OutfitGreenCrystal `5`. Их постоянные флаги находятся
по `2C/2F/31`, вторичные — по `C1/C4/C5`. Получение и использование предмета
нельзя свести к одному придуманному bool. GreenCrystal также отличается от
семейства IceSample/IceCrystal. Названия и ресурсы установлены; размещение
каждого предмета на конкретном уровне этим анализом не проверено.

Для ножниц entry helper `551AF0` проверяет соответствующие флаги, скрывает
узел `scissors` и посылает штатное сообщение на существующих ветках.
Это пример влияния сохранённого состояния на содержимое уровня.
Полного каталога таких правил для всех предметов, сундуков и R-пазлов пока нет.

Сохраняемые quest-флаги упаковываются в SavedState `11C/120`. Diary `5D3BB0`
выводит13 выбранных пар. Имена всех19 заданий, каждый их producer и весь
промежуточный script progress ещё не расшифрованы. Живые quest actors,
условия активации и экранный индикатор не заменяются двумя битовыми словами.

## Что означает меню Escape

Типы и исходящие переходы связывают разделы61 Diary,62 Magic,63 Fashion,
65 Inventory,66 Options. Diary показывает канонические данные профиля и
менеджера, а также хранит локальные страницу, курсор и выбранную строку.
В Options есть локальные display/input/audio настройки. Их расположение в
одной книге меню не делает настройки компьютера общими.

Формат `SettingsXX.wxs` отделён от игровых `SavedXX.wxs`. Полный граф getters
Magic, дополнительные challenge-рекорды и смысл четырёх сохранённых DWORD
GUI manager не закрыты. Матрица8×6 в Saved относится к сбору Gems; оснований
называть её таблицей challenge-рекордов нет.

## Минимальный контракт для E5

Сейчас P/V3 передаёт позы и анимации, IPC5 — ввод и его управление. Их сообщения
не несут валюту, предметы, покупки или квесты. Общие singleton на сервере и
проверенный E3 подбор FairyStar ещё не означают передачу этих данных клиенту.
Допуск второго тела к отдельному типу CollectibleGem также не проверен.

Для следующего этапа нужны:

1. Серверное решение входа: destination/entry, использованный путь позиции и
   выбранная группа персонажей. После native init — фактический состав сцены
   и итоговые разрешения. Не заменять их выдуманным счётчиком посещений.
2. Версионированный общий снимок Profile и одного SideQuestManager: обе валюты,
   собранные Gems, расходы, владение/доступность предметов, покупки, quest-флаги,
   сюжетное продвижение и способности. Передавать значения и IDs, без указателей.
3. Применение абсолютного серверного состояния на клиенте после подходящей
   native готовности. Не воспроизводить награду, покупку или quest completion
   повторно ради совпадения интерфейса: штатные grant/setter пути имеют эффекты.
4. Проверка до/после подбора обеих валют, покупки и одного перехода состояния
   задания; позднее подключение/повтор снимка не удваивает награды и расходы.

Для первого прототипа покупки и сложные диалоги можно оставить ведущему,
а клиенту передавать их результат. Смена костюма второго тела, все ветки
снежков/боссов и полный каталог квестов могут оставаться отдельными задачами.
Эта карта не объявляет E5 реализованным или весь сюжет пригодным для кооператива.
