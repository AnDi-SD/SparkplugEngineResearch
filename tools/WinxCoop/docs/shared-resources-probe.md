# Диагностика общих ресурсов

Это отдельные опыты ActorProbe для одного оригинального игрового процесса.
Они проверяют штатные операции боя, общий HP и подбор Star вторым телом.
Для magic energy реализован отдельный ограниченный адаптер; его расход и
восстановление ещё не приняты в живой игре.
Основание E3 проверено также в сюжетной Gardenia03: общий смертельный урон,
две native Dying-ветки, одно глобальное завершение и настоящий Game Over с
возвратом в главное меню. Это конечный игровой профиль, не допуск всех атак,
предметов, уровней или сетевой синхронизации.
Сетевой прототип P их пока не использует. Сборка и общая конфигурация — в
[руководстве ActorProbe](actor-probe.md).

## Явные параметры fixture

Для retained-опытов двух тел используется `Mode="template-bloom-body-hair-idle"`, отдельный
закреплённый `TemplateFile` с `TemplateSha256` и следующие JSON-флаги.
Все флаги по умолчанию выключены; флаг не заменяет подходящий layout шаблона.

| Параметр | Назначение и зависимости |
| --- | --- |
| `TemplatePlayerTraitsFixture`, `TemplatePlayerTraitsPickupFx` | Полный второй PlayerTraits и его native pickup FX; основа остальных адаптеров |
| `TemplateSharedHealthAlias` | Канонический HP первого тела; требует обоих предыдущих флагов |
| `TemplateHealthBattleFixture` | battle_01 и ограниченное боевое наблюдение; требует общего HP |
| `TemplateTargetRegionFixture`, `TemplateConfigureTargetRegion` | Отдельный layout с TargetRegion и его native setup; для retained idle нужны общий HP и pickup FX |
| `TemplateStingerSecondaryRole` | Допуск второй цели для проверенного Stinger; требует battle, общего HP и обоих TargetRegion-флагов |
| `TemplateStarSecondaryEligibility` | Дополнительная native proximity-проверка Star и наблюдение награды; требует battle и общего HP |
| `TemplateBattleCombatFixture` | Native подготовка разрешения атак до создания второго тела; требует battle и общего HP |
| `PrepareFirstMagicStage` | Начальный ранг0→1 в явном combat fixture; допустим также в `shared-state-combat-live` |
| `TemplateStarPlacementFixture` | Один тестовый перенос собственного тела к наблюдаемой Star через native API; требует Star eligibility |
| `TemplateSharedMagicEnergyAlias` | Ограниченный общий magic energy; требует battle и общего HP |
| `TemplateSecondAttackDegreeFixture` | Native selector53 при сохранённом ранге1; требует combat fixture и `PrepareFirstMagicStage` |
| `TemplateSharedBattleLifetime` | Удержание собственного шаблона через паузу и очистка перед настоящим выходом из battle; требует battle и общего HP |
| `TemplateDeathBattleFixture` | Отдельный опыт общего смертельного попадания; требует retained battle и Stinger, исключает цели Star/mana |
| `TemplateSharedPlayerProfile="gardenia-03"` | Отдельный сюжетный профиль level3 с общим HP и retained lifetime; legacy battle-флаги выключены |
| `TemplateCollisionDetectorSecondaryRole` | Экспериментальный допуск второго тела и once/window для ближних атак Ghoulie; требует story, TargetRegion и общего HP |
| `TemplateProjectileManagerFixture` | Полный stock BloomProjectileManager: отдельные scoped init/delete Альфеи и battle; retained режим допускается только своим явно выбранным cohort |
| `TemplateBodyInputFixture` | Конечный локальный источник movement/jump в retained `alfea-28-input`; требует PlayerTraits, pickup FX, настроенный TargetRegion и общий HP; не включает сетевую доставку |
| `TemplateOrdinaryAttackFixture` | Отдельная первая обычная атака в `battle-01-ordinary-attack`; собственный менеджер, native пул, общий HP и первая ступень магии; исключает другие action fixture |
| `TemplateNetworkInputFixture` | Экспериментальный IPC4 movement/jump в `alfea-28-network-input`; отдельный Host endpoint, собственный контроллер и общий HP; исключает локальный scripted input и боевые fixture |
| `TemplateNetworkInputBackpressureFixture` | Дополнительная краткая задержка только Host Drain для проверки очереди контроллера; требует `TemplateNetworkInputFixture`, не останавливает native update и подтверждения ранее применённых команд |
| `TemplateStoryDeathFixture` | Сюжетная общая смерть и настоящий Game Over; требует story/CollisionDetector fixture и исключает цели Star/mana |

Боевые условия завершения выбираются по включённой проверке: Star ожидает
награду для второго тела, mana — подтверждённый native spend, обычный HP —
два урона. Stinger дополнительно требует собственный native send и урон по
второму телу. Эти проверки следует проводить отдельными запусками: при
комбинации флагов приоритет цели — Star, затем mana, затем HP/Stinger.
Без достижения цели опыт останавливается при четырёх HP-транзакциях либо
по общему времени; это не успешная приёмка выбранной операции.
В отдельном `TemplateSharedBattleLifetime` достижение цели сохраняется, а
очистка ожидает настоящего выхода через игровой Flow. Ограничение — четыре
HP-транзакции для обычного опыта и десять для явного опыта смерти; общий
временной лимит сохраняется.

## Боевой профиль

`shared-state-observe` читает battle_01 (level47), сообщения урона и операции
подбора. `shared-state-combat-live` дополнительно вызывает штатное включение
атак. Оба режима ограничены общим `DurationSeconds`, не более600секунд;
собственное наблюдение завершается через90 или240секунд после готовности уровня.
Они не создают второго персонажа.

Обычный отладочный вход в челлендж не воспроизводит сюжетную подготовку магии.
Для проверочного корпуса явно включается `PrepareFirstMagicStage=true` в
`shared-state-combat-live` либо вместе с `TemplateBattleCombatFixture=true`.
Адаптер вызывает родной setter разрешения атак и,
если ранг равен нулю, повторяет одно доказанное сюжетное присваивание первого
ранга. Исходная инструкция и результат записи проверяются. Полный cinematic
manager не вызывается: вместе с наградой он меняет игровой Flow.

У игры несколько отдельных состояний:

| Состояние профиля | Назначение |
| --- | --- |
| byte510 | Разрешение обычных игровых команд атаки |
| DWORD6E4 | Ранг силы, используемый таблицей урона; увеличивается при сборе светлячков |
| bit00200000 в DWORD42C, selector53 | Флаг второй ступени/обучения, используемый BloomFSM для дополнительных вариантов атаки |

Ранг силы и вторая ступень не заменяют друг друга. Опыты не выставляют все
улучшения и не объявляют полный сюжетный путь выдачи второй ступени изученным.
`TemplateSecondAttackDegreeFixture` отдельно вызывает API профиля `4E38B0(53)`.
После возврата весь профиль должен совпадать с исходным, кроме OR00200000 в
DWORD42C; ранг1, разрешение атаки, HP и native energy-enable сохраняются.
Это ограниченная подготовка опыта, не воспроизведение сюжетного скрипта болот.
Сам флаг не доказывает расход энергии или включение глобального boss mode.
Пара вход/выход PlayerTraits и вложенная пара CharacterTraits могут описывать
одно попадание; такие сообщения нельзя считать двумя отдельными ударами.

## Второй PlayerTraits

Проверочный шаблон с полным штатным PlayerTraits отделён от прежнего шаблона
с базовым CharacterTraits. `TemplatePlayerTraitsFixture=true` допускает только
закреплённый layout и явный `template-bloom-body-hair-init` либо нейтральный
`template-bloom-body-hair-idle`. Для второго режима также требуется
`TemplatePlayerTraitsPickupFx=true`.

Native Init создаёт собственную callback-привязку. Дополнительный вызов
`4FE440(ownTraits)` после Init создаёт собственные эффекты подбора; штатный
глобальный этап загрузки для этого не повторяется. У второй Блум отдельные
FX-узлы и контроллер. Общий неизменяемый animation handle может совпадать.
Диагностика инвентаризирует принадлежащую этому FX систему частиц отдельно
от Skin; неизвестный renderable остаётся ошибкой. Такой граф нельзя передать
в выборку пассивной визуальной модели.

Деструктор PlayerTraits безусловно освобождает process-global animation set31.
Для второго экземпляра адаптер пропускает только этот вызов с проверенными
receiver, caller, аргументом и фазой удаления. Остальные native действия
деструктора выполняются. Сохранность первичных FX-привязок и12байт bucket
проверяется отдельно; это не проверка всего animation manager.

## Общий HP

`TemplateSharedHealthAlias=true` требует отдельного PlayerTraits+FX и режима
`template-bloom-body-hair-idle`. Привязка выполняется на фактическом WorldRET
после первого обновления; перед удалением второго тела она отключается.
Нейтральный опыт выполняет30 обновлений и не должен изменять HP.

В экспериментальном `TemplateHealthBattleFixture=true` используется battle_01.
Он ожидает первое фактическое обновление персонажей. После двух подробно
проверенных кадров частые диагностические перехваты снимаются; дальнейшее
наблюдение ограничено36000 WorldRET и общим временем запуска.
Без дополнительных целевых флагов условие завершения — две подтверждённые
native операции урона. Обучение закрывается обычным вводом игры. Эта проверка
сама не делает второе тело допустимой целью для всех семейств атак.

Канонический HP принадлежит первому PlayerTraits. При допущенном native уроне
по второму телу только receiver родного setter перенаправляется на первый.
Сам setter вычисляет результат и выполняет своё уведомление один раз; затем
фактические current/previous HP копируются во второе представление с readback.
Алгоритм урона не заменяется. NPC с другими Traits проходят исходный путь.

Летальная ветвь и подавление повторных глобальных действий вторичной Dying
реализованы экспериментально и требуют отдельной живой приёмки. Лечение,
изменение максимума, script/Profile-load setter и неизвестные прямые записи HP
не входят в этот допуск: распознанные неподдержанные операции останавливают опыт.
Нейтральная привязка или два попадания не закрывают смерть, возрождение,
политику одного удара по двум телам и общий инвентарь.

## Собственный TargetRegion

Отдельный закреплённый шаблон добавляет к шести прежним дескрипторам штатный
`TargetRegion`, привязанный к Root второй Блум. Его `Is Player=false` сохраняет
глобальную ссылку TargetManager на первого игрока. `Is Target=true` и
`Use Template Collision Volume=true` позволяют использовать собственную
metadata контроллера движения. Это отдельный допуск: больше компонентов и
другая сумма ссылок Root не переносятся на прежние шаблоны.

`TemplateTargetRegionFixture=true` допускает scoped Init/Delete либо отдельный
нейтральный `hair-idle` с общим HP и `TemplateConfigureTargetRegion=true`.
Последний флаг добавляет после собственного pickup FX второй вызов `5113E0`
на собственном TargetRegion. Он включает bit8 штатно, без записи флагов
адаптером. При обычном обновлении игра также может вызвать этот метод сама.

До и после жизненного цикла проверяются упорядоченный список TargetManager и
его заимствованные ссылки; удалённый TargetRegion больше не разыменовывается.
`Is Player=true` для второго тела здесь запрещён: он заменил бы глобальную
ссылку игрока. Bit10 этим механизмом не добавляется. Поэтому создание региона,
его bit8 и нейтральные обновления ещё не подтверждают, что все снаряды могут
попасть во вторую Блум. Входной фильтр Stinger имеет отдельный адаптер.

## Stinger: второе тело как цель

`StingerSecondaryRole` допускает только native Stinger из проверенного пула
Mosquito, с парными Activate/Deactivate и отдельной генерацией при повторной
активации того же объекта. В точной collision-ветви для собственной metadata
и native filter0 он меняет только EIP `501E6C→501E6E`, пропуская один отказ
по роли. Флаги metadata8/10 не записываются. Исходные mask8, исключение
источника, native damage send и retirement снаряда выполняются самой игрой.
Постоянного списка «уже повредивших» указателей нет.

Живой battle-опыт подтвердил отдельные native попадания по первому и второму
телу, общий HP через канонический setter и readback второго представления.
Перед native Delete адаптеры отключились, собственный граф был освобождён.
Это допуск данного Stinger-пути; другие снаряды, один снаряд на двух телах,
летальные ветви и сетевой once этим опытом не закрыты.

## Star: proximity двух тел и одна native награда

`StarSecondaryEligibility` оставляет первую native проверку без изменений.
Только после её промаха один раз повторяется исходный query597660 с Root
второго тела и исходным tolerance. Игра сама выполняет distance/comparison,
award58C270 и deactivate58C010. Повтор использует исходный argument-push span;
адаптер не меняет ESP/FP, не вызывает award отдельно и не подменяет Profile2B4.
Повторный промах продолжает исходную failure-ветвь. Притяжение Star остаётся
направленным на первого игрока.
Исходный award вызывает `4E6450`, protected helper `4E63B0` и native
group23/message2811; адаптер не заменяет этот путь своей наградой.

`NativeStarAwardObservation` связывает один award с точной текущей query,
проверяет native возвраты, фактическое изменение канонического Profile6F0 и
окончание native retirement с active40=0. Дельта читается после вызова, а не
вычисляется из payload адаптером. Повторный award в той же query останавливает
квалификацию; подавления по постоянному указателю Star нет.

Живой опыт moving-пути подтвердил промах по первому телу, успешную проверку
второго, native награды общего профиля и retirement предметов, затем отключение
наблюдателей и native Delete собственного тела. Для этого использовался явный
`TemplateStarPlacementFixture`: один native перенос второго тела к наблюдаемой
Star без переноса самой Star или первого игрока. Это тестовая подготовка,
не автоматическое перемещение персонажа в сетевом P. Stationary-путь реализован,
но ещё требует живой приёмки, как и overlap, повторная активация пула и смерть.

## Magic energy: реализованный контракт и открытая приёмка

Энергия хранится inline в каждом PlayerTraits: float current/max/min находятся
в `+1A8/+1AC/+1B0`, native previous current — в `+1C0`. `SharedMagicEnergyAlias`
требует равных исходных представлений и стабильных max100/min0. Он не включает
native byte1A0: оба значения0/1 допускаются и наблюдаются отдельно.

Канонический ресурс принадлежит первому телу. Поддержаны точные native spend
`4FDDD0`, current setter `4FDAC0`, state8-drain в Update и прямой drain2776.
Последний перенаправляет ECX только в `4FDE1F`, после исходных проверок byte24C
и собственного state8 поражённого тела. Для refill принят только парный источник
`5064A8→Notify2792→4FE2CB`: собственные pickup FX остаются на исходном теле.
После native возврата фактические current/previous копируются во второе
представление двумя DWORD-записями с readback. Арифметика и обычный HUD остаются
native; для прямого writer без HUD дополнительное уведомление не создаётся.

Политика адаптера: регенерирует только первое тело; его восстановление также
подавляется, пока второе находится в state8. Собственные native state8-drain и
spend каждого тела сохраняются и могут последовательно списать две стоимости.
Целиком Update receiver не перенаправляется: HP, hurt/death и управление
продолжают исполняться на своих телах. Это наша политика общего ресурса,
не обнаруженный stock-режим двух игроков.

Изменение максимума `4FDB30`, Notify272A, property-current `4FD720`, minimum
setter `563230`, copy `4FD9C0` и прочие refill/script callers не допущены.
Распознанные неподдержанные операции останавливаются до native записи.
Защита полного reset остаётся у общего HP; перед удалением тела все адаптеры
должны завершить парные вызовы и отключиться.

Первый живой mana-опыт подтвердил только binding и парные Update: оба1A0 были0,
native spend и записи зеркала отсутствовали. Он завершился timeout с кодом124
и принудительной очисткой процесса, без retirement адаптеров и native Delete
собственного тела. Это не приёмка расхода, регенерации, refill или cleanup
mana-пути. Полная общая синхронизация ресурсов между процессами остаётся
отдельной сетевой задачей.

Включение selector53 подтвердило отдельную заряженную атаку. В её обычном
пути native damage вычисляется без обращения к исследованным spend-операциям.
`wxMissileState` и `wxBlastState` используют другие пути; глобальный Notify272A
также меняет режим Bloom, максимум энергии и refill. Поэтому заряженная атака
сама по себе не служит тестом расхода энергии. Этот режим требует отдельного
допущенного игрового профиля.

## Retained battle и проверка смерти

`TemplateSharedBattleLifetime` отделён от Alfea body-live режима E1. Адаптер
удерживает собственную ссылку шаблона, чтобы штатная очистка кэша при паузе не
удалила его раньше созданного тела. Он наблюдает настоящий Flow и GameTimer;
состояния паузы и ввода не создаются адаптером.

Battle exit `5F2300` восстанавливает HP до общего unload `5F86C0`. Поэтому
очистка начинается перед первой инструкцией battle exit: завершённые адаптеры
отключаются, затем native удаляет собственные Instance, Template и Stream.
Идентичность PlayerTraits сохраняется до проверенного пропуска освобождения
глобального set31 в собственном деструкторе. После batch старые адреса
обнуляются; исходная инструкция выхода продолжается с сохранённым контекстом.
Call page освобождается на более позднем WorldRET. Далее проверяется только
свежий Flow/MainMenu, без чтения удалённых player/body объектов.

Для двух тел недостаточно скопировать нулевой HP: штатная реакция конкретного
PlayerTraits зависит также от его hurt-состояния. Экспериментальный
`SharedDeathCommandAlias` наблюдает настоящий native frontend сообщения2717 с
уроном1. Класс отправителя здесь не определяет смерть: native producer читает
фактический HP и команду поражённого тела. Только после завершённого HP1→0 и полного native возврата
фактически произведённый dead-byte команды копируется в отдельную команду
другого тела с readback. Это наша политика общего игрока. Повторный удар,
расчёт урона, HUD и hurt-byte не воспроизводятся.

Приёмка требует, чтобы обе штатные машины действительно потребили команду,
первичная Dying выполнила единственное глобальное завершение и reset, а
вторичная сохранила анимацию и пропустила повторные глобальные действия.
Сборка и публикация одного dead-byte не подтверждают эти условия. Сюжетная
выгрузка может удалить второе тело до завершения его Dying-анимации: это отмена
жизненного цикла удалением, не доказательство завершённой второй анимации.
До удаления собственные глобальные fade/completion/reset подавляются.

## Сюжетный профиль Gardenia03

Закрытый `NativeSharedPlayerProfile` задаёт level3, Playing table `710874` и
обычный exit `5F86C0`. Battle47 сохраняет отдельный тип и ранний exit с refill;
E1 Alfea28 не расширяется этим выбором. В Gardenia03 собственное тело создаётся
после первого готового snapshot вместо прежних пятнадцати: ближайший Ghoulie
уже находится в пределах восприятия. Проверки native готовности сохраняются;
потерянный до привязки HP не нормализуется под шаблон.

Ghoulie AI читает основного игрока из Profile; его броски целятся через
TargetManager+28. Список TargetRegion не включает выбор ближайшей Блум.
Штатная цель остаётся основной. Глобальный physics player-bit10 не добавляется
второму телу: он связан также с IntelliCam, публикацией глобальной позиции и
другими действиями MoveCtrl. Допуск отдельных семейств атак остаётся отдельным
адаптером.

Ближний CollisionDetector использует native события начала/конца атаки271F.
Каждое matching enable, включая повторное true, открывает новое окно. После
первого настоящего HP commit остальные P1/P2-кандидаты того же окна пропускаются
до повторных эффектов271C/275C/2717, с сохранением native hit-seen/LastVictim.
Этот путь реализован и проверен статически; в принятом сюжетном прогоне враг
применял обычные снаряды, поэтому живой допуск ближнего удара по P2 не заявляется.

Принятый сюжетный опыт проследил шесть native попаданий6→0, одну публикацию
фактической команды смерти во второе тело, обе Dying Entry и единственный
канонический reset. Дополнительное сообщение при уже нулевом HP не повторило
ни списание, ни публикацию. Собственное тело и ресурсы удалены перед исходной
выгрузкой; вызов продолжается с сохранённым контекстом, call page освобождается
на более позднем WorldRET.

Game Over появляется **после** выгрузки уровня. Пассивный наблюдатель живёт
дольше player/body-адаптеров и читает только свежий Flow и живой GameOver state.
Требуются actual Entry `5E04F0`, RET4 и парный возврат, затем settled Flow с
типом `70F778`, позже inherited Exit `5F14B0` с парным возвратом и два свежих
WorldRET главного меню. Очередь Dying и окончание челленджа этим условиям не
равнозначны. На главном меню наблюдатель отключается; старые player/scene/body
адреса после выгрузки не читаются.

## E4: собственный менеджер снарядов

`TemplateProjectileManagerFixture` добавляет к отдельному диагностическому
шаблону полный stock-дескриптор BloomProjectileManager. Всего получается
восемь дескрипторов. Scoped режим сохраняет `Character Type=1` и собственный
command, проверяет связь `Character+140` с менеджером, его Character-владельца
и точки выпуска `hand_right` / `hand_left` внутри своего скелета.

В Альфее родной Init возвращает false до создания боевых пулов. Отдельная
проверка принимает именно этот путь и последующее штатное удаление, включая
парные native возвраты и сохранность основной Блум. Поле менеджера `+130`
заимствует основной MoveCtrl; наблюдение этой ссылки не объявляет её
независимым контроллером. Снятие регистрации channel8 прослеживается по
конкретному вызову и его продолжению; весь список подписчиков этим не проверен.

В отдельной battle-проверке родной Init создаёт 18 обычных снарядов трёх
типов. Их владельцы, отдельные Node/Actor, парные возвраты удаления и снятие
регистрации channel15 прослежены до очистки. Это проверка жизненного цикла;
реальная атака, выбор цели и роль снаряда требуют отдельных проверок.
Исходный `Character Type=1` меняет
эти ветви, поэтому наличие менеджера само по себе не разрешает стрелять от
имени второго игрока. Диагностика не меняет глобальные Player/Profile/Target
ссылки для подмены владельца.

`NativeBodyInputController` содержит ограниченную очередь
movement/jump команд с generation/sequence и timeout. Нейтрализация сохраняет
углы и штатный байт смерти; после retirement обращения к старому command
прекращаются. Отдельный `TemplateBodyInputFixture` с профилем `alfea-28-input`
подключает его к собственному серверному телу. Конечный локальный источник
проверяет native ходьбу, поворот, прыжок и приземление, остановку по тайм-ауту,
паузу, свежий нейтральный возврат и retirement перед штатным удалением.
Перед удалением менеджера снимается новый stopped snapshot основной Блум:
изменяемые поля не сравниваются с байтами до начала игры.

Этот источник диагностический и задаёт конечную локальную последовательность.
Отдельный путь фактической доставки ввода описан ниже. Действующие P/V3 и IPC3
продолжают работать по прежнему контракту и не принимают input-пакеты.

Отдельный `TemplateOrdinaryAttackFixture` использует профиль
`battle-01-ordinary-attack` и первую сюжетную ступень магии. Короткая команда
атаки собственного тела проходит родной выбор состояния, `wxAttackingState`
и анимационное событие `event_orb` до выпуска и движения обычного снаряда.
В этом пути второе тело сохраняет свой command и `Character Type=1`.
Узкий адаптер выбирает player-role при штатном создании собственного пула,
отключает у своего тела допуск в качестве цели и оставляет незахваченный
выстрел на родной траектории. Общие Profile/Target ссылки не подменяются.

В живой проверке подтверждены собственный выстрел и последующая очистка
пулов при выходе в меню. Попадание по врагу, фактическая фильтрация снаряда
между двумя Блум, второй режим атаки, щит и снежки этим опытом не проверены.
Команда атаки также ещё не является принятой сетевой возможностью.

## E4: диагностическая доставка ввода

Экспериментальный `WinxCoopInputBridge` передаёт movement/jump через отдельный
контракт поверх существующих Packet/MemoryStream, SessionCore и Windows TCP
transport. `DiagnosticInputClient` связывает ActorProbe с мостом через IPC4,
не добавляя managed-реализацию сетевого serializer. Конфигурация содержит
`DiagnosticHostInput` и при локальной проверке источника `DiagnosticGuestInput`;
каждый endpoint проверяет роль, PID и время создания владельца, nonce, сеанс,
сценарий, поколение и свежую именованную область памяти.

IPC4 содержит очередь с одним производителем и одним потребителем, отдельные
sequence/epoch и срок допуска. `NativeInputCapture` читает штатные команды
04/08/14/1A после настоящего UserInputRET; основной command не изменяется.
Захваченные значения и время сохраняются в ограниченной RAW FIFO. При нехватке
кредита уже принятая запись не заменяется новым наблюдением и не получает новое
время захвата. Начальное включение и новая эпоха требуют настоящего native
возврата и нейтрального прыжка. При потере допуска накопленные записи явно
сбрасываются; старый ввод не переходит в новую эпоху.

Серверный мост назначает время приёма один раз. Ожидание в очереди и повтор
попытки при заполненном контроллере его не обновляют. Принятие очередью отделено
от ACK после следующего готового штатного игрового такта. Одновременно допускаются
не более восьми неподтверждённых команд. Свежесть данных, RAW и серверной очереди
ограничена 500 мс. Отдельный `--actor-lease-ms` регулирует только ожидание публикации
живого ActorProbe: по умолчанию 500 мс, в диагностическом игровом запуске 2000 мс.
Он не продлевает срок команд и не восстанавливает терминально закрытый канал.

Мост накапливает ограниченный диагностический trace в памяти. Файл
`<report>.trace.jsonl` записывается после терминальной публикации, закрытия TCP
и timer handles; работающий сетевой цикл не пишет trace в stdout. Итоговый
отчёт отдельно считает пропуски диагностических строк. Это не пропуски ввода.

В одной настоящей Alfea28 проверена цепочка штатный InputRET → Guest bridge →
TCP loopback → Host bridge → отдельный command и native контроллер второго тела.
Подтверждены движение, прыжок, пауза, свежий возврат и retirement перед штатной
выгрузкой с удалением менеджера, тела и ресурсов. Задержка Host Drain проверяет
повтор при заполненной очереди контроллера. Она не доказывает RAW NoCredit:
в принятом игровом прогоне источник не исчерпал кредиты. Его принудительная
проверка на моделируемом источнике остаётся отдельным контрактным результатом;
native timeout сетевого контроллера также требует отдельной проверки.

Это один игровой процесс и два настоящих сетевых моста. Работа двух игровых
экземпляров, клиентского представления, LAN и сетевой атаки ещё не принята.
Боевые команды в текущий контракт не входят; P/V3/IPC3 не изменяются.
