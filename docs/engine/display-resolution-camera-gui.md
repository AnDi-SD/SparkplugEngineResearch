# Разрешение экрана, камеры и GUI в Winx Club PC

Статус: статическое исследование без запуска и изменения исследуемых EXE. Все
виртуальные адреса и file offsets на этой странице относятся только к
`WinxClub(4).exe` размером 22 065 152 байт с SHA-256
`3F022480BF55045DA4BF692E4BC8862ED38FC024E8A964A558FBDFDF646DFC4F`.
ReadMe исследованного набора называет версию `Winx Club Release 1.01.00` от
10 января 2006 года. Эта сборка не совпадает по SHA-256 с ранее зафиксированным
baseline `WinxClub.exe`, поэтому переносить адреса на другие EXE без повторной
разметки нельзя.

Основание страницы — локальный технический отчёт
`WinxClub_resolution_research_2026-08-23.docx`, зафиксированный 23 августа
2026 года. Исходный `.docx` и исследованные игровые файлы остаются в
игнорируемом `local-data/` и не входят в репозиторий.

Здесь используются три статуса:

- **Подтверждено** — непосредственно следует из строк, импортов, байтов или
  дизассемблированного участка указанного файла.
- **Сильный вывод** — согласованная интерпретация нескольких участков кода без
  динамической трассировки.
- **Предложение** — проектное решение для будущего патчера, а не штатное
  поведение игры.

## Графический режим принадлежит игровому процессу

**Подтверждено.** Основной EXE импортирует `Direct3DCreate9` из `d3d9.dll`, а
также `AdjustWindowRect`, `GetClientRect` и `CreateWindowExA`. Физический размер
окна и backbuffer формируется внутри игры, а не только лаунчером.

В `WinxClubLauncher.exe` найдены `WinxClub.exe` и `ShellExecuteExA`, но
поверхностный статический поиск не обнаружил строк известных разрешений,
`Resolution` или собственного Direct3D-кода. Это отрицательный результат поиска,
а не доказательство полного отсутствия косвенной логики.

Штатный `winx.ini` содержит `fullScreen`, `enableShadows`, `enableSound`,
`useGamePad`, `showCinematics` и `language`, но не хранит ширину и высоту.
Добавление отдельных `customWidth`/`customHeight` возможно как дизайн будущего
патчера, но исходной игрой не подтверждено.

## Нативный пункт Resolution

**Подтверждено.** В EXE присутствуют строки `Resolution`, `resolution_label`,
`value_resolution`, `ResR`, `ResL`, `DisplayR` и `DisplayL`. Имена
`resolution`, `value_resolution`, `resolution_label`, `res_L_scroll` и
`res_r_scroll` встречаются также в `igmenu_opt_pc.smo`, `igmenu_options.smo` и
`igmenu_options2.smo`. Следовательно, выбор разрешения является штатной частью
меню, связанной с обработчиками EXE.

В объекте меню индекс Resolution хранится по смещению `+0x70`, а три указателя
на отображаемые строки — начиная с `+0x290`:

| Индекс | Строка | File offset | VA |
|---:|---|---:|---:|
| 0 | `800 X 600` | `0x30ED98` | `0x70FD98` |
| 1 | `1024 X 768` | `0x30ED8C` | `0x70FD8C` |
| 2 | `1280 X 960` | `0x30ED80` | `0x70FD80` |

Конструктор около VA `0x5E5500` создаёт три строковых буфера по `+0x290`,
`+0x294` и `+0x298`. `ResR` около `0x5E1E80` циклически меняет индекс
`0 -> 1 -> 2 -> 0`, а `ResL` около `0x5E1EC0` — в обратном направлении.
Функция около `0x5E26B0` задаёт индекс Resolution по умолчанию равным `1`, то
есть `1024x768`.

При сохранении меню функция около `0x5E40B0` переносит индекс из `+0x70` в
структуру настроек по `+0x2B8`; код около `0x5E3941` выполняет обратное чтение.
Это связывает видимый пункт меню со штатным путём применения графического режима.

## Четыре физических режима и только три пункта меню

**Подтверждено.** Код применения настроек около VA `0x4E8349` принимает индексы
`0...3`, хотя обработчики меню дают выбрать только `0...2`:

| Индекс | Ширина | Высота | Доступность в штатном UI |
|---:|---:|---:|---|
| 0 | 800 | 600 | видим |
| 1 | 1024 | 768 | видим, значение по умолчанию |
| 2 | 1280 | 960 | видим |
| 3 | 1600 | 1200 | поддержан кодом применения, но скрыт в UI |

**Сильный вывод.** Выражение `[base + index*4 + 0x290]` при индексе `3`
адресовало бы `+0x29C`, однако конструктор выделяет, а деструктор около
`0x5E508D` освобождает ровно три строки. Простого расширения границы `ResR`/`ResL`
до `3` недостаточно для безопасной четвёртой подписи: сначала нужно подтвердить
размер объекта, отсутствие конфликта по `+0x29C` и исправить весь жизненный цикл
массива строк.

### Проверка изменения режима учитывает только ширину

**Подтверждено.** После выбора новой пары width/height код около VA `0x4E83BE`
сравнивает только текущую ширину `[descriptor+0x1C]` с новой шириной. При
совпадении ветка переинициализации пропускается; высота в условии не участвует.

Практическое следствие: переход между `1280x960` и будущим `1280x720` может не
примениться штатно. Будущий патч должен сравнивать и width, и height либо
использовать более надёжный признак изменения display mode.

## Что делает существующий Resolution Changer

**Подтверждено.** `Winx Club Resolution Changer.exe` с SHA-256
`384B8A029F9FF32404196192B7224472CCF8051168C72C285B42E11519BE6FE8` —
небольшое .NET/WinForms-приложение. Оно не внедряет Direct3D hook и не создаёт
свой renderer. Обработчик открывает выбранный EXE через `FileStream`/
`BinaryWriter` и заменяет несколько immediate-значений `1024x768`, включая
штатную ветку индекса `1`:

| Width offset | Height offset | Контекст |
|---:|---:|---|
| `0xD5E5` | `0xD5EC` | начальные width/height |
| `0xD617` | `0xD61E` | поля объекта `+0x60`/`+0x64` |
| `0x53BD1` | `0x53BD8` | display descriptor |
| `0xC2681` | `0xC2689` | стартовая локальная структура |
| `0xE7777` | `0xE777F` | ветка Resolution index `1` |

Отображаемая строка перезаписывается с `0x30ED8C`. После исходной
десятисимвольной строки `1024 X 768` остаются два NUL-байта, поэтому строка из
11 ASCII-символов вроде `1920 X 1080` всё ещё завершается вторым NUL. При
12 символах терминатор перед следующей строкой исчезает, а 13 и более байт уже
перезаписывают соседние данные.

Старый патчер не проверяет SHA-256 или исходные байты. Он превращает штатный
индекс `1` в пользовательское разрешение, но не расширяет список режимов, не
исправляет FOV и GUI и остаётся жёстко привязанным к offsets конкретной сборки.

## Перспективная камера и Vert-

**Подтверждено.** Конструктор камеры около VA `0x4287FF` умножает `pi/180` на
`60.0` и передаёт результат в функцию `0x427DA0`. Та сохраняет исходный угол,
вычисляет `tan(FOV/2)` и подготавливает параметры проекции. Функция около
`0x4289B0` делит два размера viewport; при согласованной с контекстом
интерпретации аргументов в поле камеры `+0x234` попадает `height/width`.
Функция `0x426F10` строит разные матрицы для перспективной и ортографической
ветвей по флагу `camera+0x231`.

**Сильный вывод.** Совокупность формул соответствует сохранению горизонтального
FOV `60` градусов. При расширении viewport вертикальный FOV уменьшается:

| Режим | HFOV | VFOV | Результат |
|---|---:|---:|---|
| исходный 4:3 | 60.000° | примерно 46.826° | исходная композиция |
| 16:9 с тем же HFOV | 60.000° | примерно 35.983° | обрезка сверху и снизу, Vert- |
| 16:9 с исходным VFOV | примерно 75.178° | примерно 46.826° | расширение по бокам, Hor+ |

**Предложение.** Для игровой перспективной камеры следует сохранять исходный
вертикальный FOV 4:3 и пересчитывать горизонтальный:

```text
HFOV_new = 2 * atan(tan(VFOV_original / 2) * aspect_new)
```

Поправку нельзя безусловно применять ко всем объектам Camera: отдельно
существуют GUI-камера и, вероятно, служебные камеры эффектов или
render-to-texture. Сначала нужен надёжный критерий игровой камеры.

## Отдельная ортографическая GUI camera

**Подтверждено.** В EXE есть строки `GUI camera` и
`Failed to initialize GUI camera`. Код около VA `0x451D5D` назначает камере это
имя и устанавливает `camera+0x231 = 1`, то есть выбирает ортографическую ветвь
матрицы. Затем в метод камеры передаются `100.0f` и `75.0f`.

Точное имя метода без символов неизвестно, но контекст и ортографическая
математика указывают на виртуальный размер GUI `100x75`, строго `4:3`.

**Сильный вывод.** Если это пространство без коррекции растянуть на физический
viewport `1920x1080`, масштаб составит `19.2 px/unit` по X и `14.4 px/unit` по Y.
Геометрия интерфейса растянется по горизонтали на 33.3%.

**Предложение.** Сохранять виртуальную высоту `75`, а ширину вычислять из
физического aspect ratio:

```text
GUIHeight = 75
GUIWidth  = GUIHeight * ScreenWidth / ScreenHeight
```

| Физический режим | GUI virtual width | Центральная область 4:3 | Боковые поля |
|---|---:|---:|---:|
| 1920x1080 | 133.333 | 1440x1080 | 240 px с каждой стороны |
| 2560x1440 | 133.333 | 1920x1440 | 320 px с каждой стороны |
| 3440x1440 | 179.167 | 1920x1440 | 760 px с каждой стороны |

HUD можно оставить в центральной 4:3 safe-area поверх расширенного мира. Для
полноэкранных меню и загрузочных экранов безопаснее центральная композиция 4:3
с pillarbox, пока не проверено runtime-поведение каждой группы ресурсов. Не
подтверждено, используют ли mouse hit-testing и `GUICollision` ту же камеру и
преобразование.

### Статическая структура меню настроек

Разбор чистого `Media/Menus/igmenu_opt_pc.smo` (SHA-256
`D6ED2606BFCA4C4EED41F59869D1EC1C20DFAFE7A3BFD8E7FEC6C5F109052F0E`) подтвердил
2D-композицию: все 99 mesh строго декодируются и остаются плоскими после
накопления transform. Ветки `settings`, `controls`, `options`, `language`,
`display` и `default` являются отдельными панелями, которые не следует
одновременно выводить как один кадр. Визуальные состояния сериализованы под
`NORMAL*`, `HIGHLIGHTED*`, `PUSHED*`, `DISABLED*` и `shadow*`; два mesh под
`GUICollision*` дают видимую геометрию интерактивных областей.

В `display` находятся узлы `resolution`, `value_resolution` и
`resolution_label`, но во всём файле нет `spTextNode`, `spTextRenderable` или
`spFont`. Это подтверждает статические anchors и графику, но не способ, которым
runtime подставляет подписи, текущее значение и связывает их с input path.
Viewer теперь воспроизводит статическую часть отдельной ортографической камерой,
фильтруя экран и состояние; runtime-связь остаётся предметом трассировки.

## Безопасная последовательность будущих проверок

Этот раздел описывает **предлагаемый эксперимент**, а не уже выполненную работу:

1. Работать только с копией EXE; проверять полный SHA-256 и ожидаемые исходные
   immediate-байты перед записью.
2. Сначала сделать доступным штатный индекс `3` с исходным `1600x1200`, чтобы
   проверить путь UI -> settings -> display mode без widescreen.
3. После runtime-подтверждения заменить только индекс `3` на тестовый
   `1920x1080`, не трогая индекс `1`.
4. Исправить сравнение режима так, чтобы оно учитывало width и height.
5. Отдельно проверить Hor+ на одной игровой камере и сравнить одну сцену в 4:3
   и 16:9.
6. Отдельно изменить виртуальную ширину GUI и проверить HUD, меню, курсор,
   mouse hit-testing, субтитры и loading screens.
7. Только после разбора menu `.smo` проектировать окончательный список режимов,
   anchors, safe-area и pillarbox.

## Нерешённые вопросы

- Как сериализуется и восстанавливается Resolution index `3`.
- Можно ли безопасно использовать поле `+0x29C` и каков фактический размер
  объекта меню.
- Какие объекты являются gameplay camera, а какие — служебными.
- Использует ли `GUICollision` преобразования GUI camera.
- Как обрабатываются FMV, катсцены, loading screens и полноэкранные фоны.
- Как проходит D3D9 Reset и пересоздание ресурсов при смене режима.
- Нужен ли верхний предел GUI safe-area для 21:9 и 32:9.
- Каким кодом runtime связывает anchors menu `.smo`, динамический текст и
  `GUICollision` с mouse/gamepad hit-testing.

До динамических проверок подтверждённым результатом следует считать только
статическую карту существующего пути. Архитектура widescreen-патча остаётся
предложением.
