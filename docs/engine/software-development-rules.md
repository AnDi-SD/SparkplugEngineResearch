# Основы разработки инструментов

Обязательные правила пользователя от 8 сентября 2026. Применяются ко всем
приложениям, общей библиотеке и дальнейшей переработке Viewer. Для работы
агентов закреплены также в корневом [AGENTS.md](../../AGENTS.md).
При расхождении с прежними рекомендациями разработки применяются эти правила.

```text
Наши программы → восстановленные исходники → игра
```

Это направление зависимостей. Источник истины — оригинальная игра; соответствие
восстановленного кода и поведения наших программ проверяется по ней.

## 1. Игра всегда права

Восстановленные исходники описывают реальную логику игры и движка. Их нельзя
подправлять ради удобства приложения, желаемого изображения или прохождения
теста, который основан только на нашей прежней реализации.

При расхождении сначала устанавливаем, как работает оригинальная игра на тех
же входах и в соответствующем состоянии. Исправляем восстановленную логику
только после доказательства ошибки дизассемблирования, декомпиляции или ручной
реконструкции. Записываем оригинальное поведение, причину ошибки и проверку
исправления. В остальных случаях исправляем наш софт: вызовы, данные, связи,
координатные преобразования или платформенную реализацию.

Если причина ещё неизвестна, продолжаем точечное исследование. Ни ожидаемый
результат приложения, ни нехватка сведений не разрешают менять контракт игры.
Особенность оригинала сохраняется, даже если она выглядит неудобной или ошибочной.

## 2. Общие восстановленные классы без дублирования

Игровую логику и логику движка приложения получают из общей восстановленной
реализации: `Sparkplug/` для движка, `Winx/` для игрового слоя. Для каждого
подтверждённого класса/алгоритма поддерживаем один общий источник реализации.

C# использует этот код через тонкую обвязку, например C ABI/P/Invoke. Обвязка
передаёт вызовы и данные, управляет временем жизни объектов; она не содержит
второй sampler, serializer, расчёт иерархии или другие копии игровой логики.
Техническое неудобство интеграции решаем на границе языков и сборки, без
создания ещё одной версии класса в каждом приложении.

Если нужная часть отсутствует, исследуем её по игре и дополняем общий код.
Класс можно восстанавливать частично в объёме текущей задачи. Неполнота класса
не разрешает выдумывать недостающую семантику. Существующие самостоятельные
реализации инструментов — предмет дальнейшего переноса; их наличие не является
разрешением добавлять новые дубликаты.

## 3. Современный платформенный слой — наш код

Взаимодействие с железом и ОС реализуем сами под современные системы. Renderer,
создание GPU-ресурсов, окна, ввод, доступ к файлам и прочие платформенные операции
относятся к нашему коду. Целевые графические API — **OpenGL и Vulkan**.
Перенос DirectX 9, старого device lifecycle и вызовов Windows 98/XP в приложения
не является целью разработки.

При этом порядок и смысл игровых операций, данные сцены, правила материалов,
анимации и прочая подтверждённая логика остаются общими и определяются игрой.
Новый backend реализует взаимодействие с устройством, сохраняя эти правила.
Если восстановленный метод смешивает игровую логику с системными вызовами,
отделяем платформенную границу и подключаем нашу реализацию к общему коду.
Код и сведения о старом backend могут сохраняться для исследования и проверки;
это не требует использовать его в наших программах.

Собственные UI и рабочие сценарии инструментов допустимы. Их служебная логика
и проверки на границах не должны незаметно менять игровую семантику или
подменять неизвестное поведение успешной заглушкой.

## Применение к текущей работе

Перед правкой определяем её слой: восстановленная логика, обвязка приложения
или наш платформенный backend. Для восстановленной логики требуется
подтверждение по игре; для остальных слоёв — сохранение её контракта.
Проверяем затронутый сценарий на небольшой подходящей выборке согласно
[манифесту исследования](../research/research-manifesto.md).

Переработка Viewer не завершена. Пакет 0.7.0 фиксирует промежуточную проверку
подключения C++-классов и не является итогом всей задачи. Дальнейшая работа
следует этим основам; графический backend остаётся нашей современной реализацией.
Контрольные сборки и commits служат разработке. Упаковка и выпуск — отдельная
задача, а не автоматическое завершение очередного этапа интеграции.
