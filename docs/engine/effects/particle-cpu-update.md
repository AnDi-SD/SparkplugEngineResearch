# PC ParticleSystem: обновление существующих записей

`0048D450` обновляет часы и, в зависимости от флагов, вызывает обслуживание
пула `0048D210` и изменяет записи частиц. Это предшествует
[CPU draw](ballistic-cpu-draw.md); источник готового центра у ветви +AE
нельзя заменять баллистическим shader только по названию эффекта.

## Часы и режимы

Вход — один float delta. Метод записывает его в ParticleSystem+A0,
прибавляет исходный delta к текущему времени +A4 и сохраняет новый clock
как float. Если delta больше параметра +BC, только поле +A0 ограничивается
значением +BC. Часы уже продвинулись на полный delta.

| Флаги | Дальнейшая операция |
| --- | --- |
| +AC ≠ 0, loop | Если clock > +BC, вычесть +BC один раз; затем возврат |
| +AC = 0, +AE = 0 | Один `0048D210(clock, effectiveDelta)`, без интеграции записей |
| +AC = 0, +AE ≠ 0 | Несколько maintenance/integration шагов |

В loop-ветви нет ни удаления истёкших записей, ни вызова modifiers,
ни изменения записанной позиции/скорости этим методом. При превышении
нескольких периодов часы могут остаться больше +BC после одного вычитания.

## Кто вызывает обновление

Общий `spParticleSystemManager` в `0045A390` обходит список: manager+1C указывает
на sentinel, next находится в +0 узла списка, указатель на ParticleSystem — в +8.
Каждый элемент получает `0048D450` с float delta из `EngineCore+7C`.
Глобальный указатель EngineCore находится в `00755274`; при его отсутствии
менеджер вызывает lazy factory `0041CB30`.

Игровой `wxParticleManager` в `005A1170` использует тот же список, но может
заменить полный вызов одной записью `ParticleSystem+A4 = float(A4 + delta)`.
В этой ветви +A0 сохраняется, loop-время не оборачивается, пул и записи не
обслуживаются. Для конечных обычных входов наблюдаются следующие условия:

| Условие | Действие |
| --- | --- |
| Указатель на ParticleSystem в списке равен нулю | Перейти к следующему элементу |
| ParticleSystem+5C не содержит RenderNode | Продвинуть только часы |
| Duration +B8 ≥ 0 и Duration + lifetime(+BC) ≤ clock(+A4) | Продвинуть только часы |
| Дальность достигла порога и Node+3C совпадает с EngineCore+18 | Продвинуть только часы |
| Остальные исследованные входы | Вызвать `0048D450(delta)` |

Дальность — квадрат расстояния между manager+28/+2C/+30 и мировой позицией
узла +74/+78/+7C. Порог равен 6 250 000, а при состоянии игры `0x21`,
возвращённом оригинальным `005954E0`, — 42 400 000. Равенство относится к дальней
ветви. Если все три компонента позиции менеджера близки к нулю по оригинальному
сравнению, проверка дальности пропускается. Проверка окончания испускания
происходит раньше и этим исключением не отменяется.

Ещё перед проверкой Duration код читает бит `0x200` в Node+B0. Когда бит сброшен,
он вызывает virtual slot +10 у вложенного объекта Node+B4; ненулевой AL также
ведёт к продвижению только часов. Назначение этого предиката здесь не установлено.
В завершённых проверках менеджера бит был установлен, поэтому неизвестная
виртуальная ветвь не подменялась и не выполнялась. Входы менеджера, владельцев,
узлов и looping-систем были явно подготовлены; запуск полного игрового кадра
и восстановление класса `wxParticleManager` этим не заявляются.

## Внутренние шаги +AE

Поле +B0 задаёт коэффициент числа шагов; constructor записывает 30.
Это отдельное поле от emission rate +B4. В исследованном конечном диапазоне
с неотрицательным результатом целочисленного преобразования:

```text
N = max(1, trunc(B0 · effectiveDelta))
frameStart = float(clock − effectiveDelta)
stepDelta = float(effectiveDelta / N)
для i = 1..N:
    maintenance(float(frameStart + i · stepDelta), stepDelta)
    обновить каждую оставшуюся активную запись
```

При B0=0 также выполняется один шаг. Большой отрицательный результат
преобразования в оригинале используется как unsigned count; общая
аналитическая реализация отвергает его и ограничивает число шагов.

Для записи P.xyz, V.xyz, BirthTime, T интеграция семантически равна:

```text
u = (frameStart − BirthTime) / T
P += stepDelta · V
V += float(0.01) · ((1−u) · AccelBegin + u · AccelEnd)
```

Позиция меняется раньше скорости. u вычисляется от одного frameStart
**на каждом шаге**, а не от времени очередного maintenance.
Коэффициент изменения скорости — `0x3C23D70A`, а не stepDelta.
Поэтому даже delta=0 выполняет один шаг с неизменной позицией и новой
скоростью. Увеличение числа шагов меняет суммарную прибавку скорости.

Оригинальный x87 код сохраняет отдельные промежуточные результаты в float,
причём порядок stores различается у x/y/z. Общая реконструкция сохраняет
эти точки округления для координат и ускорений. Побитовое соответствие
всех возможных x87-входов не заявляется.

## Удаление из активного кольца

`0048D210` начинает с предыдущего узла от boundary +94 — последней активной
записи. Она удаляется из активной части, только если
`BirthTime + T < maintenanceTime`. На точной границе времени жизни запись
ещё остаётся. Удаление уменьшает active +98, увеличивает free +9C
и сдвигает boundary на предыдущий узел; данные записи не очищаются.

Проверка идёт назад до первой неистёкшей записи. В произвольно переставленном
входном кольце истёкшая запись в начале может остаться активной, если последняя
ещё жива. Это не общий фильтр по возрасту; нельзя заменять его удалением
всех истёкших элементов независимо от порядка.

После удаления функция может испускать новые частицы при ненулевом +58
и вызывать список modifiers через virtual slot +24. Эти ветви не включены
в ограниченную реконструкцию ниже. Отдельно восстановлен
[расчёт накопителя и запроса испускания](particle-emission-budget.md).

## Общая реализация и её границы

[spParticleCpuUpdate.h](../../../Sparkplug/Analysis/PC/spParticleCpuUpdate.h)
восстанавливает завершённое обновление **существующих активных записей**
при отключённом испускании (+58=0) и пустом списке modifiers (+84=0).
Входной vector представляет логический обход от first по next; выход
сохраняет bytes-поля выбывшего суффикса и сообщает оставшийся active count.
Физические указатели кольца, владение CPU/GPU-буферами, callbacks и полноценный
`spParticleSystem::Update` этим интерфейсом не заменяются.

Host guards требуют конечных значений, положительного +BC и времени жизни
каждой записи, не более 1024 записей и 128 внутренних шагов. При отказе
выход сохраняется. Сравнение включает следующий оригинальный draw, upload
и indexed call с явно заданными COM-ответами; это не запуск игровой сцены
и не доказательство результата GPU-отрисовки.
