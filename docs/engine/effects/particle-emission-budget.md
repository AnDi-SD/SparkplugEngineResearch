# PC ParticleSystem: накопитель испускания

В `0048D210` испускание следует после удаления истёкших записей.
Байт ParticleSystem+58 разрешает эту часть. При +B8 ≥ 0 испускание
прекращается, когда переданное время больше +B8; равенство ещё разрешено.
При отрицательном +B8 этот временной предел не применяется.

Обозначим накопитель +A8 через A, emission rate +B4 через R,
параметр +BC через T. Аргумент delta уже обработан
[внешним update](particle-cpu-update.md). Для конечных значений,
R ≥ 0 и неотрицательного результата trunc в uint32-диапазоне:

```text
E = min(A + delta, T)       // ещё в расширенной точности x87
A = float(E)               // FST не снимает E со стека x87
requested = trunc(E · R)
producer(requested, time)
A = float(A − requested / (R > 0 ? R : float(0.000001)))
```

Нижнего ограничения накопителя нет. Вызов producer выполняется даже при
requested=0. Когда gate или длительность запрещают испускание, накопитель
эта ветвь не меняет. Modifier callbacks следуют отдельно.

## Число запрошенных и созданных частиц

`0048C400` ограничивает запрос числом свободных записей. При free=0
он естественно возвращает ноль до sampler, transform и изменения записей.
Но `0048D210` вычитает из накопителя **исходный requested**; возврат producer
в этой формуле не используется. Поэтому заполненный пул не сохраняет весь
запрос как отложенный долг для следующего кадра.

Порядок округления существенен. Для float A=0.1, delta=0.7, R=5 значение E
чуть меньше 0.8: requested=3, хотя сохранённый A уже равен float(0.8).
Если вычислять запрос из сохранённого float, получается 4.
Аналогично A=0.9, delta=0.1, R=10, T=1 даёт requested=9 при сохранённом A=1.
Перенос float-store в формулу запроса меняет поведение оригинала.

## Общая реконструкция

[spParticleEmissionBudget.h](../../../Sparkplug/Analysis/PC/spParticleEmissionBudget.h)
возвращает необходимость вызова producer, requested count, значение
накопителя перед producer и после списания. Он не создаёт частицы.
Исполнение целой операции подтверждено для заполненного пула без
истёкших записей: оригинальный producer возвращает ноль, сохраняет +A8,
а следующий draw проходит через обычную загрузку и indexed call.

В [runtime ParticleSystem](../../../Sparkplug/Code/Sparkplug/spParticleSystemRuntime.cpp)
кадровое обслуживание вызывает общий producer, который также используется
loop Init. Он добавляет реальные записи в принадлежащее классу физическое
кольцо. Modifier callbacks следуют после испускания. Это конкретный исходный
алгоритм; исторические проверки заполненного пула сами по себе не являются
новой проверкой повторного испускания в этот исходник. Сравнение кадрового
producer при наличии свободного места и конкретных производных modifiers
остаётся отдельным критерием полноты. Текущая ограниченная кадровая проверка
включает запрос четырёх частиц при одном свободном слоте: одна фактически
создаётся, а накопитель списывается по исходному запросу. Совпадают физическое
кольцо, записи, все PRNG words и следующий packed draw. Это один проверенный
режим повторного испускания, не все комбинации производных modifiers.
Проверенный раньше
[loop Init](particle-loop-init-counts.md) не означает автоматически
готовность всей кадровой операции с повторным испусканием.

Host-интерфейс требует конечных входов, положительного T, неотрицательного R
и отсутствия переполнения uint32-преобразования. При отказе выход сохраняется.
Используется double-модель расширенных промежуточных значений; универсальная
побитовая эквивалентность x87 не заявляется.

## Подготовка и списание бюджета в точности PC

Участок с `0x0048D275` заканчивает подготовку перед вызовом
`0x0048D2E8`. Сумма `A + delta` сначала округляется до 64 значащих битов
x87, а `FST` в `0x0048D2B8` записывает её в binary32. Затем применяется
верхний предел `T`. Вторая запись `FST` в `0x0048D2CD` происходит даже
при совпадении байтов накопителя. Запрос получается усечением к нулю
произведения ограниченного значения в расширенной точности на `R`.

Участок `0x0048D2ED–0x0048D329` снова читает `R` и сохранённый binary32
накопитель. Он вычитает частное исходного запроса и `R`. Для нулевого `R`
используется слово `0x358637BD`. Деление и вычитание идут с 64 значащими
битами, итог сохраняется в binary32. Округление обеих точностей соответствует
ближайшему чётному (`FPCW=037F`).

[Аналитический интерфейс](../../../Sparkplug/Code/Sparkplug/spParticleEmissionBudgetPc.h)
применяет обе части к переданным сырым значениям при условии, что между
ними накопитель и `R` не меняются. Он сообщает, достигнута ли граница
вызова, а также запрос и три значения накопителя. Запись или вызов producer
через этот интерфейс отсутствуют. Действующий расчёт кадрового пути остаётся
в `spParticleEmissionBudget.h`.

Допустимы нормальные binary32 и положительный ноль с модулем не более
`2^31`, положительный `T`, неотрицательные `delta`, время и `R`, а также
усечённый запрос от нуля до `INT32_MAX` в достигнутой ветви. При отказе
выходные значения сохраняются.

Архив заполненного пула содержит фактически наблюдённые запрос и
накопитель перед producer, а также итоговый накопитель после целого update.
Для отдельных шагов многошагового update промежуточное состояние берётся
из продолжения расчёта.
