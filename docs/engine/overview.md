# Обзор Sparkplug

## Граница исследования

Цель проекта — документировать загрузку ресурсов Sparkplug настолько, чтобы независимо читать, диагностировать и визуализировать данные Winx Club: The Game. Это пока не попытка полностью заново реализовать движок или игровую логику.

Главные источники evidence:

1. байты чистых и изменённых ресурсов PC/PS2;
2. воспроизводимый вывод строгих parsers;
3. строки регистрации классов и call sites в исполняемом файле;
4. контролируемые изменения ресурса с проверкой результата в игре;
5. сравнение независимых инструментов.

## Подтверждённая слоистая модель

Наблюдаемые данные удобно разделять так:

```text
FFPS container
  └─ object directory (name, class hash, logical offset, serialized size)
      └─ SBOO object + spDataBlockSerializer fields
          └─ Sparkplug object graph
              ├─ model / mesh / render node
              ├─ material / texture layer / texture data
              ├─ node / skin
              └─ collision / bounds / shadow data
```

Из этого следует важное практическое решение: SMO нельзя надёжно читать как поиск одной vertex/index-сигнатуры. Сначала нужен контейнер и каталог, затем границы сериализованных объектов, и только потом интерпретация меша, материала или текстуры.

## Что подтверждено

- Контейнер little-endian начинается с `FFPS` и содержит абсолютное начало секции данных, её размер и число записей каталога.
- Каталог хранит именованные записи с class hash, logical offset и serialized size.
- Физический адрес объекта вычисляется как `DataStart + logicalOffset`.
- Большинство объектов начинается с `typeHash` и сигнатуры `SBOO`.
- Размер объекта каталога может включать сериализованное поддерево; соседние объекты могут быть вложены, поэтому «до следующего offset» не является корректным размером.
- Реестр уже содержит 20 подтверждённых class ID из семейств model/material/texture/scene/skin/collision/shadow/GUI.
- Для части `spMeshData` подтверждены маркеры `E0`/`E1`, triangle strip и различие serialized/runtime stride.
- Отдельный texture workflow умеет обнаруживать известные pixel layouts, применять vertex color modulation и выполнять repack.
- В PC и PS2 executable найдены эквивалентные проверки `FFPS` и поля `0x26`, а также имена классов и токены полей `spDataBlockSerializer`.
- PS2 ELF содержит баннер `Sparkplug Engine v1.0`; PC executable сохранил пути к serializer `.cpp` и идентификатор PDB.

Точные структуры и ограничения приведены в [описании SMO](../formats/smo.md) и [реестре классов](../reference/class-ids.md).

## Что пока является гипотезой

- Поле `0x10` заголовка похоже разделяет варианты сериализации/платформы, но не доказано, что это номер версии.
- Значение поля `0x08` неизвестно.
- Не все состояния материала получили подтверждённые D3D9-имена и runtime-семантику.
- Связь scene nodes, transforms, skins и animations пока не восстановлена целиком.
- Часть каталогов в рабочей папке игры могла устареть после раннего texture repack; это не следует считать штатным поведением оригинальных файлов.

## Соседние форматы

Текущая рабочая модель:

| Формат | Наблюдаемая роль | Статус |
|---|---|---|
| `SMO` | объектный ресурс: геометрия, материалы, текстуры и связанные классы | активно исследуется |
| `SAN` | анимационный ресурс, также использующий `FFPS` | структура не завершена |
| `ANM` | сопоставление состояний/анимаций | рабочая гипотеза |
| `SPT` | игровые компоненты и ссылки на ресурсы | рабочая гипотеза |
| `SPL` | размещение экземпляров/шаблонов уровня | рабочая гипотеза |

Просмотр отдельного SMO — правильный первый срез. Полноценная сцена потребует слоя SPT/SPL и анимаций поверх общего serializer.

## Следующие доказательства

Текущая работа — разметить FFPS-проверку в PS2 ELF и восстановить serializer по xrefs. Когда появятся pristine PC/PS2-наборы, обязательной контрольной проверкой станут локальные SHA-256 manifests и повтор одного scan: это отделит свойства формата от последствий старых экспериментов. Приоритеты перечислены в [открытых вопросах](../../research/open-questions.md).
