# Манифест исследования Sparkplug

Постоянные рабочие правила, обновлены 8 сентября 2026 года по поручению
пользователя. Применяются к следующим циклам исследования. Датированные
отчёты и evidence manifests сохраняют условия и результаты своих экспериментов.

## Цель и приоритет

Для переработки ядра Viewer приоритет — прямое подключение уже восстановленных
C++-классов из `Sparkplug/` через небольшой версионный C ABI. Сначала использовать
этот общий код; перенос на C# допускается при конкретном техническом препятствии.
Адаптеры приложения и невосстановленные зависимости описываются явно. Это правило
не требует восстановления всего renderer/движка до внедрения полезного среза.
Интерфейс Viewer перерабатывается отдельной задачей.

Текущая цель — корректная работа существующих инструментов. Исследовать реальные
классы, поля и алгоритмы только в объёме, нужном для конкретных команд Viewer,
Exporter, Importer, LVLcreator, TextureTool и SAN-конвертера. По уточнению
пользователя 8 сентября класс разрешено восстанавливать частично и дополнять
по мере разработки. Подробная [граница работы и критерии функции](tool-driven-research-scope.md)
имеют приоритет над прежней целью полного восстановления движка.

PC остаётся основным направлением; PS2 исследуется параллельно по относящимся
к текущему софту общим вопросам. Обе платформы имеют независимый evidence.
[Широкий контракт](pc-smo-san-completion-contract.md), каталог 279 PC-классов
и семь engine gates сохраняются для долгосрочного учёта знаний. Они не являются
обязательными условиями выпуска инструментов и не задают их процент готовности.
Исторические проценты и веса не меняются ради более быстрого роста показателя.

В [native-work-items.json](../../research/native-work-items.json) выбираются
только активные операции инструментов. Сначала проверить текущий shared code
и применимость уже полученного evidence; при достаточном знании переходить к
интеграции. Новая неизвестная зависимость исследуется в рамках её реального
влияния на команду. Отложенные части класса не мешают завершить проверенный срез.

После завершения нужного среза его широкая задача не остаётся в активной
очереди только из-за `status: partial` у класса. В CP136 такие задачи связаны
через `resumeForOperations` с фиксированными ID измерителя и переведены в
отложенное планирование. Каждый вызов `native_workbench.py queue` читает
текущую assessment и перепроверяет hashes evidence. Неготовая операция или
`needs_review` возвращает только связанные задачи в `operation-review`,
без записи нового статуса класса. Отсутствующее подтверждение не скрывает
работу. Явно активная задача по новому дефекту остаётся активной даже при16/16.
PS2-связь обозначает повод проверить пользу аналога для PC, не покрытие PS2.

## Совместное исследование PC и PS2

По поручению 8 сентября PS2 имеет собственные задачи в рабочей очереди.
Основная задача цикла должна продвигать PC-инструмент; рядом выбирать
ограниченную PS2-задачу, полезную той же операции или поддерживаемому PS2-входу.
На планировании проверять обе очереди. Отдельная PS2-задача не создаётся только
для формального распределения времени между платформами.
Для общей функции, закрытой PC-защитой, сначала изучать доступный PS2-аналог,
если его соответствие можно установить по registration, callers, полям или
диагностике. Уже доступные PC-функции не разбирать повторно на PS2 без нового
вопроса нужного инструменту либо его поддерживаемому PS2-сценарию.

Последовательность: PS2-контракт и его evidence → сопоставление с PC → проверка
различий → реализация и короткое original/source сравнение на целевой платформе.
Совпадение class ID и наследования не доказывает равенство layout, virtual slots,
округлений или поведения. Записывать общую логику и платформенные различия
рядом, чтобы не проводить два независимых полных исследования одного алгоритма.
PS2-результат сохраняется даже при незакрытой PC-проверке; PC score от него
автоматически не повышается.

Активный PS2-срез — нужные serializer/field/reference вопросы. Visibility,
collision/navigation runtime и симуляция частиц отложены до конкретной команды,
которой они нужны. Direct3D и runtime DX paths изучаются только при доказанной
необходимости для текущего софта. Связи `companionPcItems` задают пользу для PC,
а не обязательный порядок выполнения или доказанное равенство функций.

Независимые чтения и проверки двух платформ можно выполнять одновременно
при отдельных выходных файлах и отсутствии общих изменяемых данных. Бюджет
около 1 ГиБ и выбранный по измерениям параллелизм общие для обеих платформ.
Это правило не создаёт второй комплект из четырёх workers и не означает,
что нынешний runner автоматически чередует платформы.

## Короткие проверочные выборки

После обычной правки выбирать через существующие индексы базы примерно
5–15 файлов, покрывающих затронутые различия: классы, формы полей, форматы,
размеры, ссылки и существенные ветви. Это ориентир, а не обязательные десять
файлов для любого алгоритма. Сначала один новый представитель; расширение
обусловлено новым поведением или обнаруженным расхождением. Для выбора
использовать существующий `native_specimens.py` там, где его discriminators
подходят; универсальный подбор для всех подсистем пока не реализован.

Сохранять manifest выборки с причинами выбора, хэшами и явно не представленными
вариантами. Добавлять необходимые synthetic boundary/failure cases; они
учитываются отдельно от реальных файлов. Полный корпус не сканировать после
каждой правки. Расширять регрессию при изменении общего контракта, расхождении
или новой зависимости; уже успешную полную регрессию без изменений не повторять.

Повторный результат допустимо использовать только при неизменном контракте
его зависимостей: целевой EXE/платформа, входные bytes, соответствующий source
и executable, harness/fixture, параметры/seed/profile и зависимости сборки.
Один хэш файла этого не доказывает. При неизвестных зависимостях выполнять
проверку заново. Автоматический общий cache результатов пока не реализован.
Сокращённый набор или cache вводить по замеру полного прохода с учётом цены
подбора, сохраняя проверку заявленных различий. Число assertions само по себе
не показывает, где тратится время.

## Оптимизация на протяжении всей работы

Постоянно искать и применять способы ускорения без отдельного согласования
обычных исследовательских решений. При выборе следующего шага оценивать,
сколько новых контрактов или общих препятствий он позволяет закрыть за время
работы. Прежде чем повторять анализ, использовать существующие паспорта,
индексы, декомпиляцию и результаты проверок.

Сначала проверять одного представителя нового пути; расширять набор при новой
ветви, ошибке или отличии формата. Независимые чтения объединять, дорогие
повторяемые вычисления кэшировать с ключами по хэшу входа и версии алгоритма.
Новая организация стенда должна дать проверяемый пробный результат; отдельно
записывать время, память и оставшиеся ограничения. Два удачных опыта не
доказывают ускорение всей работы в несколько раз.

Когда whole-проверка локализует расхождение внутри одного helper, сравнивать
его напрямую на небольшом batch, сохраняя исходные caps и реальные аргументы.
Снимать промежуточные значения read-only observers и исправлять первый
отличающийся этап. [CP112](native-pc-texture-block-optimizer.md) так отделил
арифметическое расхождение от загрузки сцены и проверил сотни случаев за секунды.

После 30 минут без нового факта или уточнения причины остановки записать
блокер и выбрать независимый полезный шаг. После правки выполнять затронутые
проверки; полную регрессию — после связного блока, изменения общего контракта
или при закрытии цикла. Успешные проверки без новой причины не повторять.
Учёт и сводки обновлять пакетно, оставляя краткую запись каждого нового факта.

## Память

На машине 8 ГБ RAM; пользователь разрешил выделять исследованию примерно
**1 ГиБ (1 073 741 824 байта) суммарно**. Это рабочий бюджет всех одновременно
запущенных исследовательских процессов, включая дочерние процессы, эмуляторы,
кэши и сборку, а не размер отдельной guest arena. Учитывать текущую доступную
память; при давлении на систему уменьшать параллелизм и кэши. Не резервировать
весь бюджет заранее. Этот документ задаёт правило работы, а не лимит ОС.

Увеличивать явные профили памяти и кэши по необходимости в пределах этого
бюджета, без дополнительного вопроса пользователю. Размер нового профиля
выбирать до создания свежего guest; проверять границы и пересечения mappings,
учёт владельцев и освобождений, записывать профиль и peak в evidence.
Сейчас реализованы heap 64 КиБ, 128 КиБ и 256 КиБ; их исторические результаты
не пересчитываются. Новые размеры требуют соответствующей поддержки стенда.
Allocator fixture по умолчанию ограничивает один запрос 32 КиБ; отдельный
явный `guest_max_allocation_size=65536` допускает 64 КиБ в пределах общей arena.
Это позволяет исследовать подтверждённый startup pool request 57 344 байта;
суммарный bump bound и отказ до записи за пределами памяти сохраняются.
Проверки pristine EXE и ограничения доступа guest сохраняются; stopped state
не возобновляется, неизвестное поведение не заменяется успешной заглушкой.

Для новых опытов полного файла разрешён отдельный профиль `file`: 1 000 000
инструкций и 8 секунд на вызов, внешний процесс по-прежнему ограничен 30 секундами.
Профиль выбирается до создания guest и фиксируется в результате. Прежний `micro`
остаётся по умолчанию: 100 000 инструкций / 2 секунды. Это изменение методики от
7 сентября, после поручения ускорять исследование: короткий бюджет нескольких
объектов нельзя принимать за доказательство ошибки полного файла. Ранее
остановленные пробы сохраняются; новый опыт создаёт свежий guest под другим
именем, с записанной причиной и отдельным результатом. При новой остановке
сначала выяснить причину, не увеличивать предел автоматически.

8 сентября для проверки полного небольшого персонажа добавлен явный профиль
`character`: 4 000 000 инструкций / 16 секунд на вызов, heap 256 КиБ,
процесс 30 секунд. Вход специального probe ограничен 32 КиБ, 256 объектами
и двумя текстурами до 32×32. Причина — штатный разбор сохранённых узлов
скелета исчерпал миллион инструкций без диагностики повреждённого файла.
Новый профиль выбирается до создания guest; `micro` и `file` не изменены.

## CPU и GPU

Для Ryzen 2700 доступны 16 логических потоков, для RTX 3070 — 8 ГиБ VRAM.
Использовать независимые задачи параллельно, пока суммарная память и отзывчивость
машины позволяют. Число процессов выбирать по измерениям, а не по числу
логических потоков. GPU разрешено использовать для подходящих массовых
вычислений; сначала сравнить время всей операции с CPU, включая подготовку
и передачу данных. Проверять совпадение результатов и фиксировать backend.
Эмуляция последовательной x86-цепочки сама по себе на GPU не переносится.

После [замера CP110](native-parallel-profiles.md) для reviewed независимых
профилей использовать `native_workbench.py run PROFILE --workers 4`, если
другие исследовательские процессы не исчерпывают общий бюджет. В10 texture
случаях это сократило время29,44→10,74 с при sampled working set340,49 МиБ.
Runner требует `parallelSafe:true` у каждого child, сохраняет30-секундные
пределы и не запускает следующую группу после ошибки. Не переносить эту
настройку на профили с общими выходами без проверки независимости.

После [CP117](native-pc-instruction-cache.md) PC harness по умолчанию использует
fast PE mapping и page cache с invalidation на guest/host writes. В27 fresh
whole-operation сравнениях это дало1,86–2,46 раза при точных результатах.
При изменениях harness проверять не только итог, но и самомодификацию кода,
instruction counts и все прежние caps; reference bytes mode сохранять для замеров.

Для повторяемого C++-эталона использовать bounded batch input, когда каждый
случай полностью создаёт своё состояние и явно задаёт seed/зависимости.
[CP122](native-pc-particle-batch-speed.md) сократил36 запусков source executable
до одного и ускорил полный процесс ещё в1,26–1,55 раза. Сохранять одиночный
режим для контрольного сравнения, ограничивать число строк/объём ответа,
проверять одинаковые results, PRNG state и native instruction counts.
Объединение завершённых независимых случаев не разрешает возобновлять
остановленный guest или переносить непроверенное состояние между случаями.

## Сохранение работы и публикация

Делать небольшой осмысленный commit после каждого законченного проверенного
блока; ориентир — каждые 30–60 минут активной работы и обязательно перед
крупной переработкой и завершением цикла. Если блок ещё не завершён, сохранить
честно обозначенный WIP checkpoint с описанием непроверенного остатка.
Не накапливать несколько дней изменений без commit.

Перед отправкой на GitHub проверить документацию, ссылки, состав изменений
и необходимые тесты. Для файлов с evidence-хэшами сохранять точные байты:
[.gitattributes](../../.gitattributes) отключает преобразование окончаний строк
в исследовательских каталогах. Исторические manifests не переписываются
для соответствия новым версиям исходников или дополненным dossiers.
По текущему поручению пользователя исходники, исследования
и документация публикуются в существующем репозитории; выпуск release —
отдельная задача. Игровые файлы, EXE, извлечённые payloads, локальная база
и временные сборки остаются вне Git по [corpus policy](corpus-policy.md).
Пути в `local-data/` и `.codex-tmp/` в отчётах обозначают локальные артефакты,
которые не появятся при обычном клонировании репозитория.
