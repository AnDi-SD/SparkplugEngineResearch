# Remix Skin API: парная проверка и гипотеза шага весов, 13 сентября 2026

Закрытый изолированный `skin-api-v4` подтверждает ошибочную деформацию при **двух–четырёх влияниях на вершину**: все восемь парных контролей устойчивы, одинарное влияние проходит обе позы, остальные шесть случаев — FAIL. Силуэт ошибочного результата согласуется с чтением весов с шагом одного `float` на вершину. Это вывод из изображений и имеющихся исходников renderer; идентичность этих исходников установленному бинарнику не доказана. Исправление runtime и работоспособность игровых персонажей здесь не заявляются.

Проверены уже завершённые эксперименты с синтетическим треугольником из трёх вершин. Автор отчёта новых GPU-запусков не выполнял, игру и её ресурсы не использовал, проверочный алгоритм fixture не изменял. Источник: [manifest](../../research/winx-remix-skin-api-paired-checkpoint-2026-09-13.json), [199 файлов evidence](../../local-data/rtx-remix/skinning-fixtures/paired-checkpoint-v1/evidence.json), включая замороженные C++, EXE, конфигурацию, журналы, BMP и исходники анализа. В v4 слева всегда рисуется уже деформированный CPU-эталон, справа — проверяемый экземпляр. Оба проходят одну камеру и один Present; перенос эталонной маски на 288 пикселей определён геометрией сцены, без подгонки. Сохраняются исходные пороги: контроль IoU ≥ 0,98, совпадение с проекцией ≥ 0,90, skin с одновременным эталоном ≥ 0,97. Контроли дают 0,997667–0,998779. Временной A/A продолжает колебаться, поэтому старые v2/v3 FAIL сохранены и не превращены задним числом в доказательство ошибки skin.

Последние два столбца — отдельная проверка гипотезы, не новый критерий PASS. Аналитические полигоны не воспроизводят точную растеризацию и jitter: даже B1 даёт около 0,95–0,97. Параметры по полученному skin-изображению не подбирались. [Сравнение всех восьми силуэтов](../../local-data/rtx-remix/skinning-fixtures/paired-checkpoint-v1/silhouette-hypothesis.png) просмотрено: белая маска — фактический skin, голубой контур — гипотеза, розовый — правильная деформация.

В замороженном `rtx_remix_api.cpp:1022` веса копируются полным массивом, но `RasterBuffer` получает stride `sizeof(float)`; `rtx_geometry_utils.cpp:300` передаёт этот шаг в skinning. `skinning.h:67–114` тогда читает `weights[v+j]` для первых B−1 влияний вместо `weights[v*B+j]`, последнее вычисляет последовательным вычитанием из 1; индексы костей остаются `bones[v*B+j]`. Существенен его же фильтр `blendWeight > 0`: у вершины 2 при B3/B4 остаток −0,25 отбрасывается без нормализации, и Z становится 6,25 вместо 5. После этого применяется обычный world-перенос `[1.5, −0.2, 0]` и исходная проекция. Первая гипотеза без этого фильтра объясняла не все случаи; её результаты отдельно сохранены как `skin-api-v4-hypothesis-v1`, уточнение — `hypothesis-v2`.

Веса и индексы взяты из `mesh_input`, позы и арифметика — из замороженного fixture; правильный пересчёт float32 совпадает с записанными `expectedPositions` с максимальной разницей `4,965e−10`, в пределах девяти значащих цифр журнала. Исходники renderer сняты с локального дерева commit `b81a7b566b1eeb9edb4dc2b3c9d3972e0f253ad4`; они являются основанием гипотезы, а не доказательством кода установленного renderer. Для трёх вершин возможна малая CPU-ветка renderer с той же функцией skinning; выполнение именно compute shader не установлено.

Во всех трёх запусках использованы одинаковые client `4BB7BB4F…783E`, server `A99FEF75…E4F`, stock renderer `F7C31082…09F`; полные SHA256 находятся в manifest. V4: C++ `6C8FBABC…516C`, EXE `D14A29A8…EF96`. Процессы закрылись с кодом 0 без watchdog timeout, server audit завершён `queue_exit_normal`, лимит журнала не достигнут. Ошибок API, invalid handles и чужих draw/present нет. Число SUCCESS точно равно `(кадры − 60 прогрев − 3 завершение) × экземпляров API`, где экземпляров 1 для v2/v3 и 2 для v4. `early=0` ожидаем: каждый кадр сначала содержит обычную D3D-панель. Server SUCCESS означает возврат API после постановки работы в renderer, не завершение GPU и не доказательство правильной деформации.

Bridge сообщает успешную очистку, однако во всех запусках остаются сообщения ожидания Present semaphore при старте и `41 common device objects were not disposed of` при выходе; также сохранены предупреждения о null sampler и swapchain при завершении. Полная корректность времени жизни ресурсов этим тестом не закрыта. Следующий минимальный шаг — проверить целевое исправление шага тем же парным fixture с прежними порогами; до такой проверки прямую weighted-подачу B2+ считать незавершённой.
