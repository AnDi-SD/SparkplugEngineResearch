# LightController, ColorFuncEval и ссылки LightEntity

Блок 40 цикла до 11 сентября 07:30 МСК. 60 оригинальных вызовов, по 30
на платформу, все завершились с первого раза: пилот 6 / 0,409668 s,
общий пакет 54 / 3,594292 s. Это проверка поведения методов, а не новые
C++ реализации или полностью восстановленные классы.

## Обновление цвета

`spLightController`: PC `42F930`, PS2 `11A170`. При ненулевом указателе
`+6C` вызывается настоящий вложенный `spColorFuncEval` по `+1C`, затем
его настоящий `spFunctionEval` по `+18`. Таблицы вложенных объектов:
PC `6DE684` / `6EA9AC`, PS2 `48CD90` / `48CDF0`. Подтверждены записи
конструктора, но конструкторы в этом пакете не исполнялись.

Скалярные типы 0 и 7 возвращают `yOffset +24`, не меняя время `+10`.
Выборка значений −4, −1, −0,5, 0, 0,5, 1, 4 проверяет вес
`clamp((value + 1) / 2, 0, 1)`. Цвета `FC804000` и `2040C080` имеют
каналы, кратные четырём: все произведения для выбранных весов целые.
Семантика дробного PS2 `CVT.W.S` этим пакетом не устанавливается.
Каждый канал двух цветов масштабируется отдельно, затем складывается
с сохранением младшего байта. Промежуточный packed цвет прочитан
наблюдателем после настоящего sampler; возвраты helper не подменялись.

PC записывает RGBA float по `+C4..D0` и добавляет бит 8 в `+B0`.
PS2 записывает RGBA по `+D0..DC`, бит 8 — в `+B4`. PC умножает байт
на исходную float константу `6DCA9C`, PS2 делит на 255. Каждый результат
сверяется с арифметикой своей платформы; побитовое равенство платформ
не предполагается. Direct update не читает поле enabled `+10`; это
не доказательство поведения внешнего dispatcher.

Нулевой `+6C` завершает метод без вычислений и записей. Целевой Light
представлен буфером с доказанными полями: его виртуальные методы не нужны.
Нормальная фабрика PS2 Light и отображение света здесь не проверяются.
Регистрация PS2 Light имеет factory 0; это не доказательство абстрактности.

## Ссылки LightEntity

Освобождение `431050` / `150B50`: уменьшает 16-битный refcount `+8`
объекта из собственного `+14`, затем очищает этот указатель. Проверены
null и счётчик 2→1; три Node-слота `+30/+40/+50` явно нулевые.
Ветка удаления объекта при достижении нуля и обработка Node не проверены.

Присваивание `419D00` / `14E150` работает с собственным `+18`:
совпавший указатель ничего не меняет; иначе старая ссылка уменьшается,
новая увеличивается, указатель заменяется. Проверены null→null,
null→объект, тот же объект, замена и объект→null с двумя заполнениями
окружения. Счётчики выбраны так, чтобы не вызывать неизвестный destructor.

## Доказательства и границы

У каждого опыта сравниваются все 4 KiB окружения объекта, целевого света
и ссылок с ожидаемыми байтами. На PS2 сохранены исходные инструкции,
проверены SP/RA, S0–S2, F20 и верхние 64 бита GPR после возврата.
Использован ранее квалифицированный профиль стековых SQ/LQ; CPU модель
не расширялась. Аппаратное освещение, произвольная EE FPU арифметика,
другие формы скалярной функции и полный lifecycle остаются открытыми.

Уточнение разведочного capture: PC `spLightController` имеет здесь восемь
слотов. Подписи `spLightController-pc-8..11` пересекают соседнюю таблицу
ColorFuncEval с `6DE684`; они не используются как дополнительные методы
LightController. Исходный capture сохранён, неверная подпись не выдаётся
за семантическое доказательство. Попытка capture нулевой PS2 Light factory
была отклонена до гостевого исполнения; продолжение не имитировалось.

Баллы +5: LightController и LightEntity на обеих платформах, дополнительно
PS2 ColorFuncEval 15→20. PC ColorFuncEval уже имел 80 и повторного балла
не получает; базовый FunctionEval также не получает повторного зачёта.
