# GUIManager: порядок смены фокуса

11 сентября 2026. Блок27 цикла до07:30 МСК. Класс `spGUIManager`,
class hash73634C2D. [Предыдущий контракт engine core](native-engine-core-remainder-2026-09-10.md)
подтверждает PC factory452380/getter451C00/размер50 и независимый PS2
factory165130/getter163FC0. Новый опыт вызывает напрямую focus setter
**PC451AD0 /PS2163FD0**, ранее достигнутый из настоящего EditBox Notify.
Startup менеджера этим опытом не выполняется.

## Последовательность исходного метода

1. Прочитать прежний указатель `manager+4C`. Если он ненулевой, вызвать
   настоящий Notify объекта с envelope `[17,0,0,0,manager,0,0,0]`.
2. После возврата старого Notify записать новый указатель в `manager+4C`.
3. Если новый указатель ненулевой, вызвать его Notify с
   `[16,0,0,0,manager,0,0,0]`, затем вернуть управление.

На входе старого Notify поле4C ещё содержит прежний объект; на входе нового —
уже новый. Никакой проверки равенства указателей нет: для `A→A` последовательно
приходят17 и16. Null→null,Null→A,A→null проходят предусмотренные ветви.
На исследованных путях manager не изменяет reference counts объектов.
Повторный вход из Notify и произвольные действия иных callbacks не проверены.

В [реальном EditBox Notify](native-gui-message-routes-2026-09-11.md) enabled0
означает пропуск16/17. Сам менеджер это состояние не проверяет: отключённый
объект всё равно может оказаться в его поле4C. При enabled!=0 EditBox меняет
highlight0/1, затем вызывает собственный refresh. В этих случаях опыт
останавливается на настоящем refresh4369A0/169820, не подставляя возврат:

| Где остановились | Состояние manager+4C | Собственная запись EditBox |
| --- | --- | --- |
| Refresh прежнего объекта после17 | Прежний объект | Старый highlight0 |
| Refresh нового объекта после16 | Новый объект | Новый highlight1 |

Для полного возврата использованы реальные Notify отключённого EditBox,
а также явно объявленные диагностические receivers `spGUIObject`/`spWidget`,
которые не обрабатывают16/17 собственным refresh. Это не утверждение, что
все такие receivers используются обычным UI игры как поля ввода.

## Проверка и границы

14 входов на платформу:28 original executions,16 полных возвратов,
8 old-refresh boundaries и4 new-refresh boundaries. Зафиксированы38
настоящих Notify entries с полными восемью словами сообщения и полем4C
на момент входа. Пилот6:0,405s; пакет22:1,569s; все прошли с первого раза.

Guard16 КиБ покрывает manager и оба receiver целиком. Их vtables взяты
из pristine class catalog; семантику Notify выполняет исходная игра.
Manager — literal input прямого метода, его неиспользуемая vtable не выдаётся
за созданный factory объект. PS2 использует исходные SQ/LQ кадры и возвращает
caller SP/RA/S0/S1 в полных случаях; original code bytes не меняются.
PC protected entry не реконструирован по линейному мусору: порядок сообщений
и записи подтверждён реальным выполнением и независимо PS2 инструкциями.

Открыты настоящий ввод,GUI tree,renderer,полный активный EditBox refresh,
reentrant callbacks и обычный manager startup. Новых C++-классов нет;
GUIManager не считается полностью изученным. Оценка повышена PC20→25,
PS215→20 за подтверждённый focus contract. Баллы остальных участвующих
классов повторно не начисляются.
