# PC shader resources: исходник, программа и численный результат

12 сентября 2026. Разобраны **9 файлов / 11 shader-записей** из установленной
игры. Через общие восстановленные классы подготовлены и скомпилированы
**165 вариантов**, ошибок компиляции нет. Все **16 программ**, сохранённых
в последнем прогоне Гардиния 1 → Алфея → Домино → Гардиния 1, получили точное
соответствие по исполняемым инструкциям. У девяти generated-программ также
полностью совпали таблицы констант; у семи standalone таких таблиц нет.

Это исследование исходных shader-ресурсов и их потребителей. Новых оригинальных
PC EXE вызовов под эмулятором и нового покрытия классов здесь не заявлено;
PS2 не проверялась. Исправлена доказанная ошибка нашего современного GLSL
backend Viewer. Установленная Winx/Remix DLL этим блоком не изменена.

## Воспроизводимая цепочка

`analyze_pc_shader_contract.py` читает исходные ресурсы, передаёт выбранные
ключи в `SparkplugShaderCompileTests --source-batch`, компилирует результат
через системный Microsoft SDK и сравнивает его с сохранённым D3D9 bytecode.
Собственный Python-код задаёт конечную выборку входов и обслуживает API;
построение текста не дублирует игровую логику:

- `spPCShaderManager::BuildSourceInputsForAnalysis` специализирует ключ;
- `spPCEffectTemplate::BuildShaderSourceForAnalysis` собирает header,
  declarations, code и вставку у исходного маркера;
- `spDXShader::LookupParameterTypeForAnalysis` определяет смысл имён.

Общие методы ранее проверены по оригиналу:
[ключ](native-pc-shader-manager-key.md),
[генерация](native-pc-shader-generation.md),
[константы](native-pc-shader-constants.md),
[обработка обоих RFX](native-pc-rfx-corpus.md).
Новые режимы CLI — собственная исследовательская обвязка, не имена API игры.

Финальный результат:
`local-data/results/pc-shader-contract-20260912-v3/report.json`.
Полная операция заняла **3,513 с** на этой машине, без запуска игры или GPU.
Время предварительной сборки общей библиотеки в это число не входит.
Извлечённые исходники, бинарные шейдеры и SDK DLL остаются вне Git.

SDK — `C:/Windows/System32/d3dx9_24.dll`, SHA256
`1EC422BD6421C741EEF57847260967F215913649901E21DD9C46EB1B3BB10906`, flags=0.
Он сообщает compiler `9.05.132.0000`; игровые программы содержат creator
`5.04.00.2904`. Равенство установлено после удаления только комментариев
дизассемблера: сохранены все инструкции, операнды, объявления и `def`.
Полное равенство исходных bytecode bytes учитывается отдельно; metadata
компилятора не объявляется одинаковой. Таблицы констант совпали полностью.

Пилот с `d3dx9_31.dll`, flags=0, также точно воспроизвёл программу №9.
`d3dx9_43.dll`, flags=0, отверг запись в глобальные переменные старого HLSL;
compatibility flag позволил компиляцию, но не дал того же кода в этом пилоте.
Смена компилятора зафиксирована явно, исходник ради неё не переписывался.

## Все исходные программы

Формулы ниже описывают исходные выражения; ограничения старых GPU-регистров,
клиппинг и последующие texture stages учитываются отдельно.

| Источник | Входы и результат | Значение для переноса |
| --- | --- | --- |
| `BasicShader.vsh` | Только позиция и view-projection c0–c3 | Не содержит модели материала или света |
| `BallisticPFX.vsh` | Позиция, скорость, время рождения/жизни; c4–c10 задают ускорение, камеру, размеры и цвета | Сам вычисляет движение частиц, COLOR0 и размер точки; нужен путь частиц |
| `ShadowVolumePoint.vsh` | Позиция с управляющим w, LightPos c4, Range c5 | Экструзия теневого объёма; не обычная поверхность уровня |
| `Blur.vsh` | Экранный quad, TextureSize c0, Distance c1 | Четыре сдвинутых UV; позиция становится sign(x/y), z=0, w=1 |
| `Blur.psh` | Четыре texture samples | Среднее четырёх RGBA |
| `BlurLuminance.psh` | Те же samples и коэффициенты c1 | Средний RGB умножается на его скалярную яркость, alpha=1 |
| `Luminance.psh` | Один sample и c0 | RGB умножается на `dot(sample.rgb,c0.rgb)^16`; alpha берётся из sample |
| `Fixed.rfx`, VS | Skinning, матрицы, выбранный свет, ColorMode, UV | Основная семья наблюдавшихся игровых VS |
| `Fixed.rfx`, PS | COLOR0 | Возвращает входной цвет; сам не читает текстуры |
| `Bumpmap.rfx`, VS | Позиция, веса, normal/tangent/binormal, свет и inverse-view | Кодирует tangent-space light/half vectors в COLOR0/1, передаёт UV0 дважды |
| `Bumpmap.rfx`, PS | Texture0, normal map Texture1, COLOR0/1, c0–c2 | Diffuse и specular вычисляются по нормали; COLOR0/1 здесь не albedo |

В Bumpmap PS c0/c1/c2 подписаны в самом RFX как AmbientCol/LightMatDiff/
LightMatSpec. Последовательность умножений даёт **восьмую степень** dot(n,h),
хотя комментарий говорит «power of 32». В расчёт входит исполняемый код.

Ballistic: возраст t уменьшается на lifetime **один раз**, если loop включён
и возраст достиг lifetime. Это не операция modulo. Позиция содержит
`P0 + t*V0 + t²*AccelBegin/2 + t³*(AccelBegin-AccelEnd)/(6*lifetime)`.
Размер точки использует расстояние от исходной P0 до камеры, линейный размер
по нормализованному возрасту и нулевую маску вне диапазона [0,1].
Деление на ноль и иные вырожденные входы здесь не квалифицировались.

ShadowVolumePoint: для d=P−L и r=length(d), Q=L+d*max(r,Range)/r;
результат Q+(P−Q)*P.w. Вершина с w=1 сохраняет P, с w=0 получает Q.
Назначение согласуется с отдельным
[потребителем ShadowVolumePoint](native-pc-scene-render-runtime.md).

## Что действительно встретилось в игре

В указанном закрытом прогоне standalone №1–7 созданы при старте, но в draw
до последнего snapshot не использовались. Все девять №8–16 использовались.
Четыре редких смешанных варианта имели всего 1, 1, 6 и 5 draw-вызовов.

| Shader ID в этом прогоне | Точно воспроизведённая семантика |
| --- | --- |
| 8 | Четыре веса, ColorMode 2: vertex color |
| 11 | Четыре веса, ColorMode 1: MatDiffuse |
| 12 | Четыре веса, ColorMode 4, один directional |
| 9 / 10 | То же, два directional, UV без/с transform |
| 15 / 13 | То же, point затем directional, UV без/с transform |
| 16 / 14 | То же, directional затем два point, UV без/с transform |

Ключи в отчёте — **входы, способные породить эти программы**. Они не считаны
из живого manager. Мёртвые ветви могут сделать разные ключи эквивалентными;
например, цветовой unlit-режим позволяет компилятору убрать расчёт света.
Это точная идентификация программы, не доказательство единственного live key.
Набор 165 случаев покрывает выбранные ветви, не весь декартов набор игры.
Включён и отдельный нулевой weight case: шаблон компилируется, но штатный
manager при таком ключе возвращает NULL до поиска shader cache.

## Fixed.rfx: значимые правила

Пусть L — накопленный RGB света, V — vertex color, D — MatDiffuse:

| ColorMode | RGB | Alpha |
| --- | --- | --- |
| 0 | 1 | 1 |
| 1 | D.rgb | D.a |
| 2 | V.rgb | V.a |
| 3 / остальные else | L | D.a |
| 4 | L + V.rgb | D.a |
| 5 | L × V.rgb | D.a × V.a |
| 6 | ConstColor.rgb | ConstColor.a |

AmbientCol — уже произведение выбранного ambient light и ambient материала;
LightMatDiff/LightMatSpec также уже умножены на соответствующий материал.
Нельзя считать эти параметры цветом отдельной глобальной лампы.

Не-specular point при положительном dot сначала добавляет diffuse, затем
умножает **весь накопленный L** на `1/(a0+a1*distance)`. Порядок источников
влияет на результат. Point со specular этой attenuation не использует.
Spot без specular сохраняет отрицательный diffuse dot, умноженный на cone.
Эти особенности подтверждены исходником и сохранёнными инструкциями.

Все включённые UV-выходы начинаются с UV0 и собственного UVTransform[i].
Числа регистров зависят от специализации: например, AmbientCol занимает
c55/c59/c60/c62/c63/c65/c68 в разных реально снятых программах. Использовать
регистры одной программы для остальных нельзя; полная CTAB сохранена.

`ColorBegin`, `ColorEnd`, `Time_Loop_Scales`, `Range`, `TextureSize` и другие
специальные имена не обслуживаются общим `spDXShader` switch (type=0).
Это не доказательство отсутствия констант в игре: их отдельных вызывающих
потребителей ещё нужно связать с реальными записями регистров. BlendWeightCount
в Fixed — параметр генерации, а не оставшаяся runtime-константа шейдера.

## Доказанная ошибка современного backend и исправление

Исходный HLSL выполняет `normalize(-PosView)` над **float4**, после чего
присваивает xyz в float3 VDir. В сохранённом specular bytecode это `dp4`,
`rsq` и использование xyz. Viewer преждевременно отбрасывал w и выполнял
трёхмерную нормализацию. Это ошибка нашего GLSL-переноса, не реконструкции
CPU-классов и не оригинальной игры.

В контрольной точке P=(0,0,1,1), LightPos=(1,0,1,1), N=(1,0,0), power=4:
исходный specular = `(sqrt(2/3))^4 = 4/9`, прежний GLSL даёт 1/4.
Ambient и diffuse в этом входе нулевые, specular RGB единичный.

`pc_shader_vertex_oracle.cpp` исполняет скомпилированный исходный VS через
системный D3D9 ProcessVertices. Это software vertex processing, не GPU
readback. Для point и spot получено packed RGB **113/255**, alpha=191/255;
погрешность к 4/9 и 0,75 меньше одного 8-битного шага. Драйвер
`verify_pc_shader_specular.py` проверяет восемь компонентов двух центральных
входов; ещё четыре near/far результата сохраняет как наблюдения.

В общем `SmoGpuSceneRenderer` теперь сохраняется vec4 position; light delta
и view vector нормализуются до извлечения xyz. Геометрическое расстояние
attenuation по-прежнему использует xyz. Математика CPU-производителей прежняя.

- GPU-проверка **до исправления** воспроизвела 0,24999991 и завершилась отказом.
- После исправления point и spot дают **0,4444445**, ошибка к float 4/9 —
  5,96e−8. Вся серия: **23 проверки PASS** на RTX3070.
- Настоящий Icy: **34 проверки PASS**, 12 placements/passes, 7752 пикселя;
  нет ошибок материалов. Его текущая ambient-only сцена не проверяет блики;
  их проверяет отдельный численный стенд. PNG сохранён и просмотрен.
- Общий SDK helper сохранил точный результат прежнего аудита в 23 сравнениях:
  все 16 captured disassemblies и сборка семи standalone-ресурсов.
- C++ проверки композиции источника: 6/6; managed builds без предупреждений.

Первая версия ProcessVertices-стенда передала выходной buffer с FVF=0 и
завершилась access violation внутри системного d3d9.dll. Этот отказ сохранён
и не относится к выполнению игры. Исправленная версия использует обязательный
для старого пути ненулевой FVF и packed ARGB, согласно
[контракту Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/d3d9/nf-d3d9-idirect3ddevice9-processvertices).
Полная float4-точность вывода D3D9 этим стендом не заявляется.

## Следующий перенос в Remix

Теперь источник и семантика всех наблюдавшихся программ установлены.
Следующий шаг — связать оригинальные материал/light cache и режим ColorMode
с раздельными входами albedo/ambient/emission. Сохранять уже доказанные
skinning, UV, alpha и порядок цветовых операций; представление добавочного
вклада проверить отдельно на штатном Remix API.

Bumpmap, частицы, теневые объёмы и экранные фильтры имеют разные выходные
смыслы. Их нельзя переносить общим предположением «COLOR0 всегда albedo».
Общий исследовательский инструмент уже обслуживает все эти ресурсы, но
runtime-перенос всех семейств, специальные CPU-потребители, живые hooks и
полная игровая регрессия остаются открытыми. **Готовность Remix остаётся ≈45%**:
исследование и исправление Viewer не выдаются за новый завершённый RT-путь.

Машинная опись: `research/native-pc-shader-contract-2026-09-12.json`.

## Повторение

В Developer PowerShell с настроенным CMake build общей библиотеки:

```powershell
cmake --build .codex-tmp/Sparkplug-build-pc2100-utf8 --target SparkplugShaderCompileTests --parallel 2
python research/analyze_pc_shader_contract.py --run local-data/rtx-remix/runs/2026-09-12-surface-combiner-game --output local-data/results/pc-shader-contract-NEW
powershell -File research/Build-PCShaderOracle.ps1 -OutputDirectory local-data/results/pc-shader-oracle-NEW
python research/verify_pc_shader_specular.py --contract local-data/results/pc-shader-contract-NEW/report.json --oracle local-data/results/pc-shader-oracle-NEW/pc_shader_vertex_oracle.exe --output local-data/results/pc-shader-specular-NEW
```

Имена NEW заменить свежими; выходы анализа и проверки не перезаписываются.
Первая команда использует существующий исследовательский CMake build;
для другого build передать `--source-probe` в анализатор. Нужны оригинальные
ресурсы, сохранённый shader audit и установленный Microsoft D3DX9 SDK runtime.
Стенд ProcessVertices требует обычного доступа к графическому устройству;
сам анализатор компиляции не создаёт окна или D3D device.
