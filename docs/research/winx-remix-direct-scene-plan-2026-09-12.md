# Переход от D3D-перехвата к прямой передаче сцены в Remix

12 сентября 2026. Решение пользователя: цель — прямая передача данных движка
в Remix; переход выполнять постепенно, используя уже работающую D3D-обвязку.
Этот документ задаёт следующую работу. Его создание не означает выполнения
переноса или изменения установленной DLL.

## Целевое устройство

```text
Оригинальная игра: состояние мира, анимация, материалы, ресурсы
                         ↓
Общий снимок нужных данных сцены и реестр их времени жизни
                         ↓
Собственный адаптер форматов и материалов → Remix API → RT-изображение

D3D: запуск/device/Present + интерфейс и загрузки
     + временный путь ещё не перенесённых 3D-проходов
     + сравнение и диагностика
```

«Общий снимок» — собственный контракт между наблюдением и backend, не новая
копия игрового scene graph. Источники данных заменяются последовательно:
сначала доступны текущие D3D-входы, затем подтверждённые объекты движка.
Для каждого поля сохраняется происхождение. API-подача меша, собранного из
D3D-буфера, ещё не считается прямым чтением этого меша из движка.

Данные получать после необходимых игровых обновлений и до потери объектов
из-за экранного отсечения или смешивания цветовых слагаемых старым renderer.
Это требование к границе, а не уже доказанная единственная функция hook:
некоторые обновления материалов, палитры и эффектов выполняются внутри Render.
Их сохранять до исследования соответствующего producer. Подавление GPU-draw
само по себе не разрешает пропустить весь игровой Render с его побочными
действиями.

## Основание и сохранение сделанного

База — commit `70817c2`, установленная DLL `5BA41AD4…`, функциональная готовность
46,25% по существующим весам, округлённо около 45%.

- Окно, bridge, интерфейс/загрузки, API-ресурсы, сравнения и ограничения памяти
  используются повторно.
- Свет уже поступает из native scene registry через API. Сохраняются его
  проверенные создание/обновление/удаление и отделение от восьми D3D slots.
- Прямые API-меши и материалы уже создаются для ограниченного FFP-пути, но
  их вход пока в основном берётся из D3D. Меняется источник, а не весь backend.
- Общие классы материала, света, Node/Skin, mesh/layout и renderer semantics
  остаются единственной реализацией доказанной игровой логики.
- [Последний аудит](winx-remix-native-draw-context-2026-09-12.md) связывает
  26 963 draw с входами, но не доказывает готовность полного scene exporter.

Прослойка и RT-политика являются нашим кодом. Указатели живых 32-битных
объектов читаются через подтверждённый ABI; их нельзя преобразовать cast-ом
в экземпляры переносимых восстановленных C++-классов. Если нужен расчёт,
использовать уже восстановленную общую функцию с явными входами.
Старый DirectX backend не переносить в приложения `tools/`.

## Этапы и критерии выхода

### 1. Единый контракт данных и выбор пути

**Работа.** Поверх существующих API-кэшей определить минимальный общий пакет:
scene generation, ресурс/экземпляр, geometry version, world transform,
материал/pass, UV/alpha, камера, свет и при наличии палитра костей. Разделить
постоянные mesh/material resources и покадровые instances. Идентичность
включает поколение жизни объекта: повторно выданный адрес не старый ресурс.

Начать с существующих D3D-входов и native draw context. На той же границе
сопоставить прямые native mesh/material/transform с D3D без смены изображения.
Связь подтверждать по владельцам/операциям/диапазону геометрии, не по имени
уровня, номеру draw или списку известных texture hashes. Сначала поддержать
однозначный single-pass путь; неизвестные связи считать явно.

**Проверка.** Выбранные geometry/material/transform совпадают на одной и той
же игровой операции; источник каждого поля известен; создание, изменение,
удаление и повторное использование адреса различаются. Включение наблюдения
не меняет путь отрисовки. Не создавать новый универсальный слой абстракций
шире нужного первому рабочему переносу.

### 2. Первый прямой путь для статического окружения

**Работа.** Взять общую поддерживаемую группу: обычные статические single-pass
меши с известным layout, материалом и доступными данными. Получать их из
движка и подавать через существующие CreateMesh/CreateMaterial/DrawInstance.
В эту же проверку включить явную основную камеру через SetupCamera.
Выбор группы определяется свойствами данных, не перечнем объектов.

Сначала сравнить геометрию и UV в диагностическом материале, затем подключить
простой игровой материал. Ресурсы создавать при загрузке/изменении, instance
подавать каждый кадр. D3D остаётся владельцем device/Present и UI; отдельный
API Present и самостоятельный Remix-процесс сейчас не вводить.

**Переключение.** После подготовки всех ресурсов переключить только точно
сопоставленные world-pass draw. Не рисовать одновременно их D3D-копию и
API-копию. При недостаточных данных оставить весь этот проход на прежнем пути.
Отказ API после частичной подачи не считать безопасным основанием немедленно
повторить весь объект через D3D: восстановление должно исключать дубли.

**Проверка.** Окружение присутствует без соответствующих D3D world draw;
камера/UV/позиции совпадают с игрой; меню/HUD продолжают работать; переключение
туда и обратно не оставляет геометрию. Новую API-возможность проверять через
фактически установленный 32→64 bridge: наличие структуры в заголовке не тест.

Это первый законченный результат перехода. Предварительный ориентир этапов
1–2 — 1–3 рабочих дня для ограниченного статического пути; не обещание срока
всего переноса и не обязательство за это время закрыть персонажей/эффекты.

### 3. Состав сцены, камера, свет и время жизни

**Работа.** Получать поддержанные static/partition/обычные RenderNode из
владения загруженной сцены независимо от списка видимых D3D draw. Использовать
тот же generation/registry для уже существующего native light bridge.
Выбор основной камеры отделить от UI, теней и служебных проходов. Сохранить
логическую видимость игры: скрытый/выгруженный объект не равен объекту за
кадром. Ограничить дальность и память RT-набора явно; не загружать всю игру
в GPU и не создавать неизменные меши заново каждый кадр.

**Проверка.** Поворот от объекта не удаляет его из отражений/теней; источник
света не зависит от последнего light cache у draw. Проверить возврат в область,
смену камеры, reload и переход между разрешёнными уровнями. Старые ресурсы
освобождаются с учётом зависимостей mesh → material. Сбой создания/удаления
не теряет владение. Отдельно определить неподдержанный dynamic support Домино.

Расширение оригинального D3D visibility vector убирать для перенесённой группы
только после подтверждения, что её данные и необходимые обновления уже доступны
через прямой путь. Остальные группы продолжают использовать прежнюю обвязку.

### 4. Материалы, нормали, UV и физический свет одним блоком

**Работа.** Разделить авторский цвет/texture/COLOR0, добавочный цвет, ambient,
явно определённую emission и независимую alpha. Связать материал с реальным pass/layer,
UV-источником и преобразованием. FFP и Fixed.rfx могут по-разному использовать
одинаковый номер режима; сохранять происхождение и подтверждённый смысл.
Учитывать установку материала до обновления цветового контроллера.

Параллельно с этим проверить физическую адаптацию цвета, мощности, размера,
затухания и теней источников. Восстановленные игровые правила не менять ради
нужной яркости. PBR-параметры и восстановление отсутствующих нормалей обозначать
как собственную графическую политику с проверкой результата.

**Проверка.** Основная поддержанная поверхность реагирует на RT-свет без
всеобщей emission. Временное unlit → emission сохранять только в контрольном
профиле; не объявлять его физическим материалом. Исходно запечённый цвет не
объявлять автоматически разделённым на albedo/освещение. Проверить material
animation, UV1, transformed/projected UV, alpha-test и прозрачные края.
Яркость проверять устойчивым кадром после сброса/успокоения истории Remix;
известное послесвечение при переключении учитывать в сравнении.

### 5. Персонажи и динамические меши на том же контракте

**Работа.** Передавать native mesh, веса, индексы костей и актуальную палитру
Node/Skin через предусмотренные Remix skinning structures, проверив их
прохождение через установленный bridge. Использовать подтверждённые правила
inverse bind × bone world, пространства координат, позиций и нормалей.
Не писать для прослойки второй алгоритм игровой анимации.

Сначала обычный персонаж, затем другие встреченные форматы динамики. Если
конкретный API-путь недоступен, явно оставить соответствующий класс на D3D
и исследовать общую замену с использованием уже восстановленного кода.

**Проверка.** Покой, ходьба, поворот, несколько экземпляров, тени/отражения,
уход за экран и возвращение; без двойного world transform и старой палитры.
Сравнивать деформированную геометрию и нормали, не только наличие ключа VS.
После проверки подавлять только заменённые D3D-проходы персонажа, сохраняя
нужные игровые обновления и callbacks.

### 6. Несколько проходов, эффекты и совместимость с интерфейсом

**Работа.** На общем материальном и геометрическом пути последовательно
перенести наложения/decal, несколько passes, небо, воду, частицы и прочие
процедурные объекты. Получать данные после необходимых генераторов; ранний
сырой asset может ещё не содержать результат работы эффекта. Старые тени
отделять от самостоятельных поверхностей, чтобы не удваивать RT-тени.

**Проверка.** Порядок прозрачности, alpha/depth, animated UV, создание/удаление
эффекта, скрытие/возврат и смена уровня. HUD, меню, загрузки, шрифты и ролики
проверять на каждом затронутом переходе; world-space UI классифицировать
отдельно. Не пропускать необходимые offscreen render-target passes только
из-за того, что основной мир уже передаётся напрямую.

Список ещё работающих через D3D групп вести явно. Наличие резервного пути
позволяет продолжать игру, но не означает завершённого переноса этой группы.

### 7. Сокращение D3D-зависимостей и общая регрессия

**Работа.** Для уже перенесённых групп последовательно удалить лишние чтения
D3D-буферов, восстановление смысла из state, повторные преобразования и
принудительный D3D-offscreen render. При этом сначала доказать, где теперь
выполняются необходимые обновления материала/палитры/эффекта.

**Проверка.** Воспроизводимые запуски, повторные загрузки/смены уровней,
повороты и переходы камер, device reset/разрешение, длительная работа,
ресурсные ошибки и USD capture с API-материалами. Измерить CPU-время сбора,
число созданий/обновлений GPU-ресурсов, RAM/VRAM и время кадра относительно
сохранённой базы. API-подача сама по себе не доказывает ускорения.

**Граница завершения цели.** Поддерживаемый игровой 3D-мир получает геометрию,
материалы, transforms, деформации, камеры и свет из состояния движка; D3D
world draw больше не является обязательным источником этих данных. Неизвестные
3D-пути учтены и не скрыты; необходимая, но ещё не перенесённая группа означает
незавершённый переход. Исключение из конечного охвата требует отдельного
решения пользователя. Наличие D3D для запуска, Present и корректного UI
допустимо. Полностью самостоятельный renderer без D3D-bootstrap — отдельное
последующее решение, не обязательная переделка в начале этого перехода.

## Порядок работы и учёт

- После этапа 1 идти законченными группами данных. Первая — ordinary static;
  общий material/UV/lifecycle использовать повторно для следующих групп.
- На каждом этапе: достаточное исследование producer → общий исходник при
  необходимости → подключение → оригинал/RTX-проверка → переключение пути.
  Исследование всех классов заранее не является входным условием.
- Один проход имеет одного владельца: прежняя подача или direct API.
  Переключение, отказ и освобождение ресурсов являются частью реализации.
- Сохранять три режима для проверки: оригинальный renderer; текущий гибрид;
  гибрид с выбранной группой на прямом источнике. Не требовать совпадения
  физических RT-пикселей с исходным baked/unlit изображением: геометрию,
  движение, alpha/UV и согласованную RT-политику проверять раздельно.
- Пользовательский запрет на запуск Гардинии 2 сохраняется. Выборка — Алфея,
  Домино и другие разрешённые уровни; результаты не кодируются как исключения.

Сохраняются девять категорий и веса [функциональной готовности](winx-remix-progress.md).
Этот план сам по себе не прибавляет процентов. Дополнительно для каждой группы
отмечать происхождение данных: D3D / наблюдение native / прямая native-подача
/ проверенный прямой путь. Отдельно показывать резервные и неизвестные группы.
Долю direct instances считать только с объявленным знаменателем и сценой;
число API-draw не заменяет готовность механизма и не складывается с прежним %.

## Ближайшая работа

Этапы 1–2: общий пакет на существующем D3D-перехвате, точное соответствие
native mesh/material/transform и один законченный статический direct-путь
с камерой. После него уточнить сроки и очередность расширения по найденным
ограничениям. Прежняя оценка экономии 20–40% остаётся рабочей гипотезой,
не измеренным эффектом и не новым сроком завершения всей интеграции.

Техническая опора: локальный read-only `dxvk-remix` и
[официальное описание Remix SDK](https://github.com/NVIDIAGameWorks/dxvk-remix/blob/main/documentation/RemixSDK.md),
[структуры API](https://github.com/NVIDIAGameWorks/dxvk-remix/blob/main/public/include/remix/remix_c.h).
Эти интерфейсы задают возможный контракт. Поведение каждой новой функции и
extension на установленном runtime/bridge подтверждается отдельной проверкой.
