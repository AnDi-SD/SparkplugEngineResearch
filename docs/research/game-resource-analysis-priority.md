# Вспомогательная очередь анализа файлов игры

Актуально для schema v5 и базы
`local-data/results/smo-corpus-v2.sqlite` на 5 сентября 2026 года. Это очередь
форматов; порядок native-классов задаёт отдельный
[план реконструкции](native-reconstruction-plan.md), в котором приоритет отдан
прямому SMO/SAN closure и PC-first evidence.

Эта очередь больше не является главным планом реверса. Основной порядок задают
разрывы в [runtime-конвейере executable](../engine/runtime-resource-pipeline.md):
точки запроса, file/PCK resolver, serializer dispatch, runtime ownership, scene
traversal и вывод. Файл из списка ниже берётся следующим, когда он нужен как
контрольный вход для текущего участка call graph либо когда участок уже доказан
и требуется corpus coverage.

## Граница очереди

В базе нет нераспознанных файлов: формат назначен всем 14 490 версиям файлов
трёх корпусов. Это не означает, что все форматы поняты. В очередь ниже входят
только форматы и части контрактов со статусами `partial`, `research`,
`inventory_only` либо с незакрытой runtime-семантикой.

Единица работы — уникальный payload по SHA-256, а не каждое физическое
вхождение. Одинаковые PC pristine/working и повторяющиеся записи PCK не нужно
исследовать вручную второй раз. После восстановления контракта строгий scanner
обязан проверить уже весь корпус.

Из основной очереди исключены уже закрытые структурные форматы и внешние
стандарты: PCK, WXT, PC SAN, наблюдаемый object graph SMO, WAV, VAG, MPEG,
DDS, ICO, обычный текст, INI и shader assembly. Их незакрытые связи или
runtime-семантика перечислены отдельно и не выдаются за неизвестный формат.

## Шкала сложности

| Балл | Условие |
|---:|---|
| 1–2 | Малый текстовый или табличный файл; достаточно сопоставления корпуса |
| 3–4 | Простая бинарная таблица или внешний стандарт; нужны пары и несколько контролируемых изменений |
| 5–6 | Несколько вариантов, индексы или непрямые ссылки; требуется corpus parser и runtime-проверка |
| 7–8 | Платформенный формат, компрессия, банки или вложенные структуры; нужен executable evidence |
| 9 | Центральный gameplay-контракт или native PS2 payload с большим числом зависимостей |
| 10 | Loader lifecycle и полный reverse executable; завершение нельзя доказать только статическим parser |

Балл оценивает трудность полного доказательства, а не размер файла и не его
важность для моддинга.

## Рекомендуемая последовательность форматов

Это порядок вспомогательной работы с форматами, а не порядок всего проекта. Он
сначала закрывает дешёвые форматы и строит словарь идентификаторов, затем
переходит к SPT/SPL и native PS2 данным. Loader lifecycle исследуется с самого
начала параллельно и имеет приоритет при конфликте очередей.

| № | Работа | Корпус для проверки | Сложность | Что должно появиться в базе |
|---:|---|---:|---:|---|
| 1 | **WXS** — save/settings | 3 уникальных payload | 2 | Поля, типы значений, default/current различия, runtime read/write evidence |
| 2 | **WXD** — string definitions | 2 | 3 | Полный layout, идентификаторы и доказанные связи с WXT/GUI либо явное отсутствие связи |
| 3 | **CCC** — color control | 1, 785 строк | 3 | Семантика колонок и диапазонов, связь строки с персонажем/material state, безопасная mutation |
| 4 | **SPS + PSS metadata** — субтитры и фильм | 57 SPS, 135 PSS | 4 | Тайминг, индексы текста, соответствие SPS ↔ movie, язык, PAL/NTSC и длительность потока |
| 5 | **ANM** — оставшиеся семь колонок | 73 | 4 | Названия и домены всех колонок; существующая ANM → SAN связь остаётся подтверждённой |
| 6 | **SNC, текстовый контракт** | 136 | 4 | Семантика всех колонок, event/variant/volume/pitch поля и PC SNC → WAV без одной только эвристики имени |

| 8 | **Семантический проход известных текстов** | XML 7, Lua 1, RFX 2, shader 7 плюс релевантные TXT | 3–5 | Пути, runtime keys и typed dependencies; синтаксис этих форматов уже известен |
| 9 | **SFT** — font payload | 41 | 5 | Glyph table, metrics, atlas/texture mapping, Unicode/codepage и воспроизводимый preview |
| 10 | **PC STX, остаточный контракт** | часть из 400 общих STX payload | 5 | Единый decoder трёх PC-вариантов, размеры/mips/palette/alpha и отсутствие необъяснённого хвоста |
| 11 | **SPL** — placements | 75 | 7 | Строгие записи placement, transforms, instance ID и owning field для 827 наблюдаемых SPL → SPT ссылок |
| 12 | **SPT** — component templates | 340 | 9 | Типы компонентов, наследование/вложенность, owning fields и строгие SPT → SMO/SNC/SAN/SPT зависимости |

Главные PC EXE и PS2 ELF являются основным предметом текущего исследования, а не
последним пунктом этой таблицы и не только параллельным источником. Полная
декомпиляция всей игры не требуется: восстанавливаются все узлы, необходимые
для непрерывных end-to-end resource paths. В базе сейчас 11 уникальных PE и 10
ELF/IRX payload; основной runtime-приоритет имеют `WinxClub.exe` и
`SLES_532.19`.

## Обязательные связи

Наличие печатной строки внутри бинарного файла остаётся `observed`, пока не
найдено поле-владелец. Для каждого формата проверяются следующие цепочки:

| Источник | Цель | Текущий статус |
|---|---|---|
| ANM | SAN | Синтаксически подтверждено; 5 115 вхождений по трём корпусам |
| SAN track | SMO node | Подтверждено для PC; PS2 открыт |
| SPL | SPT | 827 наблюдаемых строковых ссылок; owning fields открыты |
| SPT | SMO/SNC/SAN/SPT | 2 871 наблюдаемая зависимость; owning fields открыты |
| SNC | WAV | 3 156 разрешено на PC; 1 525 PS2 имён не имеют WAV target |
| SNC | SB2/VAG/MIC | Не доказано |
| SPS | PSS/WXT | Роль ожидается по соседству и именам, но контракт не доказан |
| WXD | WXT/GUI | Не доказано |
| OneLiner DAT | WXT/SNC/WAV | Не доказано |
| SFT | glyph atlas/texture | Структура FFPS наблюдается, визуальная связь не закрыта |
| EXE/ELF | любой загружаемый ресурс | Есть отдельные call-site evidence; общего loader graph пока нет |

## Как разбирать каждый формат

Для каждого пункта используется один и тот же цикл:

1. Сгруппировать уникальные payload по platform, magic, размеру и первым
   структурным признакам.
2. Выбрать минимальный набор представителей, покрывающий все кластеры, крайние
   размеры и PC/PS2 пары.
3. Построить read-only parser с точными границами и сохранением неизвестных
   байтов, а не сразу writer.
4. Запустить parser на всех уникальных payload и отдельно перечислить каждый
   outlier.
5. Добавить свойства, символы и зависимости с byte/row locator и provenance.
6. Сопоставить данные с соседними файлами, executable и наблюдаемым поведением.
7. Если формат влияет на runtime, выполнить одну минимальную обратимую mutation
   на копии и проверить её в игре.
8. Только после этого решать, нужен ли writer, preview или editor.

Ручная проверка каждого физического файла нужна только для outlier. Обычные
файлы после появления parser проверяются автоматически corpus sweep-ом.

## Шкала работоспособности файла

Один общий процент скрывает слишком много различий. Для каждого файла или
логического asset следует хранить независимые способности:

| Способность | Возможные состояния |
|---|---|
| Inventory | missing / indexed / hash-confirmed |
| Recognition | unknown / observed / confirmed |
| Structure | none / partial / strict |
| Semantics | unknown / named / runtime-confirmed |
| Dependencies | none / observed / resolved / runtime-confirmed |
| Preview | unavailable / partial / verified |
| Mutation | untested / rejected / accepted / behavior-confirmed |
| Write | unsupported / lossless-roundtrip / constrained / runtime-verified |
| Platform parity | n/a / unmatched / paired / equivalent / intentionally-different |

Итоговый «слепок работоспособности» должен показывать эту матрицу по каждому
формату, corpus variant и логическому asset, а не объявлять весь формат
изученным после одного успешно открытого файла.

## Критерий завершения пункта

Пункт очереди можно закрыть только когда:

- все уникальные payload назначены конкретному варианту или честному outlier;
- parser проходит весь корпус без ошибки и без необъяснённых байтов;
- каждое семантическое утверждение имеет evidence и locator;
- зависимости извлекаются из поля-владельца и имеют явный результат разрешения;
- PC/PS2 различия зафиксированы как вариант, а не сглажены общей догадкой;
- runtime-важные поля имеют baseline и контролируемую проверку в игре;
- база пересобирается воспроизводимо, а `resource-audit` не показывает новых
  unknown, ошибок или потерянных зависимостей.
