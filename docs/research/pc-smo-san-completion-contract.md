## Обязательные критерии

1. **Полнота инвентаризации.** Для PC классов/вспомогательных типов в области
   известны реальные callers/callees, serializer dispatch и использованные
   методы/поля. Непроверенная ветвь/variant/unknown field остаётся открытой.
2. **Чтение.** FFPS header/FAT/index/fixup -> factories -> поля -> ссылки и
   ownership воспроизводятся одной цепочкой на реальных PC SMO/SAN;
   single-object fixture не выдаётся за полный loader.
3. **Запись.** Подтверждены native save dispatch, индексация, offsets/sizes,
   связи, geometry/material/skin/animation encodings; доказана совместимость
   сохранённого результата с оригинальным PC чтением. Неизвестные payloads
   сохраняются без потерь там, где формат допускает непрозрачное сохранение;
   это не засчитывается как знание их семантики.
4. **Обработка.** Scene transforms, placement/registration, animation sampling,
   skinning, visibility/material/mesh submission и относящиеся к ресурсу
   collision/navigation/other consumers подтверждены по реальным PC путям.
   Исключение важных классов вроде particle/text из37 не допускается.
5. **Lifetime и отказы.** Повторная загрузка, несколько одновременно живых
   ресурсов, aliases, удаление/rebind и ошибки разобраны. Host safe policy
   явно отделяется от исходных ошибок, неопределённости и ограничений native.
6. **Воспроизводимость.** Evidence привязан к hash executable, VA/RVA и
   входным данным; оригинальные инструкции и reconstructed source сравнены,
   проверены существенные branches/variants и общий regression. Опасные
   случаи устанавливаются статически/stop-before; не исполняются ради галочки.
7. **Интеграция отображения.** Подтверждён полный переход resource -> scene ->
   PC backend, а не только callbacks вместо GPU. До безопасной отдельной
   интеграционной проверки rendering readiness не объявляется полной.

100% означает закрытие принятого и проверенного PC объёма по всем критериям,
не математическое доказательство для всех возможных битовых последовательностей.
Наличие недоступного native тела с неизвестным контрактом не совместимо с100%.
Реализация Windows/Direct3D/CRT как сторонних платформенных библиотек не входит
в восстановление движка; их наблюдаемые контракты на границе учитываются.

## Порядок и ограничения

Сначала SAN resource loader/FAT/registry; затем PC SMO serialization/materialization
и save. Renderer/visibility развивается по доказанным зависимостям, но не
становится искусственной предпосылкой независимому изучению reader/writer.
Связанные остановки защищённого диспетчера получают общую карточку; нужны
новые свидетельства, а не повтор capped calls. Паспорта/тесты/сводки повторно
используются; основное время отдаётся новым контрактам.

Постоянный [манифест исследования](research-manifesto.md) требует оптимизировать
процесс на протяжении работы и регулярно сохранять проверенные блоки в Git.
Общий разрешённый бюджет исследовательских процессов — около 1 ГиБ RAM;
новые явные профили памяти вводятся по необходимости с проверкой границ.
После пользовательского поручения об оптимизации 7 сентября отдельный
integration fixture допускает128KiB heap; default micro fixture64KiB,
stack64KiB и32KiB на engine request сохранены. Исторические64KiB результаты
не пересчитываются. [Изменение процесса и первый эксперимент](native-research-strategy-2026-09-07.md).
Сохраняются100k instructions/2s per call и30s child, read-only originals,
нет map-on-fault/API forwarding/подставленного успеха неизвестным функциям.
Ресурсы и приложения не переписываются массово. Последующим поручением
пользователь разрешил публикацию накопленных исходников и документации
на GitHub после проверки; выпуск release остаётся отдельной задачей.
Результаты фиксируются небольшими checkpoints в базе, source/tests,
регулярных commits и [журнале последнего цикла](../../journal/2026/2026-09-07-pc-smo-san-1900.md).
Предыдущий [журнал](../../journal/2026/2026-09-06-pc-smo-san-completion.md)
сохраняется как история; [итоговый отчёт](native-cycle-report-2026-09-07-1900.md)
не меняет перечисленные критерии полной готовности.
