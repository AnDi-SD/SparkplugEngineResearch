# `spOBBBV` (`0x4DA04889`)

Статус: все наблюдаемые объекты и поле размера полностью декодируются; три
возможных поля подтверждены независимо кодом PC и PS2. Реализация остаётся
read-only: загрузка изменённого OBB в игре ещё не проверялась.

## Распространённость

| Корпус | Объекты | Уникальные SMO | Физические вхождения | Формы | Размеры |
|---|---:|---:|---:|---:|---:|
| `pc-pristine` | 148 | 97 | 148 | 1 | 80 |
| `pc-working` | 148 | 97 | 148 | 1 | 80 |
| `ps2-pristine` | 127 | 87 | 612 | 1 | 79 |

Все 423 экземпляра безымянные, не имеют собственных дочерних объектов и
непосредственно вложены в `spCollisionInfo`. Один SMO содержит от одного до
четырёх OBB. PS2 physical count больше unique count из-за повторных вхождений
одного ресурса в PCK; это не дополнительные варианты объекта.

Класс в основном используется персонажами и их костюмами, но встречается также
в отдельных SFX и объектах уровня. Например:

| Ресурс | Полный размер `(X, Y, Z)` |
|---|---|
| `Characters/Amaryl/Amaryl.smo` | `(47.549511, 156.852997, 31.4216003)` |
| `Characters/Animals/bird.smo` | `(10.7999983, 7.06903267, 17.7988129)` |
| `Characters/Animals/fish.smo` | `(3.57227898, 7.0254817, 3.09597492)` |

## Наблюдаемая байтовая структура

Каждый доступный объект занимает 23 байта и имеет сигнатуру
`s0:f1:12|s0:end`:

| Смещение | Размер | Значение |
|---:|---:|---|
| `0x00` | 4 | class ID `0x4DA04889` |
| `0x04` | 4 | `SBOO` |
| `0x08` | 2 | field 1: header `0xA1`, UInt8 payload size `0x0C` |
| `0x0A` | 4 | `Single size.x` |
| `0x0E` | 4 | `Single size.y` |
| `0x12` | 4 | `Single size.z` |
| `0x16` | 1 | terminator собственной serializer-секции `0x00` |

Все значения little-endian. В SMO хранится **полный размер** по трём осям.
Loader обеих платформ вычисляет half-extents как `size * 0.5`, затем сохраняет
длину вектора half-extents как радиус охватывающей сферы:

```text
halfExtents = size * 0.5
boundingSphereRadius = length(halfExtents)
```

Таким образом, показывать 12-байтовый payload как half-extents было бы ошибкой.

## Полный набор полей serializer

Исполняемые файлы подтверждают три идентификатора собственной секции:

| Field | Имя | Payload | Наблюдается в SMO | Поведение serializer |
|---:|---|---|---|---|
| 0 | `esfOBBBVPosition` | `Vector3` | нет | локальная позиция; нулевое значение опускается |
| 1 | `esfOBBBVSize` | `Vector3` | 423/423 | полный размер; записывается всегда |
| 2 | `esfOBBBVRotation` | quaternion `(X,Y,Z,W)` | нет | локальное вращение; identity опускается |

Внутри runtime вращение OBB хранится матрицей. Перед записью serializer
преобразует её в quaternion; loader выполняет обратное преобразование. Отсутствие
field 2 не делает объём axis-aligned в мире: внешний transform хранится его
родителем `spCollisionInfo`. Поля 0 и 2 задают дополнительное локальное смещение
и вращение самого box относительно этого transform.

Ни одного нестандартного случая с сериализованными position/rotation в трёх
корпусах нет. Они внесены в реестр полей как подтверждённые executable, но
ненаблюдаемые возможности формата, а не как выдуманные варианты.

## Значения и подтипы

Структурный подтип ровно один — `obb_size_only`. Все 423 объекта назначены ему с
уровнем уверенности `confirmed`. Векторы размеров являются параметрами, а не
отдельными подтипами.

По объединённому корпусу найдено 80 разных 12-байтовых payload:

| Компонента | Минимум | Максимум |
|---|---:|---:|
| X | `3.57227898` | `268.105835` |
| Y | `7.0254817` | `789.820618` |
| Z | `3.09597492` | `298.623352` |

Все 1 269 наблюдаемых компоненты конечные и строго положительные: нулей,
отрицательных значений, NaN и Infinity нет. Это инвариант доступного корпуса, а
не пока ещё доказанное ограничение loader.

## Межкорпусное сравнение

Сравнение выполняется не по object index: индексы PC и PS2 могут сдвигаться.
Для каждого канонического пути строится отсортированное мультимножество
12-байтовых размеров; это также корректно для SMO с несколькими OBB.

- все 97 общих `pc-working`/`pc-pristine` ресурсов совпадают;
- все 87 общих `pc-pristine`/`ps2-pristine` ресурсов совпадают;
- единственный отсутствующий на PS2 размер относится к PC-only ресурсам, а не к
  платформенному варианту layout.

Это особенно сильное подтверждение: совпадают не только serializer-код и форма
поля, но и реальные параметры всех доступных одноимённых ресурсов.

## Свидетельства executable

Pristine PC `WinxClub.exe`:

- load — `0x00439BA0..0x00439E61`;
- serialize — `0x00439E70..0x0043A151`;
- строки диагностик position/size/rotation — file offsets
  `0x2DE478`, `0x2DE428`, `0x2DE3E0`;
- строка `spOBBBVSerializer` — file offset `0x2DE4CC`;
- строка класса — file offset `0x2EB2FB`.

Loader переключается по ID 0/1/2. Field 1 копируется в члены объекта
`+0x58/+0x5C/+0x60`; множитель `0.5f` находится по VA `0x006DC3D4`, после чего
результат `sqrt(hx² + hy² + hz²)` записывается в `+0x24`. Position попадает в
`+0x4C/+0x50/+0x54` и дублируется в базовую часть `+0x18/+0x1C/+0x20`.
Quaternion field 2 преобразуется в матрицу объекта начиная с `+0x28`.

PS2 `SLES_532.19`:

- load — `0x00189960..0x00189BA0`;
- serialize — `0x00189BC0..0x0018A03C`;
- строки диагностик position/size/rotation — file offsets
  `0x34CA10`, `0x34CA70`, `0x34CAC0`;
- строка `spOBBBVSerializer` — file offset `0x34CBC0`;
- строка класса — file offset `0x39C368`.

MIPS loader использует те же field ID и смещения членов. Для field 1 он явно
загружает `0.5f` инструкцией `lui 0x3F00`, умножает все три компоненты и вычисляет
тот же радиус. Независимое совпадение PC и PS2 исключает случайное толкование
12 байт как произвольного `Vector3`.

## Viewer и база

`SmoOrientedBoxBoundingVolumeDecoder` строго принимает 12 байт для position/size
и 16 байт для rotation. Для size он возвращает полный размер, вычисленные
half-extents и радиус по формуле executable. В read-only панели
«Показывать восстановленные поля» Viewer выводит field 1 как `obb.size`; если в
будущем встретятся field 0 или 2, тот же инспектор уже покажет их как position и
quaternion без изменения файла.

Команда

```text
SmoViewer.Inspect research-db analyze-class <db> spOBBBV
```

повторно проверяет форму всех объектов, родителя, положительные конечные размеры,
наличие пяти executable-строк на каждой платформе и межкорпусное совпадение.
Затем она идемпотентно записывает:

- определения `obb.position`, `obb.size`, `obb.rotation` с отметками
  observed/unobserved;
- вариант `obb_size_only` и назначения всех 423 объектов;
- декодированные JSON-значения размера, half-extents и sphere radius;
- четыре evidence-записи: PC code, PS2 code, полный корпус и cross-corpus.

Редактирование намеренно не включено. Для перехода из `read_only_research`
потребуется на копии SMO отдельно проверить изменение size, материализацию
необязательных position/rotation и фактическую collision-геометрию в native
runtime.
