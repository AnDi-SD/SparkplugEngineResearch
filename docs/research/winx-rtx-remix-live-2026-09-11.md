# Winx / RTX Remix: первые живые проверки 11 сентября 2026

Продолжение [проверки файлов и исходников](winx-rtx-remix-2026-09-11.md).
Пользователь разрешил запуск выбранной оконной копии игры и начало работы
над отдельной прослойкой. Это наш экспериментальный платформенный код;
восстановленная логика, EXE, игровые ресурсы и upstream Remix не менялись.

## Установлено на контрольных запусках

* Системный D3D9 показывает полную заставку, меню, сохранения и игровой мир
  Алфеи с Блум и HUD. Скриншоты: локальный каталог
  `local-data/rtx-remix/runs/2026-09-11-system-baseline/`.
* Stock Remix 1.5.2 с `rtx.enableRaytracing = False` показывает чёрный фон
  и серые звёзды, теряет логотип, персонажей заставки и надписи.
  Это уже сбой обычной растеризации; объяснение только захватом RT-камеры
  недостаточно. Проверены меню, не 3D-мир через Remix.
* Наша наблюдающая x86 proxy DLL с системным backend сохраняет правильную
  заставку; с Remix воспроизводит тот же дефект. В сравнимых проходах
  совпадают world/view/projection, декларации вершин, размеры текстур,
  viewport, глубина, blend, fog и texture stage states. Проходы заставки
  используют fixed function: vertex/pixel shader не установлен.
* У bridge `GetFVF` возвращает 0 при декларации, для которой системный
  D3D9 возвращает ненулевой FVF. Это согласуется с реализацией client cache
  в релизном bridge, но **не доказано причиной**: опыт с SDK-преобразованием
  декларации в FVF и `SetFVF` перед draw не восстановил изображение.
* Однократное предупреждение `no valid camera` встречается при запуске
  даже с выключенным RT. Ортографические заставки нельзя использовать
  как доказательство неверной камеры основного игрового мира.

## Инструменты и границы

`research/rtx-remix/winx_d3d9_probe.cpp` — собственная диагностическая DLL.
Она загружает системный D3D9 (`WINX_REMIX_BACKEND=system`) либо сохранённую
официальную DLL `d3d9.remix-original.dll`. Перехватывает обычные CreateDevice,
Reset, Present и четыре Draw-вызова, пишет ограниченную JSONL-выборку
состояния и наблюдает загрузку VB/IB. Методы возвращают исходные HRESULT;
полученные COM-ссылки освобождаются. Ex-only CreateDeviceEx/PresentEx
не покрываются. Это прототип для выбранной игры, не универсальный D3D9 wrapper.

`WINX_REMIX_NORMALIZE_FVF=1` — отдельный необязательный диагностический опыт,
по умолчанию выключен. Использует системный D3DXFVFFromDeclarator,
пропускает programmable VS и восстанавливает декларацию после draw.
У bridge кеш GetFVF после такого опыта может отличаться от исходного;
прозрачным режимом этот опыт не считается.

Сборка: `powershell -NoProfile -ExecutionPolicy Bypass -File research/rtx-remix/Build-Probe.ps1`.
MSVC x86, Windows SDK; CRT статическая. Скрипт не устанавливает DLL.
Запуск после установки proxy: `Start-Probe.ps1 -Name <новое-имя> -Backend system|remix`;
`-Raytracing` включает RT. Конфигурация выбирается через окружение процесса,
игровой `rtx.conf` не переписывается. Каждая новая папка сохраняет конфиг,
PID, SHA256 загруженной proxy и копию DLL.

`research/winx_remix_window.py` управляет только видимым окном указанного PID,
после проверки полного пути к выбранному WinxClub.exe. Нажатия требуют
фокуса на этом окне. Снимки включают только его прямоугольник. В данном
окружении GPU и доступ к окнам проверялись в обычном пользовательском
контексте, поскольку ограниченный токен не видит игровые окна.

## Локальная установка и данные

Официальная x86 DLL сохранена как `local-data/Winx Club/d3d9.remix-original.dll`,
SHA256 `A9D0846720E90D36D19AFB67E76A4D894EB349ECF13B847DE0CEDA4861669965`.
В `d3d9.dll` на время опытов установлена наша proxy. `.trex` не изменена.
Сохранять/заменять DLL можно только после выхода игры и bridge.
Возврат stock Remix: сохранить текущую proxy в каталог опыта и скопировать
`d3d9.remix-original.dll` обратно в `d3d9.dll`. Полное отключение Remix:
убрать root `d3d9.dll` из пути загрузки с сохранением копии.

Исходные сохранения и настройки скопированы до опытов в
`local-data/rtx-remix/runs/2026-09-11-raster-baseline/`.
Результаты локальны, не являются релизом, capture сцены ещё не получен.
Следующая проверка — передача статических буферов через bridge;
рабочая RT-интеграция пока не заявляется.

## Продолжение: загрузка Алфеи и ошибка mip-уровней

Вечером проведены дополнительные опыты. Наблюдающая DLL собрана также
для x64 и временно установлена перед renderer: его оригинал сохранён
отдельно и затем возвращён. На принимающей стороне Present идёт через
swap chain; добавлен учёт этой границы. Выборки одного кадра совпадают
по матрицам и проверенным состояниям на обеих сторонах bridge.
Хеши и первые байты трёх статических VB также совпали. Это не проверка
всех возможных состояний или всех ресурсов игры.

Загрузка сохранения Алфеи воспроизвела `0xc0000005` в
`NvRemixBridge.exe + 0x1B141` с x64-наблюдением, с исходным renderer и
**полностью исходными обеими DLL Remix**. `Reset` 1024×768 → 1280×960
предшествует падению, но сама авария происходит позже: разыменование
нулевой поверхности перед `IDirect3DSurface9::LockRect` при обработке
`IDirect3DSurface9_UnlockRect`. Это установлено по ExceptionStream,
ModuleListStream minidump, дизассемблированию и очереди команд bridge.

В релизном [CalculateNumMipLevels](https://github.com/NVIDIAGameWorks/dxvk-remix/blob/b81a7b566b1eeb9edb4dc2b3c9d3972e0f253ad4/bridge/src/client/d3d9_util.h#L135)
используется `ceil(log2(maxDimension)) + 1`. Для текстуры **3000×3000**
из данной установки это даёт 13, тогда как деление размеров пополам
с округлением вниз заканчивается уровнем 1×1 при количестве 12.
Именно такие правила размеров описывает
[Microsoft CreateTexture](https://learn.microsoft.com/en-us/windows/win32/api/d3d9/nf-d3d9-idirect3ddevice9-createtexture).
Неподдержанный GetSurfaceLevel не регистрирует поверхность на сервере,
а следующий UnlockRect использует отсутствующий объект без проверки.

Добавлен opt-in `WINX_REMIX_EXPLICIT_MIPS=1` (`Start-Probe.ps1 -ExplicitMipLevels`):
только для запроса CreateTexture с `Levels=0` передаётся явное число
уровней, вычисленное целочисленным сдвигом. Размеры, формат, usage,
pool и ресурсные данные остаются исходными. Runtime не пересобирался.

Проверка `2026-09-11-explicit-mips-raster`: зафиксирован исходный запрос
3000×3000, Levels=0, forwardedLevels=12; Алфея дошла до State 28 и кадра
с персонажем и HUD без прежней аварии. Скриншот `alfea.png` сохраняет
другой дефект: большая часть изображения чёрная. В выборке игрового
кадра 134 draw: 120 fixed function, 14 с vertex shader, без pixel shader.
Матрица перспективы игровой сцены присутствует. RT в этом опыте выключен.

Проверка чтения текстур (`2026-09-11-texture-readback-both`) обнаружила
ненулевые BGRA-суммы на клиенте и нулевые на renderer. Это чтение CPU
буферов через LockRect, а не доказательство содержимого GPU image:
режим отложенной загрузки требует отдельной проверки. Наблюдение
`WINX_REMIX_TEXTURE_READBACK=1` специально выключено по умолчанию.
Первый опыт `immediate-texture-upload` с DXVK_CONFIG оказался невалидным:
эта переменная не применена данным runtime. Повторный опыт использует
rtx.conf и подтверждает настройку в Effective Combined Config.
