# Система внешних волос Bloom

Статус: исходно подтверждено для PC-сборки `WinxClub.exe` с MD5
`3bbb8d47516ca7f7d7dcb8f5067380f5`; патчер применяет выводы только после
поиска и однозначной проверки самих машинных блоков.

## Архитектура

Обычный костюм Bloom состоит из body SMO и отдельно загружаемого
`bloom_hair.smo`. В body-модели игра ищет `Head` и шесть управляющих узлов:

- `hair_top_l`, `hair_top_m`, `hair_top_r`;
- `hair_bottom_l`, `hair_bottom_m`, `hair_bottom_r`.

В hair-модели игра ищет `Hair_Master` и набор `Hair_*`/`hair_tip_*` узлов.
Функция около VA `0x004E49A0` передаёт `Hair_Master` вместе с `Head` в
`0x00421A60`. По структуре вызова это parent/attachment-операция или её близкий
эквивалент. Практический эксперимент подтвердил, что перенос шести управляющих
точек не отделяет волосы от головы: он только резко меняет направление прядей.

## Отдельная preview-модель меню костюмов

Меню не переиспользует gameplay-персонажа. `FashionMenu_PC.spl` открывает
`Menus\FashionMenu_PC.spt`, а трёхмерное представление находится в
`BloomFashion.spt` (`wxBloomFashionAnim`). При инициализации меню функция
`0x005E7710` отдельно загружает `bloom_hair.smo` и находит `Hair_Master`.

При смене костюма функция `0x005E74F0`:

1. отсоединяет `Hair_Master` от предыдущего `Head`, если он был найден;
2. загружает body-модель выбранного костюма;
3. находит в ней новый `Head`;
4. для всех ID, кроме штатного Winter/5, вызывает тот же attachment
   `0x00421A60`.

Именно этот независимый четвёртый шаг объясняет, почему ранний патч убирал
волосы в gameplay, но не в меню. Безопасная точка изменения — оригинальная
проверка Winter перед attachment, а не загрузка общей hair-модели: так остаются
штатные detach и lifetime-пути menu-объекта.

В меню 15 позиций, которые переводятся в реальные fashion ID таблицей
`[0, 2, 3, 4, 5, 7, 6, 8, 9, 10, 11, 12, 13, 14, 15]`. Bloom X/1 в ней
отсутствует, а переставленные Crystal/6 и Bike/7 подтверждают, что в gate
передаётся именно ID, а не визуальный индекс позиции.

## Различие Bloom X и Winter

Нельзя трактовать проверки ID 1 и 5 как единый флаг отключения волос.

- ID 1 (`Bloom X`) пропускает стандартный поиск управляющих attachment-точек и
  runtime hair update, но всё равно загружает `bloom_hair.smo` и прикрепляет
  `Hair_Master` к `Head`.
- ID 5 (`Winter`, `bloom_snow.smo`) дополнительно проходит отдельную строковую
  проверку имени, поэтому стандартный hair setup полностью не вызывается.
  Winter содержит собственную укороченную геометрию волос.
- ID 0 соответствует `bloom_jeans.smo` и использует обычную внешнюю hair-модель.

## Подтверждённые участки EXE

Для исследованной PE32-сборки `.text` отображается по формуле
`file_offset = VA - 0x00400C00`.

| Назначение | VA | File offset |
|---|---:|---:|
| Пропуск поиска body attachment nodes | `0x004E8997` | `0x000E7D97` |
| Проверка Snow / вызов hair setup | `0x004E8A1F` | `0x000E7E1F` |
| Пропуск runtime hair update | `0x004E6694` | `0x000E5A94` |
| Загрузчик волос menu-preview | `0x005E7710` | `0x001E6B10` |
| Menu gate Winter / attachment `Hair_Master` | `0x005E76C6` | `0x001E6AC6` |

В таблице приведены адреса исследованной сборки, но `WinxHairPatcher` 0.2.0
не использует их для записи: он сканирует весь выбранный файл и требует ровно
одно совпадение каждого исходного или совместимого пропатченного блока. Патчер
заменяет найденные блоки без изменения размера секции. Маска
полного отключения управляет вызовом hair setup. Отдельная управляющая маска
равна ей с принудительно добавленными ID 1 и 5, сохраняя оригинальную особую
логику Bloom X и Winter. Menu gate использует исходную маску полного отключения:
`bt` по фактическому fashion ID пропускает только attachment `Hair_Master`,
повторяя штатный путь Winter.

Старые патчи 0.1.x с тремя изменёнными gameplay-блоками и оригинальным menu
gate считаются совместимым состоянием миграции. Патчер читает их gameplay-маску
и при следующем применении добавляет menu-блок. Если обе семьи уже изменены,
их маски обязаны совпадать.

## Границы уверенности

Проверены исходные байты, таблица menu ID, detach/attach control flow,
эквивалентность подготовки стека после компактной замены, повторное распознавание
патча и сохранение длины EXE. Четвёртая сигнатура уникальна во всех локальных
pristine, dubteam, gameplay-patched и debug-menu вариантах. Влияние выбранных
комбинаций на изображение в игре ещё требует практической проверки.

Нестандартный EXE допускается, если все четыре подтверждённые сигнатуры найдены
однозначно либо распознано строгое legacy-состояние 0.1.x. Отсутствующая,
частично изменённая, повторяющаяся или рассогласованная сигнатура считается
небезопасной и приводит к отказу без записи файла.
