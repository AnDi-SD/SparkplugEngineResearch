# spCameraManager

Подтверждена ограниченная PC-часть: создание, lifetime хранилища, унаследованный
Copy и Clone. Тип элементов внутреннего массива и API его заполнения пока
неизвестны. [Исходники](../../../Sparkplug/Code/Sparkplug/spCameraManager.h)
не означают полного восстановления менеджера камер или его работы в игре.

## PC-идентичность и раскладка

Class ID `33800A37`, регистрационная и физическая база `spBaseObject`.
Factory `45B080`, getter `45AF50` возвращает registration `75FD00`, основная
таблица `6E718C`. Объект занимает `28` hex байт. Отдельная таблица по `10`
наблюдается физически; исходное имя и декларация второго подобъекта неизвестны.
[PC ABI](../../../Sparkplug/Analysis/PC/spCameraManagerAbi.h) отделён от
переносимого C++-объекта.

| Смещение | Подтверждённое значение |
| ---: | --- |
| `00..0F` | физическая часть Base |
| `10` | вторичная таблица `6E7188` |
| `14` | constructor записывает ноль, роль неизвестна |
| `18` | constructor не присваивает значение, роль неизвестна |
| `1C/20/24` | begin/end/limit массива 32-битных слов |

После успешной factory массив пуст и имеет резерв `32` слова, то есть `80`
hex байт backing storage. Global `75DB98` указывает на полный объект, не на
его подобъект `10`. Создание другого экземпляра заменяет этот указатель.

## Copy, Clone и удаление

PC Copy slot указывает на общий Base `40ECE0`: он возвращает true, не переносит
собственные поля/массив и не меняет singleton. Clone `45B0E0` создаёт новый
экземпляр, регистрирует пару в общем CloneManager и вызывает этот Copy. Поэтому
clone имеет пустой массив, `14=0` и собственное неизвестное значение `18`.

Удаление `45AFE0` вызывает `45AEF0`, затем при bit0 deleting flag освобождает
storage самого объекта. `45AEF0` освобождает backing storage массива, обнуляет
его указатели, завершает вторичную часть и **безусловно** записывает ноль в
global, затем вызывает Base destructor. Старый экземпляр также обнуляет global,
когда более новый ещё жив. Проверка `global==this` перед очисткой изменила бы
поведение оригинала.

Элементы массива в этом пути не разыменовываются, не retain/release и не
удаляются. Это наблюдение об операции освобождения storage; оно не устанавливает
тип элементов или правильный игровой способ заполнения массива. Исследованный
профиль имеет пустой optional список Base `04`, не использует allocator callbacks
и выполняется синхронно.

## Переносимая граница

Общий класс хранит массив сырых `uint32_t` как явно аналитическое представление.
Отдельный captured-input профиль допускает до восьми уже полученных слов и
значения `14/18`; по умолчанию он не квалифицирован. Он не является нативным
Add/Load. Числа, кодирующие original addresses, не приводятся к host-указателям.
Неизвестное constructor-значение `18` представлено отсутствующим `optional`,
а конкретное захваченное значение не объявляется его default.

Логический начальный резерв `32` отделён от физической вместимости host vector,
которая составляет не менее `32`. Его размеры и адреса выделений не являются
нативным ABI. Деструктор освобождает backing storage до очистки singleton;
унаследованный Copy и общий CloneManager используются напрямую. Обычные C++
copy/move запрещены, чтобы они не обходили этот протокол. Host-final не является
утверждением о native finality.

Остальные методы, исходный тип элементов/producer, secondary class, ошибки
выделения, cold startup и глобальный lifetime, PS2 и игровая интеграция остаются
открытыми.
