# wxBlastState

`wxBlastState` физически наследует [`wxCharacterState`](wx-character-state.md).
Class ID — `0x918946D1`, selector — `22`; объект PC и PS2 занимает `0x3C` байт
без собственных полей. Переносимый объект не заявляет соответствие нативному ABI.

Вход переписывает ключ как `(key & 0xFF800081) | 0x81` и ищет анимацию. После
lookup он повторно читает caller-owned key и извлекает пятибитный вариант из
битов `23..27`. Варианты `0..6` отправляют получателю `owner +0x24` уведомление
`0x2747` с payload `{variant, 0}`. Если второй manager содержит персонажа, его
получателю `+0x24` отправляется `0x2780` с `{0, 0}`. Варианты `7..31` вместо
этого отправляют filtered `0x2780`, filter `8`, payload `{0, 0}`.

Затем состояние всегда запускает найденный handle с `mode=false`,
`interrupt=true`, даже если он нулевой или совпадает с прежним. Completion
records для handle сбрасываются перед запуском; fade selector `0` либо `2`
определяет предикат владельца. Pending записывается после callback consumer,
виртуальный update обнуляет слово `+4` контроллера действий владельца. Прежний
pending перед этим не освобождается. Permission возвращает `true` для нулевого
pending; иначе выполняет consuming completion query.

Event hook ищет подстроку `event_blast`, включая имя с префиксом или суффиксом.
Значение глобального signed word `+0x6E4` выбирает стоимость и действие:

| Глобальное значение | Запрашиваемый ресурс | Действие |
| --- | --- | --- |
| Меньше `4` | `15.0` | `7` |
| От `4` до `5` | `20.0` | `8` |
| От `6` | `40.0` | `9` |

PC использует один снимок значения. PS2 после проверки `<6` повторно читает
глобальное поле для сравнения с `4`; профиль host сохраняет этот порядок.
Успешный resource callback вызывает выбранное действие, затем уведомляет
получателя второго персонажа кодом `0x2783`, payload `{0, 0}`. При отказе
главному получателю `+0x2B4` отправляется `0x27D1`, payload `{0xCC, 0}`.

Если blast-подстроки нет, полное совпадение `event_dragon_fire` отправляет
filtered `0x274B`, filter `8`, payload `{5, 0}`. Другие строки ничего не меняют.
Все targeted уведомления пропускают нулевого получателя. В проверке второго
персонажа и доставке исходник выполняет два чтения его указателя.

Copy пустой и наследуется от базы; clone создаёт новый объект с начальными
flags и пустым pending. Остальные transition/reset hooks принадлежат базе.
Компонент восстанавливает собственные методы, но требует привязанных resource,
consumer, manager/owner и notification служб; полный граф игры этим не закрыт.
