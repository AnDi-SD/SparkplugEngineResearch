# wxBeforeTrollFightState

Class ID `3EFE78B7`, физическая и регистрационная база `wxCharacterState`.
PC и PS2 выделяют `0x4C` байт. Selector `10` равен `8`; собственные 32-битные
поля `3C/40/44/48` обнулены конструктором. Восстановленный класс находится в
`Winx/Code/wxBeforeTrollFightState`; внешние объекты и игровой RNG подключаются
через обязательный `wxBeforeTrollFightStateHost`.

| Поле | Подтверждённое использование |
| --- | --- |
| `3C` | Беззнаковый срок переключения, `0` отключает ожидание |
| `40` | Handle анимации с packed key `00008000` |
| `44` | Handle анимации с packed key `00000000` |
| `48` | Handle анимации с packed key `00800000` |

Вход `1C` загружает три handle через animation manager с внешним owner word
`128` на PC / `134` на PS2. Порядок загрузки: `44`, `48`, `40`. Затем берёт
беззнаковый 32-битный результат игрового генератора случайных чисел.
PC выбирает `44` при результате `< 80000000`, иначе `48`.
PS2 преобразует результат в float32 перед сравнением с половиной диапазона:
результаты `7FFFFFC0..7FFFFFFF` уже выбирают `48`, хотя PC выбирает `44`.

При отличии выбранного handle от pending вход освобождает pending,
запускает выбранный handle с mode=true, interrupt=true и сохраняет его.
После этого читает clock word `1C` и ещё один random word, записывает срок
`clock + 1000 + random % 1501` с переполнением uint32. При совпадении handle
playback и обновление срока пропускаются. В конце всегда вызывает базовый вход:
тот снова освобождает pending и вызывает виртуальный update. Этот порядок
сохранён как поведение оригинала, несмотря на промежуточный playback.

Update `30` при once-флаге базы `1D` регистрирует объект у completion consumer,
подписывает объект на key `5` у `spSubscriptionManager`, затем очищает `1D`.
Если срок `3C` ненулевой и **строго меньше** текущего clock word, берёт handle
`40`. При его отличии от pending освобождает pending, запускает mode=false,
interrupt=true, сохраняет handle и обнуляет срок. Совпадение handle оставляет
срок ненулевым. Сравнение срока беззнаковое и не является модульной проверкой
прошедшего интервала. Update не меняет key запроса.

Permission `34` всегда возвращает false; выход и остальные state hooks
наследуются от базы. Базовый Reset сохраняет собственные четыре слова.

Собственный notification hook находится в PC slot `04` / PS2 slot `0C`:

- Code `3`: сравнивает packet word `1C` с handle `40`. При совпадении выбирает
  `44/48` по random. Если handle отличается от pending, запускает mode=true,
  interrupt=true **без предварительного release**, сохраняет handle и задаёт
  новый срок по clock и следующему random. Совпадение pending пропускает запись
  срока. Несовпадающее packet word игнорируется.
- Code `272A`: проверяет младший byte packet word `18`. При нуле действий нет.
  При ненулевом byte освобождает pending, вызывает node из `owner24->24` через
  PC vslot `34` / PS2 vslot `3C` с аргументами `(0,1)`. Затем проверяет список
  этого node: при наличии первого ненулевого элемента обнуляет его byte `88`
  на PC / `84` на PS2. Если PC-объект `owner124->12C` существует, вызывает
  внешнюю reset-службу. Её исходный тип и имя метода не установлены. PS2
  при ненулевом `owner130->138` обнуляет слова в порядке
  `1C8/1CC/1D0/1BC/1C0/1C4/1D4/1D8/1DC/1A0/1A4/1A8/194/198/19C`.
  PS2 повторно читает owner/node при доступе к первому элементу списка;
  PC использует уже прочитанный node. Эти платформенные операции сохранены
  отдельно: PC-служба не объявляется эквивалентной PS2-записям.
- Другие коды игнорируются.

Деструктор обязательно удаляет объект из completion consumer и отписывает
его от key `5` менеджера подписок, затем вызывает деструктор базы. Вызовы
удаления не ограждены once-флагом `1D`. Поэтому модель связей и времени жизни
нельзя заменить пустым деструктором или успешной заглушкой при отсутствии
consumer. Clone создаёт поля конструктора; полный жизненный цикл объекта
должен учитывать эти внешние связи.

Переносимая модель времени жизни явно отделена от native ABI. Фабрика и clone
создают неподключённый аналитический объект; `BindForAnalysis` начинает его
связанный жизненный цикл. Owner, consumer и host должны существовать до
уничтожения состояния; повторная привязка запрещена. Деструктор связанного
объекта всегда вызывает удаление из consumer, затем отписку от key `5`,
включая случай, когда вход/update не вызывался. Уничтожение неподключённого
аналитического объекта не представляет native-деструктор с null consumer.
Host callback удаления не может бросать исключения; notification hook
сохраняет `noexcept` общего переносимого интерфейса и требует исправных связей.
Обработка сообщений принимает явно нормализованный host-пакет, а не сырой
native указатель. Подписки могут подключаться к общему `spSubscriptionManager`.

Собственная логика перечисленных методов подтверждена. Реальный игровой RNG,
внешние consumer/node/reset-службы и полный игровой жизненный цикл остаются
границами host, поэтому это не утверждение о полном восстановлении класса
в игре. Узкая проверка — `WinxBeforeTrollFightStateTests`.
