# wxAIManager

Менеджер AI и нескольких сценариев уровня, class ID `56887B3F`. Регистрационная база и первый физический подобъект — `spBaseObject` (`415352A1`). По смещению `10` находится второй полиморфный подобъект, связанный с singleton; исходное имя его C++-типа не установлено.

Переносимая [реализация](../../../Winx/Code/wxAIManager.cpp) и [интерфейс](../../../Winx/Code/wxAIManager.h) содержат PC-логику списка, обхода, сообщений, счётчиков, условий срабатывания и порядка внешних вызовов. [Host-интерфейс](../../../Winx/Analysis/Host/wxAIManagerHost.h) передаёт работу внешним объектам игры: сцене, членам списка, таймерам, камере и данным игрока. Он не содержит реализаций по умолчанию и не является оригинальным базовым классом.

| Основная vtable | `00706640` | `004920B0` |

| Destructor / deleting destructor | `005A6070 / 005A61B0` | `00224AB0` |

Все размеры и смещения здесь шестнадцатеричные. Точные 32-битные структуры отделены от переносимого объекта: [PC layout](../../../Winx/Analysis/PC/wxAIManagerAbi.h), [PS2 layout](../../../Winx/Analysis/PS2/wxAIManagerAbi.h). Совпадение размеров не означает совместимости контейнеров.

| Поле | PC | PS2 | Начальное состояние |
| --- | --- | --- | --- |
| Base | `00..0F` | `00..0F` | constructor `spBaseObject` |
| Вторичная vtable | `10` | `10` | таблица менеджера |
| Контейнер | `14..1F` | `14..1F` | пустой список |
| Первый курсор | `20` | `20` | end |
| Курсор ограниченного обхода | `24` | `24` | end |
| Счётчики дверей | `28 / 2C` | `28 / 2C` | 0 |
| Флаг срабатывания уровня 14 | `30`, byte | `30`, byte | 0 |
| Счётчики уровней 21 / 18 | `34 / 38` | `34 / 38` | 0 |
| Неизвестная связь | `3C` | `3C` | null |
| Узел `RespawnPoint` | `40` | `40` | null |

PC хранит указатель на выделенный sentinel по `18`, число элементов по `1C`. Word `14` и padding после byte-полей не инициализируются. PS2 хранит число элементов по `14`, встроенный sentinel — по `18..1F`; направление ссылок в узле также отличается от PC. Данные узла списка лежат по `+8` на обеих платформах.

## Время жизни, владение и Copy

Constructor записывает себя в глобальную singleton-ссылку и подписывает основной объект на группу сообщений `11` (десятичное). Destructor уничтожает членов списка виртуально, освобождает узлы, снимает подписку, обнуляет `3C`, уничтожает контейнер и базу. Глобальная ссылка обнуляется без проверки, указывает ли она ещё на уничтожаемый экземпляр.

Добавление ищет совпадение указателя; при отсутствии добавляет объект в конец. Повторное добавление ничего не меняет. Удаление из списка освобождает только узел, не сам объект: вызывающий снова отвечает за его lifetime. Если удаляемый узел совпадает с одним или обоими курсорами, соответствующие курсоры передвигаются на следующий узел.

Copy унаследован непосредственно от `spBaseObject`: успешно завершается без переноса или очистки payload получателя. Clone создаёт пустой менеджер, регистрирует соответствие source/destination, затем вызывает виртуальный Copy источника. Новый экземпляр подписывается на сообщения и заменяет singleton; содержимое списка, счётчики и ссылки source не копируются.

Переносимая RTTI factory требует явной установки host через `SetFactoryHostForAnalysis`. Без него она сообщает об ошибке. Это наша привязка внешнего окружения, не восстановленный accessor игрового singleton. Прямой constructor принимает host по ссылке; host должен пережить менеджер и его clones.

Native Clear оставляет курсоры без перенастройки и может оставить их указывать на освобождённые узлы. Переносимый `ClearForAnalysis` завершает использование списка: последующее добавление явно отклоняется. Он не выдаёт безопасное повторное заполнение за оригинальное поведение. Destructor после отдельного Clear повторно выполняет снятие подписки, как и оригинал. Удаление из списка во время обычного broadcast или из callback уничтожения не поддерживается; native обход в этих случаях также не обеспечивает сохранность текущего узла.

## Обход AI

Update сначала проверяет внешний блокирующий предикат. При true возвращает false без обхода и сценариев уровня. Иначе последовательно выполняет ограниченный обход, сценарий уровня 14 и сценарий уровня 6, после чего возвращает true.

Ограниченный обход запоминает начальное число элементов и выполняет не более трёх итераций. В каждой заново проверяет, не опустел ли список. Курсор `24`, достигший end, переходит к началу. Курсор передвигается **до** вызова объекта; нулевой объект пропускается. У ненулевого объекта вызывается PC slot `2C` с адресом неинициализированного локального блока в 36 байт. Если предикат возвращает true, вызывается slot `40` того же объекта без аргументов. Тип блока и исходные имена этих методов неизвестны. Это не основание считать члены списка экземплярами `wxAIAction`.

Зафиксированный начальный размер и повторное чтение текущего размера имеют значение, если callback удаляет элементы. Удаление следующего элемента корректирует уже передвинутый курсор. Null допустим для этого прохода и очистки; broadcast, напротив, разыменовывает каждый элемент без проверки.

## Входящие сообщения

Код находится в первом word сообщения; значение читается по native offset `18`. Переносимый `wxAIManagerMessageForAnalysis` — отдельное представление этих двух значений.

| Код | Действие |
| --- | --- |
| `2712` | Сброс флагов `30/44` и счётчиков `28/2C/34`. Если значение равно 6, поиск `RespawnPoint` в сцене с аргументами `(true, false)` и сохранение результата в `40`. |
| `27A3` | Обработка таймера падения; проверяется младший byte значения. |
| `27B6` | Рассылка значения всем элементам через PC slot `4C` / PS2 slot `54`. |
| Другие | Ничего не происходит; базовый notification не вызывается. |

Сброс уровня сохраняет счётчик `38`, поле `3C`, оба курсора и список. Для уровня, отличного от 6, сохраняется также прежний `RespawnPoint`. PC broadcast передаёт целое входное word; PS2 предварительно оставляет только младший byte. Переносимая реализация следует PC.

## Сценарии уровня

Условия ниже используют десятичные номера уровней и значения счётчиков.

- Счётчик `28` увеличивается при каждом отдельном вызове. При результате ≥ 2 отправляет для `door_03` и `door_05` сообщения `2733`, затем `2736`, затем `2732`; для каждого кода сначала первая дверь, затем вторая. Тип сообщения 6, значение 0.
- Счётчик `2C` работает аналогично с порогом 3 и дверями `door_01` / `door_06`. Повторные вызовы после порога повторяют рассылку; счётчики не насыщаются и имеют 32-битное переполнение.
- Отдельный helper уровня 21 увеличивает `34`; при результате ≥ 2 записывает true во внешний игровой byte `2CB5`.
- Helper уровня 18 сначала проверяет внешний флаг `79`. Если он снят и текущий уровень равен 18, увеличивает `38`; только при точном равенстве 2 обнуляет его и вызывает внешний метод с `(3, true)`.
- В Update уровня 14, если `30` снят и signed-поле игрового прогресса `514` меньше 5, проверяется квадрат расстояния игрока до `(107, 1075, 764)`. При результате строго меньше `22500` отправляются `(2735, door_06, 0)`, `(2733, door_06, 1)`, `(2733, door_01, 1)`, все с типом 6; затем устанавливается `30`.
- В Update уровня 6, если `44` снят и Y игрока строго меньше `-240`, вызывается внешний таймер с задержкой 200 мс, затем устанавливается `44`.

Helper `battle_cage` работает только на уровне 30. Ищет узел с `(true, true)`, при наличии передаёт ему `(enabled, true)`, ищет дочерний `collision` с `(true, false)` и, если его первый объект существует, записывает туда byte `enabled`. На PC вход содержит защищённую загрузку singleton; полный запуск этого входа с восстановленным protection startup не подтверждён. Последовательность после загрузки и независимый PS2-код установлены.

При сообщении таймера `27A3` с ненулевым младшим byte снимается `44`, если он был установлен. При нулевом младшем byte, независимо от текущего `44`, происходит следующая последовательность:

1. Игрок перемещается в позицию сохранённого `RespawnPoint`.
2. Копируются девять word его ориентации в transform игрока, dirty flags объединяются с `1`, вызывается transform slot `30(0)`.
3. Сбрасывается внешний объект камеры.
4. Запускается второй таймер на 1500 мс.
5. Внешний счётчик игрока уменьшается на 1 без проверки нуля.
6. Отправляется сообщение `2716`, тип 4, числовой target 4, значение 0.

В этой ветви нет защиты от отсутствующего `RespawnPoint`; корректное внешнее состояние необходимо. Сам флаг `44` здесь не снимается. Диагностический `printf` оригинала не перенесён в игровой интерфейс.

## Границы реализации

Это общая переносимая реализация поведения менеджера, а не ABI-совместимый объект для подстановки в память игры. Собственные имена методов с `ForAnalysis` описывают установленный смысл и не заявляются исходными символами. Native allocator, реализация контейнера, protected singleton accessors и служебное allocator-mode переключение остаются вне переносимого класса.

PC является целевым поведением. PS2 подтверждает идентичность, lifetime и общую последовательность сценариев, но имеет свой контейнер, вызовы, сокращение broadcast-аргумента и EE floating-point операции. Равенство платформ во всех входных состояниях не заявляется. PC проверка расстояния учитывает отдельное округление Z в float; переносимый double не воспроизводит все режимы точности, исключения и крайние случаи x87. Реальная работа сцены, таймеров и объектов AI зависит от предоставленного host.
