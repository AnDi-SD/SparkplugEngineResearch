# wxAlfeaDoorTrigger

Триггер синхронизируемой поворотной двери Алфеи, class ID `6AE9310E`. Регистрационная и физическая база — `wxPivotingDoor` (`4AC3694A`). Собственная логика находится в [wxAlfeaDoorTrigger.cpp](../../../Winx/Code/wxAlfeaDoorTrigger.cpp), интерфейс — в [wxAlfeaDoorTrigger.h](../../../Winx/Code/wxAlfeaDoorTrigger.h).

Реализованы собственные constructor/destructor, Copy/clone, RTTI, четыре сообщения, отложенное открытие, условия взаимодействия, фазы поворота и описание двух enum-свойств. Методы ещё не восстановленной базы `wxPivotingDoor`, сцена, игровое время и общая математика подключаются через обязательный [host-интерфейс](../../../Winx/Analysis/Host/wxAlfeaDoorTriggerHost.h). Это реализация собственного поведения класса, а не готовая автономная система дверей.

Constructor сначала вызывает constructor `wxPivotingDoor`, устанавливает собственную vtable, группу и три byte-поля, снимает inherited byte `125/131`, затем подписывает объект на группу сообщений `23` (десятичное). Door ID сохраняет содержимое памяти выделения: ноль не является подтверждённым значением по умолчанию. Переносимый constructor поэтому принимает явный `initialDoorIdStorage`; argumentless RTTI factory получает это значение у host. Позднее ID можно установить через setter.

Cleanup снимает подписку на группу 23, вызывает cleanup базы и возвращает true независимо от его результата. Destructor выполняет этот cleanup, затем destructor базы. Отдельный cleanup не делает последующий destructor пустым.

## Сообщения

Native сообщение содержит code по `00`, sender по `10`, два слова значений по `18/1C`. Переносимый `wxAlfeaDoorMessageForAnalysis` представляет эти значения отдельно от 32-битной памяти игры.

| Код | Условия и действие |
| --- | --- |
| `27AC` | При совпадении value18 с Door Group записывает младший byte value1C в inherited interactionBlocked. |
| `27AD` | При совпадении value18 с Door ID снимает notifyPlayer, ставит queued и locked в 1, сохраняет младший byte value1C как instant. |
| `27AE` | Если sender — другой объект, Door ID совпадает и moving=0: сохраняет instant, вызывает виртуальную анимацию, затем ставит moving=1. |
| `27AF` | При совпадении Door ID и текущем угле, не равном нулю, ставит enabled=moving=1, угол=targetAngle, phase=3 и запоминает текущее время. |
| Прочие | Передаёт сообщение в notification базы `wxPivotingDoor`. |

Распознанные сообщения не передаются базе даже при несовпадении группы/ID. Отбрасывание sender=this в `27AE` предотвращает реакцию двери на собственную рассылку. `27AF` не сбрасывает locked/queued/instant. PC проверяет угол через x87: оба знака нуля отклоняются, unordered-сравнение не отбрасывает NaN.

Собственный Update сначала проверяет queued. Если он установлен, вызывает виртуальную анимацию, после её возврата снимает queued и ставит moving=1. Затем всегда вызывает Update базы и возвращает true, игнорируя его bool-результат. Порядок существенен: виртуальный вызов и его рассылки происходят до изменения queued/moving.

## Фазы поворота

Каждый вызов анимации получает текущее время и вычисляет `elapsed = now - started` как uint32, с переполнением по модулю 2³². В конце **каждой** ветви узлу задаётся поворот вокруг `(0, 1, 0)` на `initialAngle + angle`, после чего его dirty flags объединяются с `1`.

| Исходная фаза | Действие |
| --- | --- |
| 0 | Запоминает now, обнуляет angle, ставит phase=1 и выполняет начальные уведомления. Интерполяция в этом вызове ещё не происходит. |
| 1 | При instant!=0 ставит angle=targetAngle, иначе angle=`elapsed / duration * targetAngle`. Если `abs(targetAngle) <= abs(angle)`, ограничивает угол целевым и ставит phase=2. |
| 2 | Оставляет целевой угол, ставит locked=1, снимает moving и возвращает phase=0. При autoDisable!=0 также снимает enabled. |
| Любая другая | Вычисляет angle=`(1 - elapsed / duration) * targetAngle`. Только при `elapsed > duration` обнуляет угол, moving и phase; при autoDisable!=0 снимает enabled. |

Для закрытия равенство elapsed и duration ещё не завершает движение, хотя угол уже может стать нулём. Фаза 2 также требует отдельного вызова после достижения целевого угла фазой 1. Длительность не ограничивается снизу; обработка деления на ноль не подменяется успешным мгновенным переходом.

В фазе 0 порядок внешних действий следующий:

1. Если notifyPlayer!=0, отправить игроку notification `27D1` со значениями `(50, 0)`; иначе лишь поставить notifyPlayer=1.
2. Найти в сцене узел по inline-имени с аргументами `(true, false)`. Поиск выполняется и для пустой строки: оригинал проверяет адрес массива, а не его первый символ.
3. Если узел найден, поставить byte `20` его первого компонента в 1, затем то же для второго. Наличие обоих компонентов предполагается, проверок длины нет.
4. Отправить группе 23 сообщение `27AE` с Door ID и byte instant. Sender — текущая дверь.
5. Установить поворот собственного узла и dirty bit.

## Условия взаимодействия

Обычный Enter делегирует базе только если locked=0, interactionBlocked=0 и специальный предикат false. Специальный предикат true ровно при Door ID=2, игровом progress-поле `514`=2 и снятом внешнем флаге `19` (hex).

CanInteract сначала вызывает предикат `wxPivotingDoor`. Если он false, геометрические проверки не выполняются. Иначе берёт направление игрока из элементов transform `58/60`, обнуляет Y и нормализует. Затем строит горизонтальный вектор от позиции игрока к позиции узла двери, нормализует и вычисляет угол между векторами. Результат true только при угле строго меньше 2 радиан. Это отдельная проверка от запретов в Enter.

Общая математика вынесена в host-вызовы оригинальных по назначению helpers: PC `41D2D0` нормализует с порогом длины `0.001f`, `4DAF00` возвращает 0 для покомпонентно близких векторов или вычисляет acos скалярного произведения. Направление на дверь, порог угла и порядок вызовов остаются в общем коде класса.

## Copy, clone и свойства

Copy сначала вызывает Copy базы. При false сразу возвращает false. При успехе переносит Door Group, Door ID, locked и queued. **Instant не копируется**, поэтому у свежего clone он остаётся нулевым, а при Copy в существующий объект сохраняет значение получателя. После собственных полей PC вызывает пустой marker clone manager с class ID. Clone создаёт экземпляр через factory, регистрирует связь source/destination и вызывает виртуальный Copy; при неудаче уничтожает получателя.

`RegisterPropertiesForAnalysis` описывает два enum-свойства в исходном порядке, затем вызывает регистрацию свойств базы и возвращает true. Значения индексов начинаются с нуля; исходное написание строк сохранено.

| Свойство | Значения по порядку |
| --- | --- |
| `Door Group : ` | FaragondaDoor, LoomaDoor, Others, Girl Appartment, BallroomAnteroom |
| `Door ID : ` | FaragondaDoor, LoomaDoor, GirlAppartment, BloomDoor, StellaDoor, MusaDoor, LibraryDoor, SimulationDoor, BallRoomDoor, EastAnteroomDoor, WestAnteroomDoor |

Оба setter записывают целое uint32 без проверки диапазона enum. Enum-схема — отдельный явный вызов: переносимый RTTI manager не запускает игровой reflection backend автоматически.

## Границы переносимого кода

Переносимый C++-объект наследует существующий `spNamedObject`; недостающие уровни `spEntity → wxEntity → wxGenericTrigger → wxPivotingDoor` представлены регистрационными метаданными и host-вызовами, а не фиктивными реализациями. Проверка IsKindOf описывает игровую цепочку регистрации; она не разрешает native casts или приведение к отсутствующему C++-классу базы.

Исходные имена методов неизвестны. Имена `vfunc_*` используют PS2-смещения таблицы: cleanup `40`, update `48`, predicate `54`, animation `58`, enter `5C`; PC-смещения на 8 меньше. Методы и состояния `ForAnalysis` — наши аналитические имена.

PC Copy базовой двери содержит защищённый переход и остаётся внешней зависимостью. Поведение собственной части проверяется отдельно от реализации базы. Внешние методы должны работать с тем же объектом и общим состоянием, сохранять порядок callback и переживать lifetime триггера. Нет заглушек, автоматически объявляющих базовую дверь работоспособной.

PS2 имеет больший layout и самостоятельно подтверждённые методы с той же общей логикой. Его EE floating-point код и полная базовая цепочка здесь не исполняются. PC-интерполяция использует x87; переносимый double не заявляется точной заменой всех режимов extended precision и исключений. Отрисовка, матрица реального узла, маршрутизация сообщений и базовая геометрия требуют соответствующего host.
