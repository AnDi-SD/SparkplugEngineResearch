# Разработка и сопровождение

Правила распространяются на приложения, общие библиотеки и восстановленные исходники. Зависимости направлены от наших программ к общим исходникам Sparkplug/Winx, а источник истины — оригинальная игра.

## Игровая логика

1. При расхождении сначала устанавливаем поведение игры на тех же входах и в соответствующем состоянии. Восстановленную логику исправляем только при доказанной ошибке реконструкции; иначе исправляем приложение или его обвязку. Особенности оригинала сохраняем, даже когда они неудобны.
2. Поддерживаем одну общую реализацию логики в `Sparkplug/` и `Winx/`. C# обращается к ней через тонкий мост. Не создаём отдельные копии игровых sampler, serializer и алгоритмов для каждого инструмента.
3. ОС, устройства и современные графические API принадлежат нашему платформенному слою. Целевые API — OpenGL и Vulkan. Исторический DirectX-код в восстановленных исходниках описывает оригинал; он не задаёт архитектуру нового backend.
4. Собственный код, адаптеры и предположения обозначаем явно. Неизвестный метод, имя, ветвь или тип поля остаются неизвестными; успешная заглушка и поведение нашего приложения не служат доказательством поведения игры. Регистрационную базу класса не приравниваем автоматически к физическому C++-наследованию.

Для исправления реконструкции сохраняем оригинальное поведение, доказанную ошибку и относящуюся к исправлению проверку. Собственные технические замены остаются общими для потребителей и явно отличаются от восстановленного эталона.

## Где хранить материалы

| Материал | Место |
| --- | --- |
| Устройство движка и игры, формат, семантика поля | `docs/engine`, `docs/game`, `docs/formats`, `docs/reference` |
| Восстановленная реализация | `Sparkplug/`, `Winx/` |
| Наш алгоритм, приложение, backend или мост | `tools/` либо явно обозначенный общий `Sparkplug/Analysis/Host` |
| Инструкция пользователя и устройство конкретного инструмента | Рядом с инструментом: `README.md`, `docs/` |
| Рабочий журнал | `.private/journal/` |
| Доказательства, измерения и воспроизводимые результаты | `.private/evidence/` |
| Текущие задачи и приоритеты | `.private/plans/` |
| Одноразовые эксперименты и их рабочие зависимости | `.private/research/` |
| Исторические материалы без изменения байтов | `.private/archive/`; прежние dossiers — `.private/docs/research/` |
| Игровые файлы, EXE, извлечённые payload, локальная база, сборки | `local-data/` и уже принятые игнорируемые каталоги артефактов |

Не перестраиваем `local-data/` в рамках редактирования документации. Не публикуем игровые файлы, извлечённые ресурсы и локальные базы. Датированные доказательства сохраняем без переписывания под новые исходники или новые пути. Изменение текущего дерева Git само по себе не удаляет старые версии файлов из истории.

Публичная статья отвечает на вопрос, как работает система. В ней нужны платформы, типы, размеры, порядок операций, владение и честные границы знания. Ход получения этих сведений, контрольные суммы проверочных входов, статистика прогонов и планы хранятся закрыто. Спецификацию формата пишем один раз; инструкции инструментов ссылаются на неё.

## Организация исходников

Структура отражает ответственность и зависимости. В корне инструмента оставляем README, при необходимости CHANGELOG, файлы проекта/сборки и основные точки запуска. Подробные руководства, контрактные описания и документы выпусков располагаем в `docs/`. Исходники, тесты и служебные команды отделяем, когда у инструмента действительно есть эти части. Существующее осмысленное разделение на Core, GUI, CLI и тестовые проекты сохраняем.

- Новая папка объединяет связанную работу с понятными входами и результатом: например, чтение доноров, текстуры, подготовку скелета или запись графа. Расширение файла или общий префикс имени сами по себе не задают модуль.
- Для новой папки обычно нужны несколько связанных файлов и самостоятельная ответственность. Один файл оставляем в ближайшей подходящей группе; отдельный каталог оправдан только реальным контрактом сборочной системы, внешнего пакета или независимого ресурса. Пустые уровни и папки «на будущее» не создаём.
- Большую группу делим, если в ней смешались разные причины изменений и стало трудно найти владельца операции. Не делим по алфавиту или ради одинакового количества файлов; верхнего лимита файлов, заменяющего анализ ответственности, нет.
- Не создаём свалки `Utils`, `Common`, `Misc` или универсальные `Services`. Общий код выносим при нескольких реальных потребителях и явном контракте. Восстановленная игровая логика остаётся в Sparkplug/Winx.
- Крупный файл с несколькими обязанностями требует отдельного разбора. Перенос файла в подпапку не является декомпозицией его логики. Разделение поведения проверяем отдельно от механического переноса.
- Перемещаем ограниченную связанную группу. Сохраняем байты исходников, если меняется только путь; одновременно обновляем project/include/import paths, ссылки документации, пути ресурсов и manifests упаковки. Публичные имена и форматы не меняем ради красоты дерева.
- После переноса проверяем новый состав сборки, отсутствие потерянных или дважды включённых файлов и соответствующий законченный сценарий. Для документов выпуска сохраняем содержимое и имена в готовом пакете. Исторические доказательства не исправляем под новые пути; новую карту перемещения сохраняем отдельно.

Небольшой инструмент может оставаться плоским, если его файлы действительно относятся к одной операции. Типовая структура — ориентир, а не требование создавать одинаковые каталоги во всех программах. Ответственность групп и оставшиеся границы описываем в существующем `docs/development.md` или README.

## Сборка

Текущие приложения с общим C++-ядром собираются на Windows x64. Нужны .NET SDK, MSVC x86/x64 (из Visual Studio или отдельных Visual Studio Build Tools), Windows SDK и CMake. VS Code может служить единственным редактором; [настройки и задачи](.vscode/README.md) находятся в репозитории. Для `.slnx` и используемой Avalonia рекомендуется SDK 9.0.300 или новее; целевая среда выполнения приложений — .NET 8. Сборка отдельных `.csproj` возможна SDK 8, с ограничениями совместимости генераторов Avalonia.

Из корня репозитория:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools/SparkplugViewer.Native/Build-Native.ps1 -Configuration Release -BuildWorkers 1
dotnet build tools/SmoViewer/SmoViewer/SmoViewer.csproj -c Release -m:1 -nr:false -p:UseSharedCompilation=false -p:SkipSparkplugNativeBuild=true
dotnet build tools/SMOTextureTool/SMOTextureTool/SMOTextureTool.csproj -c Release -m:1 -nr:false -p:UseSharedCompilation=false -p:SkipSparkplugNativeBuild=true
```

`SkipSparkplugNativeBuild` используем после сборки актуальной native DLL. Без него проекты сами вызывают сборку моста. Инструкции других программ находятся в [каталоге инструментов](tools/README.md). Внешние зависимости вроде FBX SDK и Remix описаны у соответствующего инструмента.

## Проверка изменений

Проверяем законченную затронутую операцию, включая связи объектов, владение, запись и повторное чтение там, где это применимо. Сборка сама по себе не доказывает соответствие игре. При различии ищем первый несовпадающий этап, не маскируем его последующей коррекцией результата. PC приоритетен; сведения о PS2 и её отличиях сохраняем независимо.

Для документации:

```powershell
python tools/RepositoryMaintenance/catalog.py
python tools/RepositoryMaintenance/check_docs.py
```

Первый скрипт обновляет навигацию из публичных Markdown-файлов; второй проверяет ссылки, полноту каталога и отсутствие ссылок базы знаний в закрытые материалы. Изменения структуры завершены только после исправления ссылок из исходников, проектов и инструкций.

Для выбранной C++-проверки используем `Build-Native.ps1 -RunChecks -CheckSuites FullLoader` или другой затронутый suite. После связного изменения общего контракта проверяем соответствующий полный сценарий. Успешные проверки не повторяем без новой причины. Внешние зависимости и оригинальные файлы не скачиваем и не изменяем при обычной проверке документации.

| Изменение | Подходящая проверка |
| --- | --- |
| Текст, ссылки и навигация | `catalog.py --check`, `check_docs.py`; генератор с записью нужен при изменении каталога |
| Native-контракт | Каноническая native-сборка, затронутые `CheckSuites`, законченная операция и сравнение с оригиналом при изменении реконструкции |
| Managed-обвязка | Сборка с актуальной native DLL и затронутый сценарий приложения |
| Импорт, экспорт или сериализация | Запись и повторное чтение, повреждённые входы и значимые проверки реального ресурса |
| Только пути исходников | Сверка байтов, project/include/import и упаковочных ссылок, сборка и затронутая операция |

## Среда и ресурсы

Тяжёлые сборки и исследовательские профили запускаем по текущим свободным ресурсам с запасом для системы. Параллелизм выбираем по измерениям. Независимые случаи не разделяют изменяемый выход и неизвестное игровое состояние. Для ограниченных опытов сохраняем пределы, владение и освобождения; новый опыт получает новое состояние и результат.

Текстовые файлы читаем и записываем как UTF-8. Для PowerShell задаём `Get-Content -Encoding utf8`, для Python с произвольными символами в выводе — `python -X utf8`. Автоматизацию PowerShell запускаем с `-NoProfile`, если ей не нужны пользовательские настройки. Проверяем результаты вложенных процессов, а не только код оболочки.

Перед коммитом и отправкой проверяем состав изменений, документацию, ссылки и необходимые тесты. Commit и контрольная сборка не являются релизом; упаковка и выпуск выполняются по отдельной задаче.
