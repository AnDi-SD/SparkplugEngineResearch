# Обязательные правила работы в репозитории

Перед изменением софта или восстановленных исходников прочитать
[основы разработки](docs/engine/software-development-rules.md) и применять их
вместе с [манифестом исследования](docs/research/research-manifesto.md).
Правила закреплены пользователем 8 сентября 2026 и действуют для всех инструментов.

Текущий приоритет уточнён пользователем утром 10 сентября: **исследовать весь
каталог классов PC и PS2 исполняемых файлов, максимально эффективно; PC раньше**.
Разработка ядер `tools/` поставлена на паузу. Очередь исследования единая:
игровая и движковая логика равноправны, использование классом SMO/SAN или
конкретным инструментом больше не является условием его приоритета.
Выбирать классы и семейства по ожидаемому приросту подтверждённых знаний,
доступности кода и общим зависимостям; не застревать на одном защищённом пути.
Подтверждённый общий результат обязательно записывать для обеих платформ,
с отдельными адресами, evidence и оценками. Совпадение имени/ID или PC-проверка
сами по себе не доказывают PS2-поведение. Переиспользовать уже выполненный
анализ, регулярно обновлять общий учёт и сохранять проверенные commits.
Датированные старые отчёты сохраняют прежний объём задач. Новое направление
не разрешает выдуманные реализации или несогласованную замену оригинала.

1. **Игра всегда права.** Цепочка зависимостей: наши программы → восстановленные
   исходники → игра. При расхождении сначала установить причину по оригинальной
   игре. Исправлять восстановленную логику можно только при доказанной ошибке
   реконструкции; в остальных случаях исправлять приложение или его обвязку.
   Подгонять классы под ожидаемый нашим софтом результат запрещено.
2. **Одна общая реализация игровой логики и логики движка.** По умолчанию использовать
   восстановленные классы `Sparkplug/` и `Winx/` напрямую или через тонкий
   межъязыковой мост. Не создавать их C#-копии, параллельные sampler/serializer
   и обходные реализации для отдельных инструментов. Недостающую логику
   исследовать по игре и дополнять в общем восстановленном коде.
   Если прямое использование невозможно или измерения показывают неэффективность,
   предложить переписывание с нуля: указать препятствие/замеры, ожидаемый выигрыш,
   границы замены и проверку по игре. Реализовывать такую замену после согласования
   с пользователем. Замена остаётся общей для инструментов; восстановленный код
   сохраняется как эталон, игра остаётся источником истины.
3. **Платформенный слой пишем сами.** Работа с ОС, устройствами и графическим API
   принадлежит нашему современному backend. Целевые графические API — OpenGL
   и Vulkan. DirectX 9 и привязки Windows 98/XP не переносятся в приложения.
   Новая реализация backend сохраняет подтверждённые игровые правила и результат.
4. **Каждый нестандартный случай сообщать пользователю.** Если следующий шаг
   не укладывается в правила или их применения недостаточно для понятного решения,
   сразу описать случай и приостановить затронутую задачу. Не подгонять решение
   под формулировки, не обходить ограничения и не вводить скрытые «чёрные ящики».
   Зафиксировать причину и перейти к следующей независимой задаче в согласованном
   объёме работы. В итоговом отчёте перечислить все такие случаи, что отложено
   и варианты решения с рекомендацией. Возвращаться к спорному шагу после решения
   пользователя; отсутствие ответа не является согласием. Независимую работу
   продолжать без повторного запроса разрешения.

При изменении восстановленной логики записывать оригинальное поведение,
доказанную ошибку реконструкции и относящуюся к исправлению проверку.
Адаптеры, UI и платформенный код не выдавать за восстановленные классы игры.

Промежуточная проверочная сборка не означает завершения всей переработки.
Граница завершения определяется задачей пользователя. Контрольная компиляция
и локальный commit не являются выпуском. Не превращать очередной этап
разработки в упаковку релиза без задачи на выпуск.
